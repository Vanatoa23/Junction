# Entrant 64: Tidepool, a balanced supply-network MVP (lens: Balanced generalist)

## 0. Bold bet
Instead of a showcase of one exotic technology, Tidepool runs one boring, reliable spine (Postgres, one TypeScript API, one Valio order path) and spends every spare hour on the three things judges score most: a flawless Valio buyer flow, a live Context.dev run visible on screen, and a visibility model that a judge can test in front of them. It wins on dependability: the demo is designed so that any single component failing still leaves a complete story.

## 1. Summary and name
- Name: **Tidepool** (a small, self-contained network that grows as more pools connect).
- A hotel buys through Valio. It sees its own supply map, a risk alert on an upstream dairy producer, visible alternatives with price ranges, and a procurement proposal. A manager approves, the order goes through the Valio mock API, and every step is logged.
- Stack: Postgres on Aiven, TypeScript (Fastify API, React and Cytoscape.js UI), Gemini function calling, Context.dev for live web data, a separate Valio mock service with OpenAPI.

## 2. Architecture and DB choice
- **Postgres (Aiven) as the single store.** Graph needs here are shallow (depth 2 to 3), so recursive CTEs are enough. One engine means one backup, one migration path and one place to enforce rules.
- **ArcadeDB: not used.** It is strong, but a second engine would split the team's attention over 48 hours. Stretch only: a read-only Cypher view of exported edges for a blast-radius visual.
- Components: API (auth, visibility service, orders); ingestion worker (discovery and monitoring jobs); agent runner (Gemini tools); Context.dev client; Valio mock; audit writer.
- Visibility is enforced in two layers: Postgres views per persona, and a server-side visibility function every endpoint must call. A test suite proves both.
- Assumption: Aiven hosts a plain Postgres with standard extensions only.

## 3. Data model and key queries
- `company(id, name, kind[registered|unregistered], industry_code, country, alt_opt_in)`
- `edge(id, from_id, to_id, trust_level[inferred|claimed|agreed|audited], confidence, source_urls jsonb, declared_by)`
- `edge_event(edge_id, actor_id, action[declare|confirm|audit], at)`: trust level is derived from events by a trigger; the app cannot set it directly.
- `product(id, name, category, unit)`, `listing(supplier_id, product_id, price_eur, published, alt_visible)`
- `risk_signal(id, entity_id, type, severity, confidence, source_url, observed_at)`
- `approval(id, proposal_id, approver, decided_at, decision)`, `audit_log(id, at, actor, actor_kind[human|agent|system], action, payload_hash)`

Visibility rules, as views:
```sql
CREATE VIEW v_buyer_map AS
SELECT e.* FROM edge e WHERE :viewer IN (e.from_id, e.to_id);

CREATE VIEW v_buyer_alerts AS
SELECT r.*, s.name AS supplier_name
FROM risk_signal r
JOIN edge e ON e.to_id = r.entity_id OR e.from_id = r.entity_id
WHERE :viewer = e.from_id AND e.trust_level IN ('agreed','audited');
```
Upstream names are hidden by default: `v_buyer_alerts` shows the upstream entity only when `disclosure(upstream_entity -> viewer)` exists; otherwise the alert reads "input of your supplier X".

Industry usage with a minimum cohort:
```sql
SELECT CASE WHEN n >= 10 THEN (n/5)*5 END AS peers_band
FROM (SELECT count(DISTINCT e.from_id) n
      FROM edge e JOIN company c ON c.id = e.from_id
      WHERE e.to_id = :supplier AND e.from_id <> :viewer
        AND c.industry_code = :viewer_industry) x;
```
Alternatives, opted in only: `SELECT * FROM listing l JOIN company c ON c.id=l.supplier_id WHERE l.product_id=:p AND l.published AND c.alt_opt_in ORDER BY price_eur;`

Blast radius: downstream customers of a failed supplier that the viewer can see, via `v_buyer_map`.

## 4. Agents (discovery, monitoring, procurement)
Shared rules: every agent gets typed tools only; outputs are proposal or signal rows, never direct writes to orders or trust levels; each run is logged with its tool calls.
- **Discovery.** Input: a company name or a product category. Tools: Context.dev company enrichment, news search, structured scrape. Output: `inferred` edge with confidence and source URLs. Validation: discard without a URL; hide below 0.6; check name against a local sanctions snapshot (assumption). Outbound queries carry public names only.
- **Monitoring.** Input: entities linked to the demo network. Tools: Context.dev monitors (webhook if reachable, otherwise a 60-second poll), news search. Output: `risk_signal` rows with source URLs. Signals carry no edge data.
- **Procurement.** Input: an alert, a current supplier, alternatives from `listing`, Valio availability and lead times. Tools: Valio `GET /products`, `GET /availability`, `POST /orders` (only with an approval record). Output: a proposal with price delta and reason. Human approval creates an `approval` row; the order call is refused without one. Partial availability is handled by splitting the order across two alternatives.

Prompt sketch for procurement: "Use only the supplied candidates. Rank by price, delivery lead time and certificates. Cite every figure by its field name. Do not name any company outside the candidate list."

## 5. Risk engine
Each risk type has one detector, one score and one source.
- Geopolitical: country risk table (static, labelled), scored 0 to 1 by severity.
- Sanctions and regulatory: fuzzy name match against a sanctions snapshot; certificate expiry (EUDR, organic, MSC) from Context.dev page checks.
- Concentration: count of the viewer's suppliers sharing an upstream edge; reported only over granted disclosures, with a "partial view" label otherwise.
- Financial health: news keywords (layoffs, insolvency) from Context.dev, decayed over 90 days.
- Live events: recall and strike news from Context.dev, with the source URL shown.
- Price premium: current price vs best published alternative; shown only when published.
- Overall alert score: severity x confidence x 0.6^depth. Alerts below 0.5 are not shown.

## 6. Screens and graph view
1. Login with four personas: hotel, Valio, supplier, auditor.
2. Supply map: own suppliers and customers; upstream shown as grey "hidden input" nodes unless disclosed.
3. Alerts: card with score, source URLs, and a "why you see this" panel naming the rule and any grant.
4. Alternatives: ranked list with price range, lead time, certificate badge.
5. Proposal and approval: current vs proposed, price delta, approve button, order receipt.
6. Audit log: searchable rows with actor kind and payload hash.

Graph encoding: arrows show direction; solid lines for agreed or audited, dashed for claimed, dotted for inferred; line width tracks confidence; node colour tracks max risk; an audited badge sits on audited edges.

## 7. Demo script (4 minutes)
- 0:00 Hotel logs in; supply map shows Valio and its visible inputs.
- 0:40 Live Context.dev run: a dairy producer's news is fetched; the alert appears with source URL.
- 1:20 Alternatives with price ranges and an industry usage band ("10-14 peers").
- 2:00 Procurement proposal; manager approves; order placed through Valio mock; receipt shown.
- 2:40 Supplier confirms an edge on a second browser (claimed to agreed); an auditor stamps one audited.
- 3:20 Open audit log and the visibility test run: "buyer cannot see supplier's private edges" passes.
- 3:50 Closing: what is live, what is seeded, and where the path to production goes.

## 9. Judging-criteria mapping
- Valio (30%): end-to-end order via mock API with approval. Buyer need (20%): alternatives, price ranges, risk alert. Controls (20%): approval record, audit log, visibility tests. Exceptions (15%): split order on partial availability. Open standards (15%): OpenAPI mock, JSON Schema proposals.
- Context.dev (15%): live discovery and monitoring in the core flow, source URLs, a visible change over time.
- Trust and privacy (10%): four trust levels stored and derived; visibility views and tests.
- Concreteness (10%): schemas, SQL and prompt in this document.
- Bounties: Gemini (agents), Aiven (hosted Postgres), CRACI (CI from day one), Codex (test generation and migrations, noted in commits). Cala: cut.

## 10. Risks and cuts
- Cut order: stretch ArcadeDB view, then webhooks (polling only), then sanctions snapshot (static list), then industry band (show "not enough peers" text), then audit search.
- Biggest technical risks: Context.dev latency or rate limits (mitigate with cached fixtures and a flagged live mode); visibility bugs (mitigate with the test suite); LLM output drifting (mitigate with the candidate-list constraint and schema validation).
- Demo risk: a single live call failing on stage. Mitigation: the backup video and a one-click fixture mode.

## 11. Biggest weakness of this proposal
It is deliberately conservative. Judges who want a graph-database showcase will see Postgres and recursive CTEs and mark down the technical wow factor. The visibility model is also split across views and application code, so one missed endpoint could leak data; the test suite reduces that risk but does not remove it.

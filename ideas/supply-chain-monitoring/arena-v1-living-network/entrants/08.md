# Entrant 08: Ravel, MCP-first supply network (lens: MCP everywhere)

## 0. Bold bet
Every capability (network graph, risk, alternatives, Valio ordering) is an MCP server with scoped tools, so the hotel's procurement agent, our own agents and any judge's Claude Desktop use the same interface. Interoperability is the demo, and the approval gate lives in the server, not in the UI, so no client can skip it.

## 1. Summary and name
- **Ravel**: a living supply-chain network where companies declare edges, agents fill gaps with sourced `inferred` edges, and buyers (human or agent) query it through MCP.
- Three MCP servers: `ravel-network` (graph, risk, alternatives), `valio-order` (Valio mock adapter with approval gate), `ravel-agents` (discovery, monitoring, procurement as tools that can be triggered and observed).
- Our web UI is just one MCP client. Judges can connect Claude Desktop or any MCP client to the same endpoints.
- Assumption: Valio mock exposes REST endpoints for product search, availability, quote and order. Our adapter maps them to tools. If the mock differs, we adapt the adapter only.

## 2. Architecture and DB choice
- **Primary store: Postgres on Aiven** (Aiven bounty; managed, fast to set up). Tables for companies, edges, risk_signals, visibility grants, approvals, audit_log. pgvector for alternative-supplier similarity (product embeddings).
- **ArcadeDB: optional stretch, read-only.** Run in Docker for Cypher blast-radius queries behind one `ravel-network` tool. Cut at Saturday night if not working. Reason: a hybrid store doubles sync bugs in 48h.
- Upstream traversal in Postgres uses `WITH RECURSIVE` with depth cap 4; supply chains here are shallow.
- Flow: Context.dev monitors and Exa results → webhook into `ravel-agents` → risk_signals row → `ravel-network` tool → any MCP client.
- Hosting: Aiven Runtime for the three MCP servers (HTTP transport, Streamable HTTP). Local dev uses stdio.
- Auth: each client gets a scoped API key per persona (`hotel-buyer`, `supplier-valio`, `auditor-sim`, `human-approver`). Scopes checked in every tool.

## 3. Data model and key queries
- `company(id, name, country, industry, registered bool, opted_in_visible bool)`
- `edge(id, from_id, to_id, trust ENUM('inferred','claimed','agreed','audited'), confidence NUMERIC, source_urls JSONB, declared_by, confirmed_by, audited_by, created_at)`
- `visibility_grant(edge_id, viewer_company_id)`: the only way a buyer sees a private edge; default empty.
- `risk_signal(id, company_id, type, severity, score, evidence_url, detected_at, source)`
- `price_publication(product_id, seller_id, price_min, price_max, currency, published bool)`
- `approval(id, action JSONB, requested_by_agent, approver, status, decided_at)`
- `audit_log(id, actor, tool, args_hash, result_summary, at)`: every MCP call is logged, including denied ones.

Visibility enforcement: `ravel-network` tools never return raw rows. They return projections filtered by the caller's company id. Example: `find_supplier_chain(company, depth)` returns the caller's own edges plus any edges where it is a `visibility_grant` viewer, and for upstream nodes only `{name, country, risk_summary}`.

Key queries (SQL sketch):
- Upstream: `WITH RECURSIVE up AS (SELECT from_id, to_id, 1 d FROM edge WHERE to_id=$hotel_supplier UNION ALL SELECT e.from_id, e.to_id, up.d+1 FROM edge e JOIN up ON e.to_id=up.from_id WHERE up.d<4) SELECT * FROM up;`
- Hidden concentration: `SELECT from_id, count(DISTINCT to_id) FROM edge WHERE to_id IN (direct suppliers) GROUP BY from_id HAVING count(DISTINCT to_id) >= 2;`
- Blast radius: same recursion, `to_id = failing_supplier`, returns downstream buyer count.
- Alternatives: `ORDER BY product_embedding <=> $q LIMIT 10 WHERE company.opted_in_visible AND price published`.
- Industry aggregate: `count(DISTINCT buyer) per supplier, industry`, shown only if count >= 5 (k-threshold).

## 4. Agents (discovery, monitoring, procurement)
Each agent is an MCP client calling `ravel-network` and external MCP servers. Gemini does function calling (bounty).
- **Discovery.** Inputs: Exa `search` (company, news filters) and Context.dev `extract`/company enrichment. Tools: `propose_edge`. Output: `inferred` edge with confidence and source_urls. Validation: at least 2 distinct source URLs, or confidence ≥ 0.6, else dropped. Unregistered companies become nodes with `registered=false` and an invite event.
- **Monitoring.** Context.dev monitors on supplier domains and news queries, with webhooks to `ravel-agents`. Each change is classified by Gemini into a risk type with severity and evidence_url, written via `record_risk_signal`. Re-check cadence: 15 minutes for demo nodes.
- **Procurement.** Input: risk_signal on an upstream node plus alternatives and published prices. Calls `valio-order.search_products`, `check_availability`, `get_quote`. Output: an order draft plus a reason. It calls `request_order`, which only creates an `approval` row and returns `pending_approval`. It cannot execute orders itself.
- Human approval: `human-approver` persona calls `approve_order` via the UI or a second MCP client. `valio-order.place_order` requires an approved approval_id, and it refuses otherwise.

## 5. Risk engine
Score 0-100 per company, combined with severity bands: 0-39 green, 40-69 amber, 70+ red. Each signal has an evidence_url.
- **Geopolitical:** static country-risk table (assumption: seeded from a public index) × supplier country.
- **Regulatory:** sanctions list (seeded offline, assumption) matched on name; certificate expiry from Valio synthetic certificates; EUDR flag for commodities such as cocoa and coffee.
- **Concentration:** single-source count per product and shared-upstream query (section 3).
- **Financial:** Context.dev company enrichment plus news keywords (layoffs, insolvency).
- **Live events:** Context.dev news search and monitors (recalls, strikes, outages).
- **Price premium:** Valio price vs lowest published alternative; only when both are public.

## 6. Screens and graph view
- **Buyer (hotel) login.** Persona picker and the MCP endpoint list with connection status.
- **Supply map.** Cytoscape.js graph. Direction arrows, edge style by trust (dashed `inferred`, dotted `claimed`, solid `agreed`, double `audited`), node colour by risk score, badge with confidence on inferred edges.
- **Risk alert panel.** Signal, severity, evidence URL (clickable), and "which MCP tool produced this".
- **Alternatives.** Opted-in suppliers only, with price ranges (published only) and industry aggregate usage.
- **Procurement.** Agent proposal, reason, Approve or Reject buttons.
- **Supplier inbox.** Confirm edge (`claimed` to `agreed`).
- **Auditor.** Stamp edge `audited`.
- **Audit trail.** Every MCP call in order, with args hash and result summary.

## 7. Demo script (4 minutes)
1. **0:00-0:30.** Hotel persona. Supply map shows Valio Aimo at centre with trust-coloured edges.
2. **0:30-1:15.** Claude Desktop (external, not our UI) connected to `ravel-network` asks "Any risks in my dairy chain?" Answer comes from MCP tools with source URLs. Judges see interoperability live.
3. **1:15-1:45.** Live run: Context.dev monitor fires on a dairy producer's news page, the webhook arrives, and the risk alert appears in the UI with the live URL.
4. **1:45-2:30.** Alternatives: opted-in supplier with price range, plus industry aggregate.
5. **2:30-3:15.** Procurement agent drafts a switch. Partial availability on one SKU triggers a substitution tool call. Manager approves.
6. **3:15-3:40.** `valio-order.place_order` returns an order id. Audit trail shows each call.
7. **3:40-4:00.** Supplier confirms edge (`agreed`), auditor stamps `audited`.

## 9. Judging-criteria mapping
- **Valio (30%):** end-to-end through MCP tools, with the order placed by the adapter. Guardrails: scoped keys, approval-gated `place_order`, audit log. Exceptions: partial availability returns substitutes through a tool call. Open standards: MCP for everything, which is the credible production path.
- **Context.dev (15%):** monitors plus webhooks are core to the risk flow; live URL shown on screen; uses their MCP server.
- **Gemini (bounty):** function calling in all three agents.
- **Aiven (bounty):** managed Postgres and Runtime hosting for the MCP servers.
- **CRACI (bounty):** GitHub Actions CI with SBOM on the three servers. Low effort.
- **Codex (bounty):** used to scaffold MCP tool handlers; log usage honestly.
- **Trust and privacy (10%):** visibility enforced in tool projections, k≥5 aggregates, risk-only for buyers.
- **Concreteness (10%):** schemas and SQL above; tool list is the spec.
- **Cala:** skipped; at most one optional `cala_company_lookup` tool if time allows.

## 10. Risks and cuts
- **Cut first:** ArcadeDB, then Cala, then the external Claude Desktop beat (fallback: our own MCP client panel showing the same calls).
- **Biggest technical risks:** scoped auth across three servers taking too long (mitigation: one shared JWT validator); Valio mock shape differing from assumptions; live monitor latency during demo (mitigation: pre-triggered run plus recorded backup).
- **Operational risk:** three servers plus Postgres is more to start than a monolith. Mitigation: one docker-compose for local, and a single Aiven Runtime app with three routes if needed.

## 11. Biggest weakness of this proposal
The MCP pitch risks reading as plumbing. Judges want to see a hotel manager, a map and an order. If the UI is thin, the interoperability story wins nothing on the "buyer need" criterion. We also assume Valio's mock exposes the order and availability endpoints we need, which is unverified.

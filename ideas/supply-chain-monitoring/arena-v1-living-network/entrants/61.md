# Entrant 61: Guarded Bargaining (lens: Multi-agent negotiation)

## 0. Bold bet
The procurement agent does not just recommend a switch; it runs short, logged negotiations with seller agents (quotes, partial quantities, substitutions, delivery windows) inside a rulebook the manager sets, and only a deal that passes deterministic guardrail code reaches the approval queue. The judges see agents actually talking to each other, with every message auditable and every rule enforced in code rather than in a prompt.

## 1. Summary and name
Name: **Haggle Fleet** (short: **Haggle**). A hotel manager sets guardrails once ("dairy only, max 8% premium, EU-certified, delivery within 3 days"). When a dairy risk appears, the buyer agent opens RFQs to Valio and two opted-in alternatives, negotiates over what each seller can offer, and brings a single best deal to the manager with the full transcript. Approval places the order through Valio's mock API.

## 2. Architecture and DB choice
**Postgres (Aiven, with pgvector) as the only store.** Negotiation is message passing with structured payloads, which fits JSONB rows and an append-only table. Recursive CTEs cover upstream risk and the supplier graph. ArcadeDB's graph and vector features do not change the negotiation logic, and its setup cost is not worth it in 48 hours.

Components:
- **Buyer agent (BPA):** Gemini with function calling. Owns the negotiation, never sets prices itself.
- **Seller agents (SA):** one per seller. Valio's SA reads its price and availability from the Valio mock; opted-in alternatives' SAs read their published `price_point` rows. Others are rule-based simulated sellers.
- **Guardrail engine:** plain Python, not an LLM. Every offer and every BPA action passes through it.
- **Message bus:** Postgres table plus a worker loop. No Kafka.
- **Discovery and monitoring:** Context.dev enrichment and news search (live), Context.dev monitors posting to `/hooks/ctx`.
- **Frontend:** React; a chat-like transcript panel, a graph view, the approval queue.
- **Hosting:** Aiven Runtime for API and workers; laptop fallback.

## 3. Data model and key queries
```sql
CREATE TABLE guardrail (buyer_id uuid PRIMARY KEY, categories text[], max_premium_pct numeric,
  min_certs text[], max_lead_days int, budget_eur numeric, allowed_sellers uuid[],
  min_trust text DEFAULT 'claimed', max_rounds int DEFAULT 3);
CREATE TABLE negotiation (id uuid PRIMARY KEY, buyer_id uuid, product_id text, qty int,
  trigger_risk_id bigint, status text CHECK (status IN ('open','deal_pending','needs_human','closed_no_deal','approved','ordered')));
CREATE TABLE msg (id bigserial PRIMARY KEY, negotiation_id uuid, seq int, from_agent text, to_agent text,
  kind text CHECK (kind IN ('rfq','quote','counter','accept','decline','substitute','escalate')),
  payload jsonb, guard jsonb,  -- {pass: bool, failed: [...]}
  prev_hash bytea, hash bytea, created_at timestamptz DEFAULT now(), UNIQUE (negotiation_id, seq));
CREATE TABLE edge (id uuid PRIMARY KEY, buyer_id uuid, seller_id uuid,
  trust text CHECK (trust IN ('inferred','claimed','agreed','audited')), confidence real, sources jsonb);
CREATE TABLE price_point (company_id uuid, product_id text, unit_price numeric, lead_days int,
  certs text[], published boolean, PRIMARY KEY (company_id, product_id));
```
- `msg` is append-only (trigger blocks UPDATE and DELETE). `hash = sha256(prev_hash || payload)`.
- Privacy: a seller's `price_point` is visible to buyers only where `published = true`. The buyer's own `edge` rows are private; upstream risks are returned by a `SECURITY DEFINER` function that exposes severity and headline only.
- Upstream risk query (depth ≤ 4):
```sql
WITH RECURSIVE up(anc, depth, path) AS (
  SELECT seller_id, 1, ARRAY[buyer_id, seller_id] FROM edge WHERE buyer_id = $me
  UNION ALL
  SELECT e.seller_id, up.depth+1, up.path || e.seller_id FROM up
  JOIN edge e ON e.buyer_id = up.anc WHERE up.depth < 4 AND NOT e.seller_id = ANY(up.path))
SELECT * FROM up;
```
- Hidden concentration: group the same recursion by ancestor, keep ancestors shared by ≥ 2 direct suppliers.
- Alternatives: `price_point` where `published` and `certs @> $min_certs` ordered by pgvector similarity to the risky supplier's description.

## 4. Agents (discovery, monitoring, procurement)
**Discovery.** Context.dev company and news calls for a domain or query. Gemini extracts `{buyer, seller, quote, source_url}`. Validation: the URL is in the fetched set, the quote appears verbatim, both names match. Confidence = min(model, 0.5 + 0.15 × sources), cap 0.9. Writes `inferred` edges. Each edge in the chat shows its URL.

**Monitoring.** Context.dev monitor fires on the dairy producer's news page. Gemini classifies it into a risk kind and severity. If severity ≥ 3 on a current supplier, the monitor creates a `negotiation` with `trigger_risk_id`.

**Procurement (negotiation protocol).**
1. BPA sends `rfq` to Valio plus up to two opted-in sellers in the same category (max 3 sellers).
2. Sellers reply `quote`. Valio quotes are fixed prices from the mock API; alternatives quote within their published range.
3. BPA may `counter` on lead time, certification, or quantity split only. It may not counter on a Valio fixed price; it can request a `substitute` SKU instead.
4. Rounds capped at `max_rounds`. Each message passes the guardrail engine before it is sent; a failure sends `escalate` to the human.
5. When one seller `accept`s a combined offer, the negotiation becomes `deal_pending`. The manager's approval tray shows the transcript, guardrail results and the total. Approval calls `POST /orders` on the Valio mock with `Idempotency-Key = negotiation.id`.

BPA prompt (abridged): "You negotiate for the buyer within the guardrail JSON. You may only propose terms the guardrail engine can check. Never state a price that is not in a tool result. If a seller refuses twice, close that seller and move on."

Assumption: Valio mock supports fixed-price orders and substitution SKUs; the negotiation is over terms other than unit price for Valio.

## 5. Risk engine
- **Regulatory:** sanctions name match (cached EU list, assumption), certificate expiry (Valio data). Missing certificate = severity 3 and a `min_certs` violation for any seller that lacks it.
- **Concentration:** hidden shared upstream query; single-source flag from edge counts.
- **Geopolitical, financial, live events:** Context.dev news plus Gemini classification; severity from a fixed table, not the model.
- **Price premium:** Valio fixed price vs cheapest published alternative; premium > guardrail `max_premium_pct` triggers a negotiation.
- Score = severity × confidence × 0.7^(hops − 1). Only scores ≥ 2 reach the buyer.

## 6. Screens and graph view
1. **Guardrails page:** the manager's rulebook as a form (categories, premium cap, certs, lead time, budget, allowed sellers).
2. **Negotiation room:** message list with sender, kind, guard pass/fail chips and payload; the trust chip on each seller; source URLs for any risk cited.
3. **Graph panel:** supplier map with trust styles and risk badges; the negotiation's sellers highlighted.
4. **Approval queue:** deal total against budget, guardrail summary, Approve or Reject.
5. **Audit page:** every message with hash, plus "verify chain".

## 7. Demo script (4 min)
- 0:00–0:25 Manager shows guardrails (premium 8%, EU cert, 3-day delivery, €5k budget).
- 0:25–0:55 Live: "Scan now" pulls a news item about the dairy co-op via Context.dev; new risk appears with URL.
- 0:55–1:55 Negotiation room: Valio RFQ, two alternative quotes; BPA counters on lead time; one message fails the guardrail (certificate missing) and is blocked, visibly.
- 1:55–2:35 Partial stock from Valio: BPA proposes a substitute SKU and a split with an alternative; SA accepts.
- 2:35–3:20 Supplier confirms the edge (`claimed` → `agreed`); auditor stamps `audited`.
- 3:20–3:50 Approval; Valio mock order with idempotency key.
- 3:50–4:00 Audit page: hash chain verified.

## 9. Judging-criteria mapping
- **Valio (30%):** full request → quote → negotiated deal → approval → fixed-price order, on the mock API.
- **Buyer need (20%):** manager sets rules once; the agent does the comparison and the bargaining.
- **Controls (20%):** guardrails enforced in code, every message hashed, human approval gate.
- **Exceptions (15%):** partial availability, substitution, rejected offers, escalation.
- **Context.dev (15%):** monitor and discovery drive the negotiation, sourced URLs.
- **Trust/privacy (10%):** published prices only; upstream exposed as severity and headline.
- **Bounties:** Gemini (BPA and seller LLMs), Aiven (store), Codex (tests), CRACI (CI).

## 10. Risks and cuts
- Cut first: the LLM-driven seller agents (fall back to scripted seller replies with the same message format); Exa; Oxylabs; Cala.
- Risk: LLM negotiation loops or stalls. Mitigation: hard round cap and timeout; deterministic fallback path.
- Risk: Valio mock lacks substitution or partial stock. Mitigation: simulate both in our own mock layer and label it.
- Risk: live Context.dev latency. Mitigation: pre-cached fixture of the same JSON shape.

## 11. Biggest weakness of this proposal
Judges may see negotiation with fixed-price Valio as theatre, since the one thing that matters to buyers (price) is not negotiable there. The multi-agent message flow is also the most complex part to build in 48 hours, and a bug in it can take down the whole demo.

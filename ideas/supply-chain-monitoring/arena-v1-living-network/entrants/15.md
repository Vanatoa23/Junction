# Entrant 15: Leash, a policy-gated supply network (lens: guardrails and policy engine)

## 0. Bold bet
Every agent action becomes a typed Intent that must pass a declarative policy gate (spend caps, approval tiers, allow-lists, agent scopes, kill switch) before anything executes, and the demo shows a live out-of-policy proposal being blocked and a kill switch freezing an agent mid-run. This scores the 20% autonomy-and-controls criterion and the 20% audit weight, which most entrants will treat as a slide.

## 1. Summary and name
- **Leash**: a living supply-chain network where agents can discover, monitor and propose, but cannot spend, publish or see private maps without a policy decision and, for orders, a human.
- A buyer (hotel chain, Valio Aimo as hub) sees its supply map, risk alerts about upstream dairy, opted-in alternatives with published price ranges, and a procurement proposal. A manager approves; the order goes to Valio's mock API; every step is in a hash-chained audit log.
- Assumption: Valio mock exposes product/availability lookup and an order POST with an idempotency key. Label as assumed until API docs are checked.

## 2. Architecture and DB choice
- **Primary store: Postgres on Aiven** (Aiven bounty). Holds companies, edges, policies, grants, approvals and the audit log. Graph traversal uses recursive CTEs; depth is 3 to 4 tiers, so this is fast enough.
- **Valkey on Aiven** for kill-switch flags and atomic spend counters (INCRBY, checked against Postgres truth every write).
- **ArcadeDB: stretch only.** If Saturday night is green, mirror edges and run Cypher blast-radius for one slide. Cut first if behind.
- Components: Next.js UI, one Node API, **Policy Gateway** (single choke point: every tool call from every agent and every human order goes through it), Gemini agents with function calling, Context.dev (scrape, news, monitor webhooks), Valio mock client.
- Data flow: agent tool call → Gateway (kill switch → scope → allow-list → limits → tier) → ALLOW / REQUIRE_APPROVAL / DENY → side effect → audit event.

## 3. Data model and key queries
- Nodes: `Company(id, name, country, registered, sanctions_hit, industry)`, `Product(id, company_id, price_range, published)`.
- Edges: `Edge(from, to, kind in {buys_from}, trust in {inferred, claimed, agreed, audited}, confidence, sources jsonb, confirmed_from, confirmed_to, audited_by)`.
- Policy: `Policy(id, scope, rules jsonb, version)`; `Grant(principal, tools[], budget_eur, expires_at)`; `Approval(intent_id, payload_hash, approver, decision, expires_at)`; `KillSwitch(scope, active)`.
- Audit: `AuditEvent(seq, prev_hash, hash, actor, tool, decision, rule_ids[], policy_version, inputs_snapshot, ts)`. Append-only, hash-chained, verified in UI.
- Visibility is enforced in one function, `visible_edges(viewer)`, plus SQL views. A buyer sees: its own map; risk rows for suppliers and upstream; aggregates only where group size is at least 5; alternatives where `opted_in = true`; prices where `published = true`. Other companies' edges never leave the DB layer.
- Upstream traversal: `WITH RECURSIVE up AS (SELECT ... WHERE to_id = :supplier UNION ALL ...) ` capped at depth 4.
- Hidden concentration: `SELECT upstream_id, count(DISTINCT direct_supplier) FROM up GROUP BY upstream_id HAVING count(...) >= 2`.
- Blast radius: same CTE from a failed node, counting downstream buyers.
- Alternatives: products with `category = X AND supplier.opted_in AND published`, ordered by price, with a Gemini-free rule for ranking.

## 4. Agents (discovery, monitoring, procurement)
Each agent runs with a Grant: allowed tools, a euro budget, and a 10-minute expiry. Gateway enforces it; the prompt is not trusted.
- **Discovery.** Inputs: seed names, Context.dev search and company enrichment, news. Tools: `search_web`, `enrich_company`. Output: `Edge(trust=inferred)` with confidence and at least 2 source URLs. Validation: the company name must appear in the fetched page text, otherwise the edge is dropped. Writes only inferred edges; never touches agreed or audited ones.
- **Monitoring.** Context.dev monitors with webhooks on each registered supplier's news and site. Writes `RiskSignal` rows with source URL and timestamp. Cannot change edges. Rate-limited to 50 calls per run by Grant.
- **Procurement.** Tools: `read_catalogue`, `read_availability`, `propose_order` (always writes an Intent). `place_order` is not in its Grant at all; only the approval handler can call Valio, with a single-use token bound to the payload hash. Exceptions (partial availability) create a new Intent and re-enter the gate.

## 5. Risk engine
Rules are deterministic and cite a source. Gemini only writes the explanation text.
- Sanctions and regulatory: name match against a seeded sanctions list plus expired-certificate check. Hit gives `critical`.
- Geopolitical: country table with a seeded score, weighted by spend share.
- Concentration: distinct direct suppliers sharing one upstream node (CTE above).
- Financial and live events: Context.dev news keyword rules (insolvency, strike, recall), each with a URL.
- Price premium: only when alternatives are published; premium = price / cheapest published minus 1.
Each risk stores `rule_id`, `score`, `sources[]`, `as_of`.

## 6. Screens and graph view
- **Buyer map:** Cytoscape graph, arrows show direction, dashed line = inferred, solid = agreed, thick = audited, red halo = open risk. Click an edge for confidence and sources.
- **Risk and alternatives panel:** risk card with rule ID and source link; alternatives with price range and an opt-in badge.
- **Procurement inbox:** proposal, price delta, and the policy explanation ("within €2,000 cap; tier 2; needs manager").
- **Policy and kill switch:** current limits, grants with spend bars, global and per-agent kill toggles.
- **Audit log:** filterable table, hash-chain status, "why" expander showing rule IDs and inputs.

## 7. Demo script (4 min)
- 0:00–0:25 Hotel login. Supply map; private view visibly hides other buyers' edges.
- 0:25–1:05 Live: monitor webhook fires on an upstream dairy plant (or a Context.dev discovery run pulls URLs live). Risk card appears with source link.
- 1:05–1:40 Alternatives with price ranges, opted-in only. A non-opted-in supplier is absent.
- 1:40–2:20 Procurement agent proposes a switch. Then the agent attempts a non-allow-listed supplier: DENY, shown in the audit log with the rule ID.
- 2:20–2:55 Manager approves on the inbox. Order to Valio mock. Partial availability returns; substitution Intent goes back through the gate and needs a second approval.
- 2:55–3:25 Press the agent kill switch mid-run. The next tool call is blocked. Supplier confirms (claimed to agreed); auditor stamps audited.
- 3:25–4:00 Audit replay with hash verification. Close on "no order without a human, no action outside scope."
- Fallback: pre-recorded video of the same beats.

## 9. Judging-criteria mapping
- Valio end-to-end (30%): full request → approve → order flow with mock API.
- Buyer need (20%): hotel gets risk, alternatives and a switch proposal without sharing a private map.
- Autonomy and controls (20%): gate, scopes, budgets, kill switch and DENY demo are on screen.
- Exceptions (15%): partial availability creates a substitution Intent that re-enters the gate.
- Open standards and path to production (15%): hash-chained audit, idempotency keys, OAuth-ready scopes; state it as a path, not built.
- Context.dev (15%): monitor webhook and discovery are in the core flow with source URLs and as-of times.
- Trust and privacy (10%): visibility function, aggregates with a minimum group size.
- Side bounties: Gemini (agents), Aiven (Postgres and Valkey), CRACI (CI run with SBOM, near-zero effort), Codex if used in dev.

## 10. Risks and cuts
- Cut first: ArcadeDB, Cala, Modal, Oxylabs, Websets.
- Biggest technical risk: Context.dev latency during the demo. Mitigation: cached snapshot with as-of time, and a live run started before the pitch.
- Gate bugs letting an order through unapproved. Mitigation: one code path to Valio, tested, and the approval token is required by the type.
- Gemini tool-call drift. Mitigation: the Gateway enforces scope, so a bad prompt only gets a DENY.

## 11. Biggest weakness of this proposal (be honest)
The policy engine is homegrown JSON rules, not a formal policy language such as Cedar or OPA, so a technical judge may see it as a checklist rather than a real control plane. The graph is also Postgres, which under-uses the graph database the brief highlights, and the risk engine is thinner than the controls story.

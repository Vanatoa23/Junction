# Entrant 24: Larder Mesh, the menu-aware buyer (lens: Restaurant group / grocery persona)

## 0. Bold bet
Swap the hotel for a fictional nine-site restaurant group, Nordic Table, with a central kitchen. Restaurants make Valio's trust story concrete: a dairy recall stops a named dish on a named menu today, so the risk alert, the spec-matched substitute and the two-person approval all have stakes a judge can see in one screen.

## 1. Summary and name
- **Larder Mesh.** Nordic Table's central kitchen buys through Valio. Every menu item is a recipe with ingredient specs (fat %, certification, pack size, allergen flags). When a supplier upstream fails, the risk alert names the affected dishes and sites. The procurement agent proposes a substitute that passes every recipe spec, prices it against published alternatives, and waits for the group purchasing manager.
- Why a restaurant group beats the other personas: perishable dairy has a short window, menu cost is visible, and a grocery store would bring a retail price and shelf-compliance story that Valio, a food-service wholesaler, does not sell. A hotel is close, but a restaurant group has more daily orders, so the agent has more reasons to act.
- **Assumptions:** A1 Valio mock exposes catalogue, price, availability, delivery slots and order placement. A2 Valio mock has sustainability certificate fields per SKU. If either is missing, we extend the seed data and say so on the slide.

## 2. Architecture and DB choice
- **Postgres on Aiven** (Aiven bounty). One store for the company graph, recipes, mandates, proposals and audit. ArcadeDB is not used: the demo graph is about 2,000 nodes, and recursive CTEs cover upstream and downstream traversal without a second engine.
- Components: React web app with Cytoscape.js; a Node/TypeScript API; an agent runtime using Gemini function calling with typed tools; a Valio adapter; a Context.dev client (SDK, monitors, webhooks); a background worker for monitor polling.
- Flow: Context.dev monitor or discovery → `signal` → risk engine scores affected SKUs → recipe impact computed → procurement agent → `proposal` (pending) → manager approval → order service → Valio order → `audit_event`.
- **Hard rule:** the agent has no order tool. The order service accepts only an approval whose hash matches the proposal payload, using the proposal ID as the Valio idempotency key.

## 3. Data model and key queries
- `company(id, name, country, domain, status: unregistered|registered, opt_in_alt)`
- `supply_edge(id, from_company, to_company, sku_category, trust, confidence, sources jsonb, confirmed_by_from, confirmed_by_to, audited_by, updated_at)` with `trust` in `inferred|claimed|agreed|audited`.
- `menu_item(id, site_id, name, active)` and `recipe_line(menu_item_id, ingredient_key, spec jsonb)` where spec holds `fat_pct_min`, `certs[]`, `pack_g`, `allergens[]`.
- `sku_offer(sku, supplier_company, category, spec jsonb, price_min, price_max, currency, published bool, lead_days)`
- `signal(id, company_id, risk_type, severity 0-100, confidence, sources jsonb, observed_at, expires_at)`
- `mandate(id, group_id, max_order_eur, two_person_over_eur, allowed_origins[], max_supplier_risk, max_premium_pct, valid_until)`
- `proposal(id, group_id, trigger_signal_id, lines jsonb, affected_menu_items jsonb, checks jsonb, payload_hash, status, quote_expires_at)`
- `approval(id, proposal_id, approver, role, payload_hash, decided_at)`
- `audit_event(id, entity, entity_id, actor, action, payload, prev_hash, hash, at)`: append-only, hash-chained. It records trust transitions, every agent tool call and every approval.
- **Visibility** lives in the API as `visible(viewer, row)` plus SQL views. A site manager sees only its group. Other groups see alternatives only where `opt_in_alt` is true, industry usage only as counts with k≥5, and prices only where `published`.
- **Queries**
  - Upstream chain (depth ≤4): `WITH RECURSIVE up AS (SELECT from_company AS id, 1 AS d FROM supply_edge WHERE to_company=$1 UNION ALL SELECT e.from_company, up.d+1 FROM supply_edge e JOIN up ON e.to_company=up.id WHERE up.d<4) SELECT id, min(d) FROM up GROUP BY id;`
  - Menu blast radius: join the upstream set to `sku_offer` by supplier, then to `recipe_line` by `ingredient_key`, then to `menu_item` and `site`. This returns "Béarnaise at Site 3 and 6, feta salad at Site 1."
  - Hidden concentration: group the upstream traversal by ancestor and keep ancestors reached through at least two direct suppliers.
  - Spec-matched alternatives: `sku_offer` where `category` matches, `spec` covers every `recipe_line.spec` for the affected dish, `published` is true, and the supplier is opted in. Order by `price_min`.

## 4. Agents
- **Discovery.** Inputs: Valio supplier list and supplier domains. Tools: `ctx.company_enrich(domain)`, `ctx.news_search(q)`, `ctx.extract(url, schema)`. Output: candidate companies and `inferred` edges with confidence and source URLs. Rule: no source URL, no edge.
- **Monitoring.** Context.dev monitors watch supplier domains, a Finnish food-safety recall page (**A3**: scrapable, and a monitor can target it), and news queries. Webhooks reach the API through a tunnel (**A4**). Fallback: worker polls every 60 seconds. Gemini converts each change into a `signal` with structured output. A signal needs one source URL. Confidence below 0.5 is shown but does not trigger procurement.
- **Procurement ("Reorder Sous").** Triggered by severity ≥70 or a premium alert. Tools: `valio.search`, `valio.availability(sku, date)`, `valio.quote(lines)` (fixed price, 30-minute TTL), `graph.alternatives`, `recipe.check(menu_item, sku)`, `mandate.check`, `propose`. At most 8 tool calls per run. Output: a proposal and a checks table.
  - Exceptions: a substitute fails recipe spec → try next offer, else flag the dish for a menu change. Partial availability → split the order between central kitchen and a backup supplier. Price moved → re-quote; re-approval if the premium rises. Delivery slot missed → next slot before the cut-off.
- **Human approval:** orders above €2,000 need two approvers (the purchasing manager and the central-kitchen chef). Each approval records the payload hash, so the placed order equals the approved one.

## 5. Risk engine
Score = base × confidence × recency decay (half-life 30 days). Upstream risk passes down with 0.8 per hop.
- **Geopolitical:** curated country table with a cited index, plus `ctx.news_search` for conflict and trade-restriction terms.
- **Regulatory:** sanctions name match against an offline EU consolidated list (fuzzy ≥0.9; **A5**: CSV available). EUDR: cocoa, soy, palm, beef and wood ingredients with no declared statement. CSDDD: `ctx.extract` on the supplier policy page. Expired certificates from the Valio certificate fields.
- **Concentration:** single-source count per `ingredient_key`, plus the hidden shared-upstream query.
- **Financial:** `ctx.news_search` for layoffs, insolvency and funding keywords.
- **Live events:** recall, strike and outage monitors on webhook.
- **Price premium:** (price − cheapest published spec-matched offer) / cheapest, only where published.

## 6. Screens and graph view
1. **Kitchen board:** today's orders, active signals, pending approvals.
2. **Menu impact:** affected dishes by site, with spec-matched status.
3. **Supply map:** graph view (below).
4. **Signal detail:** confidence, clickable source URLs with timestamps, upstream path, blast radius.
5. **Proposal review:** old vs new lines, recipe-check ticks per dish, price range, checks table, approve or reject, two-approver status.
6. **Audit timeline:** agent calls, sources, approvals and a "hash chain verified" badge.
7. **Supplier portal:** confirm edge (claimed → agreed), publish prices, opt into alternatives.
8. **Auditor page:** stamp an edge as audited (simulated account).
- **Graph view:** Nordic Table's central kitchen on the right; supply flows left to right. Node colour = max risk (green, amber, red). Dashed border = unregistered. Edge style = trust: dotted `inferred`, thin solid `claimed`, thick solid `agreed`, double `audited`. Edge label shows confidence. Clicking a red node highlights affected dishes.

- **0:20–0:45** Supply map: Nordic Table central kitchen, upstream dairy co-op via a `claimed` edge.
- **0:45–1:15 LIVE.** "Run monitors": Context.dev pulls fresh news and a recall notice for the co-op. Three source URLs with timestamps appear. If live results are thin, a seeded item is labelled as seeded.
- **1:15–1:35** Impact: "Béarnaise at Sites 3 and 6, cheese board at Site 1." The procurement agent starts; its tool calls stream.
- **1:35–2:15** Proposal: spec-matched substitute from an opted-in supplier, published price range shown. Exception: one SKU partially available, so the order splits to a backup supplier. Recipe ticks confirm fat % and certification. Premium 4%, within mandate.
- **2:15–2:50** Two-person approval: purchasing manager approves, then the chef. Order placed via the Valio mock. Hash chain verified.
- **2:50–3:20** Supplier confirms an edge on their phone (claimed → agreed). Auditor stamps audited.
- **3:20–3:45** Privacy panel: "used by 7 of 40 restaurant groups"; no names. Alternatives show only opted-in suppliers.
- **3:45–4:00** Close on Context.dev in the core loop, Gemini, Aiven.

## 9. Judging-criteria mapping
- **Valio end-to-end (30%):** one scripted path from signal to placed order, with a real-looking menu context.
- **Buyer need (20%):** a restaurant group's problem is a named dish on a named site. Spec-matched substitutes answer it directly.
- **Autonomy and controls (20%):** no order tool for the agent, two-person approval over €2,000, payload-hash binding, idempotency key, hash-chained audit.
- **Exceptions (15%):** spec failure, partial availability, split orders, price moved, missed slot.
- **Open standards (15%):** tools exposed as an MCP server, JSON Schema for mandates and recipe specs. Production path named, not built.
- **Context.dev (15%):** monitors, enrichment, extract and news in the core loop, with visible URLs and latency.
- **Gemini:** all three agents. **Aiven:** hosted Postgres. **CRACI:** GitHub Actions with SBOM. **Codex:** claimed only if used and logged. **Cala:** skipped (no investor angle).

## 10. Risks and cuts
- A1 or A2 wrong: local mock and extended seed by Friday 22:00.
- Webhooks unreachable: polling fallback. Cached results shown with real timestamps.
- Gemini latency: pre-warm and cache the last run.
- Recall notice not scrapable: use a curated notice page and say so.

## 11. Biggest weakness of this proposal
Recipe modelling is the hidden cost. Spec data for dishes is invented, so a judge could ask whether the recipe checks are real or decorative. The restaurant framing also narrows the buyer story to food service, so the grocery-shelf angle is lost.

**Assumptions:** A1 Valio endpoints as described. A2 sustainability fields per SKU. A3 recall page scrapable by Context.dev. A4 webhooks reachable via tunnel. A5 offline EU sanctions CSV.

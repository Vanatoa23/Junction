# Entrant 27: Keel, Risk Radar First (lens: Contrarian)
## 0. Bold bet
Most teams will build a graph browser and bolt risk on as a badge; we invert it. The product is a risk radar whose signals must be corroborated by two independent sources before a buyer sees them, and procurement is one deterministic lookup plus one human approval. Judges on real-timeness and robustness will see the deepest part of the stack, and the Valio flow is short enough that it cannot fail on stage.

## 1. Summary and name
**Keel**: a supply-chain network where every edge carries a trust level and every company carries a live risk state. Buyers see a radar of their upstream chain, alternatives only when opted in, and prices only when published.
Assumptions: the Valio mock API exposes product search, availability and order endpoints as the brief describes. We fetch its exact shapes on Friday morning and treat any mismatch as a Friday blocker.

## 2. Architecture and DB choice
- **Postgres on Aiven only. ArcadeDB rejected for the 48h build.** Reason: a second query language and a Docker setup nobody on the team has used. Graph depth is at most 4 hops over roughly 250 companies, which recursive CTEs handle. ArcadeDB is a post-hackathon option.
- Frontend: React with Cytoscape.js. Backend: FastAPI. Scheduler: in-process APScheduler.
- Inbound: Context.dev monitor webhooks hit `/hooks/ctx` and write raw `source_item` rows.
- Pipeline: `source_item` → extraction (Gemini, no tools) → `claim` → corroboration (code) → `signal` → scoring (code) → `risk_state` → `alert` → `proposal`.
- Gemini is the extractor and classifier. It never scores, never writes trust, never places orders.
- Hosting: Aiven Runtime for the app and Postgres (bounty).

## 3. Data model and key queries
- `company(id, name, country, industry, status enum[seeded,scraped,registered], vat_id, lei, visible_opt_in bool)`
- `edge(id, supplier_id, buyer_id, category, trust enum[inferred,claimed,agreed,audited], confidence, sources jsonb, price_published jsonb null)`
- `trust_transition(edge_id, from_trust, to_trust, actor, actor_type, reason, ts)`. The only write path to `trust`. Agents can write `inferred` only.
- `source_item(id, url unique, domain, retrieved_at, provider enum[ctx_news,ctx_monitor,exa], content_hash, text)`
- `claim(id, source_item_id, company_id, type enum[geo,reg,conc,fin,event,price], claim_text, quote, quote_verified bool, event_date, severity_hint)`
- `signal(id, company_id, type, severity, corroboration int, status enum[unconfirmed,corroborated,expired], claim_ids[], valid_until)`
- `risk_state(company_id pk, level enum[green,amber,red], score, driver_signal_ids[], updated_at)`
- `alert`, `proposal(id, kind, payload jsonb, status, decided_by)`, `audit(id, actor, actor_type, action, args, result, ts)`. `audit` is append-only (no UPDATE/DELETE grants).

Visibility lives in SQL views:
- `v_buyer_radar`: `risk_state` rows for the buyer's upstream closure, and only `corroborated` signals. Unconfirmed signals stay internal.
- `v_industry_usage`: supplier usage per industry, suppressed when count < 5.
- `v_alternatives`: `visible_opt_in` suppliers with `price_published` set.

Queries:
- Upstream closure (depth 4, cycle-safe):
```sql
WITH RECURSIVE up(id, via, depth, path) AS (
  SELECT supplier_id, supplier_id, 1, ARRAY[supplier_id] FROM edge WHERE buyer_id=$1
  UNION ALL
  SELECT e.supplier_id, up.via, up.depth+1, up.path||e.supplier_id
  FROM edge e JOIN up ON e.buyer_id=up.id
  WHERE up.depth<4 AND NOT e.supplier_id=ANY(up.path))
SELECT id, MIN(depth) AS depth FROM up GROUP BY id;
```
- Hidden concentration: the same query keeps `via`. `SELECT id, COUNT(DISTINCT via) FROM up GROUP BY id HAVING COUNT(DISTINCT via) >= 2`.
- Blast radius: the same recursion run downstream (`supplier_id = $1` and walk `buyer_id`), summing buyer volume from order history.
- Alternatives: `SELECT * FROM v_alternatives WHERE category=$1 AND id<>ALL($2) ORDER BY price_published->>'min'`.

## 4. Agents (discovery, monitoring, procurement)
Monitoring is the deep part. Discovery is a feeder. Procurement is thin on purpose.

**Monitoring (Gemini extraction, then code).**
- Input: a `source_item` from a Context.dev monitor webhook, or a scheduled `news_search` per company.
- Call 1: Gemini, no tools, `responseMimeType: application/json`, `responseSchema`: `{claims:[{company_name, type enum[geo,reg,conc,fin,event,price], claim_text, quote, event_date, severity_hint 0-1}]}`.
- Code validates each `quote` as a verbatim substring of `source_item.text` (normalised whitespace). Failures are stored with `quote_verified=false` and never promoted.
- Corroboration (code): claims are grouped by (company, type, event_date within 3 days). `corroboration` = distinct registrable domains. One domain = `unconfirmed`. Two or more = `corroborated`.

**Discovery (Gemini function calling, scheduled twice a day plus a demo "Scan now" button).**
- Allowlist: `news_search(query, since_iso, limit<=10)`, `company_enrich(domain)`, `propose_edge(...)`. Runs with `toolConfig.functionCallingConfig.mode="ANY"`, `allowedFunctionNames` set to the three names above.
```json
{"name":"propose_edge","description":"Propose a supplier link as INFERRED. Creates no edge until corroborated.",
 "parameters":{"type":"OBJECT","properties":{
   "supplier_name":{"type":"STRING"},"buyer_name":{"type":"STRING"},
   "category":{"type":"STRING","enum":["dairy","meat","produce","dry_goods","beverages","packaging"]},
   "confidence":{"type":"NUMBER"},
   "source_urls":{"type":"ARRAY","items":{"type":"STRING"},"minItems":2}},
 "required":["supplier_name","buyer_name","category","confidence","source_urls"]}}
```
- Validation (code): `source_urls` must be the exact URLs returned by tools, from at least 2 distinct domains for confidence above 0.7. Otherwise the confidence is capped at 0.6. Below 0.4 is dropped. Dedupe by normalised name, then VAT ID.
- Final structured output is a second call with `responseSchema` over the tool transcript (assumption: tool calling and JSON schema are not mixed in one request; verify on day 1).

**Procurement (thin).**
- One deterministic step: `valio_search_products(category)` plus `valio_check_availability(sku, qty, date)`, then `v_alternatives`.
- One Gemini call, schema-constrained: `{alt_sku, price_delta_pct, delivery_days, rationale<=40 words, evidence_refs[]}`. No tool loop.
- No order tool is exposed to any model. Approval calls `valio_place_order` with the stored payload and writes `audit`.

## 5. Risk engine
Gemini classifies. Code scores. Every type has a source and a rule.
- **Geopolitical:** seeded country table (labelled as seeded, public index snapshot). Score = table value x 0.5 plus the severity of corroborated conflict or trade-restriction claims.
- **Regulatory:** sanctions name match on a static EU consolidated-list snapshot (assumption), normalised token match >= 0.9, score 1.0. Certificate expiry from Valio sustainability data. EUDR flag for cocoa, soy, palm and beef without a deforestation-free certificate. CSDDD flag where due-diligence records are missing.
- **Concentration:** single-source in a category = 0.4. Hidden shared upstream reached through >= 2 direct suppliers = 0.7, scaled by volume share.
- **Financial:** insolvency claim 0.9, layoffs 0.4, funding stress 0.3.
- **Live events:** recalls, strikes and outages from monitors, scored by `severity_hint` x corroboration.
- **Price premium:** only with published prices. Premium above 10% = 0.3, above 25% = 0.6.
- Decay: each signal's weight halves every 7 days (event types) or 90 days (regulatory).
- Aggregation: company score = 1 - product(1 - s_i) over active corroborated signals. Red >= 0.7, amber >= 0.4.
- Propagation: a red upstream supplier raises its downstream buyers' suppliers to amber with 0.5 attenuation per hop.
- Each `risk_state` stores `driver_signal_ids`, so every alert can explain itself with links.

## 6. Screens and graph view
1. Radar home: red and amber list for the buyer, Valio at centre.
2. Signal detail: claim, verified quote, source URLs with retrieval times, corroboration count, decay.
3. Supply map: arrows point supplier to buyer. Node ring = risk level. Edge style = trust (dashed inferred with confidence label, grey claimed, solid agreed, gold double audited).
4. Alternatives: opt-in suppliers, published price ranges, industry usage bars (k >= 5 only).
5. Proposal: diff, rationale, evidence, Approve or Reject.
6. Audit timeline: every agent call, arguments, model and output hash.
7. Supplier view (confirm claimed to agreed) and auditor view (stamp audited).

## 7. Demo script (4 min)
- 0:00-0:25 Radar: red ring on an upstream dairy co-op. Click through to the verified quote and two source URLs.
- 0:25-1:05 Live: "Scan now". Context.dev news search runs; URLs stream in. A new dashed edge appears at confidence 0.74 with 2 domains.
- 1:05-1:40 Real-timeness: a single-source claim sits as "unconfirmed". The second source lands through a monitor webhook, and it turns "corroborated" and amber on screen.
- 1:40-2:15 Hidden concentration: three Valio dairy suppliers share one upstream co-op.
- 2:15-2:50 Alternatives with price ranges and industry usage bars.
- 2:50-3:15 Procurement proposal. Manager approves. Valio mock order ID shown.
- 3:15-3:50 Supplier confirms claimed to agreed. Auditor stamps audited.
- 3:50-4:10 Audit timeline. Close on the radar.
Fallback: the pre-recorded run, labelled as a replay.

## 9. Judging-criteria mapping
- **Valio (30%):** approval gate, order only via mock API, audit timeline, partial-availability handling.
- **Buyer need (20%):** the radar answers "what is building upstream of me".
- **Feasibility (25%):** one database, scoring in code, one fallback path.
- **Context.dev (15%):** news search, extraction, monitor webhooks, corroboration arriving live.
- **Trust and privacy (10%):** SQL views, `trust_transition` as the only trust write path.
- **Concreteness (10%):** schemas, SQL, scoring rules.
- **Bounties:** Gemini (extraction, discovery), Aiven (hosting, Postgres), CRACI (about an hour of CI setup). Cala and Codex skipped.

## 10. Risks and cuts
- **Cut first:** alternatives beyond one category, Cala, Oxylabs, Modal, ArcadeDB.
- **Risk:** Context.dev latency or rate limits. Mitigation: a recorded run that is labelled as a replay if the live call fails.
- **Risk:** quote check rejects too much. Mitigation: fall back to domain-level corroboration for the demo event only.
- **Risk:** Valio mock API shape differs from the brief. Mitigation: Friday-morning contract check.

## 11. Biggest weakness of this proposal (be honest)
Procurement is thin, so Valio judges looking for richer substitution, sustainability or delivery comparisons will score us lower on exception handling and buyer need. The regulatory layer runs on a seeded snapshot, so its credibility depends on a snapshot rather than live data.

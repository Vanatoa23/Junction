# Entrant 30: Ledgerline, Resumable Agents with Human Gates (lens: LangGraph orchestration with checkpoints and interrupts)

## 0. Bold bet
Every agent run is a LangGraph graph persisted to Postgres checkpoints, so any run can pause for a human, survive a restart, and be replayed step by step on screen. The approval gate is a real `interrupt()` bound to a hash of the exact proposal shown, which is the strongest answer to "guardrails and auditability" we can give in 48 hours.

## 1. Summary and name
- Name: **Ledgerline**. Buyers see their supply map, risk alerts and opt-in alternatives. Agents grow the network and propose supplier switches. A manager approves each order before it reaches Valio's mock API.
- Stack: Python 3.12, LangGraph with `langgraph-checkpoint-postgres`, FastAPI with SSE, React + Cytoscape.js, Aiven Postgres (pgvector) for all data and checkpoints, Aiven Runtime for hosting, Valkey for a Context.dev response cache.
- Assumption: LangGraph's `interrupt()`, `Command(resume=...)`, `PostgresSaver` and `astream(stream_mode="updates")` behave as in current docs. Verify in the Friday spike.

## 2. Architecture and DB choice
- **Postgres on Aiven, not ArcadeDB.** The team already knows it, Aiven is a sponsor bounty, and LangGraph's checkpointer targets it directly. Upstream traversal is a recursive CTE capped at depth 4, which is cheap at demo size. Alternatives use pgvector. ArcadeDB would add a second engine with no benefit to the orchestration story.
- Components:
  - API (FastAPI): sets `app.user_id` per request. Clients never send SQL.
  - Three LangGraph graphs: `discovery`, `monitoring`, `procurement`. Each run is a thread; its `thread_id` is stored in `agent_runs`.
  - Context.dev: company enrichment, news search, JSON-schema scrape, monitors that post to `/hooks/context`.
  - Gemini: structured output for extraction, risk tagging and rationale.
  - Valio mock: catalogue, availability, order.
  - Event stream: `astream(stream_mode="updates")` pushed to the UI over SSE.
- Graphs share no in-memory state. Monitoring starts a procurement thread through the database, so each graph can be restarted alone.

## 3. Data model and key queries
Tables:
- `companies(id, name, domain, country, industry[], registered, visible_alt, certs jsonb, embedding vector(768))`
- `edges(id, supplier_id, buyer_id, trust trust_level, confidence, owner_id, visibility private|public, sources jsonb, supplier_confirmed, auditor_id, updated_at)`. `trust_level` is an enum ordered inferred < claimed < agreed < audited. A trigger rejects any downgrade.
- `products(sku, supplier_id, name, price_min, price_max, price_published, lead_time_days)`
- `risks(id, company_id, type, score, confidence, sources jsonb, observed_at)`
- `proposals(id, thread_id, payload jsonb, payload_hash, status)`
- `audit_events(id, thread_id, ts, actor, action, payload jsonb, prev_hash, hash)`
- LangGraph checkpoint tables, created by `PostgresSaver.setup()`.

Visibility is enforced by Postgres row-level security, not by application code:
```sql
CREATE POLICY edge_view ON edges FOR SELECT
  USING (owner_id = current_setting('app.user_id') OR visibility = 'public');
```
Aggregates come from a SECURITY DEFINER function that returns counts only and suppresses any group under 5.

Key queries:
- **Upstream chain:**
```sql
WITH RECURSIVE up(supplier_id, buyer_id, trust, depth) AS (
  SELECT supplier_id, buyer_id, trust, 1 FROM edges WHERE buyer_id = $me
  UNION ALL
  SELECT e.supplier_id, e.buyer_id, e.trust, up.depth + 1
  FROM edges e JOIN up ON e.buyer_id = up.supplier_id WHERE up.depth < 4
) SELECT * FROM up;
```
RLS filters each viewer's rows, so the same query returns only what that viewer may see.
- **Hidden concentration:** group upstream rows by upstream company; keep those with at least 2 distinct direct suppliers. Output: "two direct suppliers share milk co-op X".
- **Blast radius:** recursive downstream walk from a failed supplier; returns affected buyers and hop count.
- **Alternatives:** `SELECT c.*, p.price_min, p.price_max FROM companies c JOIN products p ON p.supplier_id = c.id WHERE c.visible_alt AND p.price_published ORDER BY c.embedding <=> $q LIMIT 5`.

## 4. Agents
Each agent is a LangGraph `StateGraph` with a Postgres checkpointer.

**Discovery graph:** `plan_queries` (Gemini turns Valio's supplier names into search queries) → `search` (Context.dev news and company search; Exa optional) → `extract` (Context.dev scrape with a JSON schema: company, supplies_to, source URL) → `validate` (at least 2 distinct URLs, or confidence ≥0.7 with a domain match; otherwise `needs_review`) → `upsert` (node `registered=false`; edge `trust=inferred`, `visibility=public`, confidence and sources stored) → END.
- Interrupt `review`: fires only for candidates with confidence 0.4–0.7. A manager accepts or drops them. This shows human-in-the-loop outside payments.

**Monitoring graph:** triggered by a Context.dev monitor webhook or a 6-hourly cron. `classify` (Gemini → `{type, severity, summary, source_url}`) → `score` (section 5) → `write_risk` → `propagate` (recursive upward walk, decay 0.8 per hop) → if a score ≥0.6 sits in a buyer's chain, start a procurement thread.

**Procurement graph (the showpiece):**
1. `load_context`: affected SKUs, current supplier, trust level, risk.
2. `find_alternatives`: SQL plus pgvector, excluding suppliers already tried in this thread.
3. `propose`: Gemini returns a JSON proposal (lines, substitute, price delta, rationale citing graph facts and risk URLs). Stored with `payload_hash`.
4. `approval` (`interrupt`): the UI receives `{proposal, payload_hash, total_eur}`. Resume must send `{decision, payload_hash}`. A mismatched hash is rejected, so an approval covers only the exact proposal the manager saw.
5. Guardrail: totals above €2,000 raise a second `interrupt` for a senior approver.
6. `check_stock`: Valio mock availability. Partial stock routes to `substitute`, which loops back to `find_alternatives` (maximum 2 loops). A lead time outside the delivery window ends as `rejected` with a reason.
7. `place_order`: Valio mock order at fixed price. Only reachable through the approval edge.
8. `audit`: every node appends a hash-chained `audit_events` row.

A rejection at step 4 ends the run as `rejected`. Nothing is ordered.

## 5. Risk engine
Each type scores 0–1 with a confidence. The company score is the max; upstream risk reaches buyers with 0.8 decay per hop.
- **Geopolitical:** labelled country-table snapshot, plus Context.dev news from the last 30 days. A Gemini conflict tag adds 0.3.
- **Regulatory:** sanctions snapshot exact match 1.0, fuzzy 0.6. Expired certificate 0.8. Missing CSDDD/EUDR certificate for a product in scope 0.5.
- **Concentration:** shared upstream count / 5, capped at 1.
- **Financial:** news tags; layoffs 0.4, insolvency 0.7, funding informational only.
- **Live events:** recall, strike or outage tags, 0.5–0.9 by severity.
- **Price premium:** premium / 0.3, only when prices are published.

## 6. Screens and graph view
1. Persona switch (hotel, grocery, manager, supplier, auditor). No real auth.
2. Supply map: arrows run supplier → buyer. Line style encodes trust: dotted inferred, solid claimed, double agreed, bold with badge audited. Node colour encodes risk. Dashed border marks invited, unregistered nodes. Inferred edges show confidence.
3. Risk card: type, score, confidence, source links, traversal path ("via tier-2").
4. Alternatives: opted-in suppliers, price range, lead time, certificates.
5. Run inspector: the procurement graph drawn with the current node lit, a checkpoint timeline, and an approval card with Approve and Reject. This is the screen that makes the orchestration visible.
6. Audit timeline with hash chain.
7. Supplier confirm (claimed → agreed). 8. Auditor stamp (audited).
9. Discovery console streaming hits with URLs.

## 7. Demo script (4 min)
- 0:00–0:20: Valio at the centre. "Who do they depend on?"
- 0:20–0:50: Log in as the hotel. Walk the map and trust legend.
- 0:50–1:30: Run discovery live. Hits stream with URLs; inferred nodes appear; the run inspector lights up node by node.
- 1:30–1:50: Supplier confirms in a second tab, claimed → agreed over SSE. Auditor stamps audited.
- 1:50–2:30: Monitor webhook fires on a dairy producer (recall or strike news). Risk card shows sources; procurement thread starts automatically.
- 2:30–3:10: Run inspector pauses at approval. Show proposal, hash, rationale. First alternative is short on stock, so the substitute loop shows in the checkpoint timeline; second alternative works.
- 3:10–3:40: Manager approves. Total is above €2,000, so a second approver is requested briefly. Valio mock order placed.
- 3:40–4:10: Audit timeline. Log in as the supplier to show the hotel's private edges are absent (RLS). Show aggregate usage view.
- Optional: kill the API during the pause and restart it; the approval card reappears from the checkpoint.
- Backup: recorded run.

## 9. Judging-criteria mapping
- **Valio (30/20/20/15/15):** approval interrupt bound to a hash is a concrete guardrail; second approver over threshold; hash-chained audit; exceptions modelled as graph edges (partial stock, lead time); open standards: inspectable checkpoints and OpenAPI-described mock calls.
- **Context.dev:** discovery extraction and monitor webhooks are in the core flow; URLs shown on every inferred edge; webhooks give real-timeness.
- **Trust and privacy:** RLS in Postgres; monotonic trust trigger; aggregates suppressed below 5.
- **Concreteness:** schemas, SQL and the run inspector on screen.
- **Bounties:** Gemini (structured output in all three graphs); Aiven (Postgres, Valkey, Runtime); CRACI (Action, SBOM); Codex (development, logged in commits). Cala is cut.

## 10. Risks and cuts
- **Cut order:** Cala, Oxylabs, Modal, Exa, Valkey, pgvector (fallback: keyword match on industry and country), discovery review interrupt, second approver.
- **Risks:** (1) LangGraph API drift and the interrupt-plus-SSE combination; pin versions and spike Friday. (2) Recursive SQL as the graph layer; fine at this size. (3) Context.dev latency on stage; pre-warm and cache. (4) Webhooks need a public URL; use a tunnel and fall back to polling. (5) Gemini rate limits; cache extractions.

## 11. Biggest weakness of this proposal
Orchestration adds three moving parts that must all work on stage: checkpoints, interrupts and SSE streaming. Debugging a paused graph is slow. The graph story is also weaker, because traversal is recursive SQL on Postgres rather than a graph engine. The backend is Python and the UI is TypeScript, which costs integration time.

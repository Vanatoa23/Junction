# Entrant 10: Vouchline (lens: Verifiable credentials trust layer)

## 0. Bold bet
Every trust upgrade (claimed, agreed, audited) and every human approval is a signed W3C Verifiable Credential, hash-chained per edge, so trust and guardrails are cryptographically checkable by Valio and buyers, not just logged. A "Verify" button that checks issuer signatures live turns the auditability criterion into something judges can click.

## 1. Summary and name
- **Vouchline**: a living supply-chain graph where each edge's trust level is backed by signed attestations. The hotel chain sees its map, a dairy risk alert, priced alternatives and a procurement proposal. A manager signs an ApprovalCredential, and the Valio mock API verifies it before placing the order.
- Assumption: credentials follow VC Data Model 2.0 payloads, encoded as VC-JWT (JWS, Ed25519 via `jose`) instead of Data Integrity proofs, to avoid tooling friction. Swapping encodings is a one-module change.
- Identifiers: `did:web` per company, resolved from a local DID-document map (no hosting). Keys are generated at seed time and stored in the seed file. This is demo-only custody, labelled as such on screen.

## 2. Architecture and DB choice
- **ArcadeDB as primary store** (graph, document, vector in one engine). Credentials are document vertices; edges reference them by RID. One store, one query language (Cypher) for traversal, no second database to sync.
- Stack: Node/TypeScript API (Fastify), `jose` for signing, React + Cytoscape.js for the graph, Gemini for extraction and classification, Exa for search, Context.dev for enrichment, news and monitors.
- Flow: UI → API → services (VC library, trust deriver, visibility filter, risk engine, agents) → ArcadeDB. Context.dev webhooks and the Valio mock client sit at the API edge.
- Hosting: app on Aiven Runtime (side bounty). ArcadeDB runs in Docker locally.
- Fallback decision point: if ArcadeDB Cypher quirks block us by Saturday 18:00, the same schema moves to Postgres with recursive CTEs. The VC layer is DB-agnostic, so it survives the switch.

## 3. Data model and key queries
Vertices:
- `Company {did, name, country, sector, registered, opted_in, published_prices, embedding}`
- `Credential {id, type, issuer_did, jwt, sha256, prev_hash, subject_edge, issued_at, revoked_at}`

Edge `SUPPLIES` (supplier → buyer) with `{id, trust_level, confidence, sources[], vc_ids[], updated_at}`.

Trust level is derived by the API, never trusted from the client. The edge takes the highest level whose required credentials verify:
- `inferred`: no party credential. Agent provenance (`InferenceCredential`) is attached, carrying confidence and source URLs. It is not a trust upgrade.
- `claimed`: one valid `SupplyClaim` signed by either party.
- `agreed`: `SupplyClaim` from both DIDs over the same `edge_hash`, or a counter-signed `SupplyConfirmation`.
- `audited`: `AuditCredential` from an allowlisted auditor DID referencing an agreed edge's hash.
- Downgrade: a revoked credential or a broken `prev_hash` chain drops the edge one level.

Example VC payload (claimed):
```
{"@context":["https://www.w3.org/ns/credentials/v2","https://vouchline.example/ctx/trust/v1"],
 "type":["VerifiableCredential","SupplyClaim"],
 "issuer":"did:web:valio.example:company:valio",
 "validFrom":"2026-11-14T10:00:00Z",
 "credentialSubject":{"edge_hash":"sha256:ab12…","supplier":"did:web:…:dairy-x","buyer":"did:web:…:valio","relation":"SUPPLIES"},
 "prev_hash":"sha256:…"}
```

Visibility: a single `visibleEdges(viewerDid)` function in the API returns the viewer's own edges. For other companies it returns only risk credentials, anonymised aggregates (minimum group size 5) and opted-in alternatives. This is enforced in the API, not by DB ACLs, which we state honestly.

Sketch queries (verify Cypher syntax in ArcadeDB on Friday):
- Upstream, 3 tiers, excluding inferred: `MATCH (b:Company {did:$me})<-[e:SUPPLIES*1..3]-(s) WHERE all(x IN e WHERE x.trust_level <> 'inferred') RETURN s, e`
- Hidden concentration: `MATCH (b:Company {did:$me})<-[:SUPPLIES]-(d)<-[:SUPPLIES]-(u) WITH u, collect(DISTINCT d.name) AS via WHERE size(via) >= 2 RETURN u, via`
- Blast radius: `MATCH p=(u:Company {did:$failed})-[:SUPPLIES*1..4]->(c) RETURN c.did, min(length(p))`
- Alternatives: opted-in companies in the sector, ranked by vector distance on product embeddings (ArcadeDB HNSW), joined to published prices only.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery.** Inputs: seed company names, Exa news and company search, Context.dev enrichment and news. Gemini extracts `{supplier, buyer, relation, evidence_url, quote, confidence}`. Validation: at least one fetched source URL, and the quote must appear in the fetched text. The edge is written as `inferred` with confidence and sources. The agent DID signs an `InferenceCredential` for provenance. No human gate, but inferred edges render dashed.
- **Monitoring.** Context.dev monitors on supplier recall, certification and news pages, delivering webhooks to `/hooks/monitor`. Gemini classifies each change into a risk type. The monitor DID signs a `RiskCredential` carrying evidence URL, confidence and expiry. A 5-minute poll backs up the webhook.
- **Procurement.** Triggered by a risk or a published price premium. It queries the Valio mock for product, availability, lead time and price, then finds opted-in alternatives. Output: a draft `OrderProposal`. Human gate: the manager clicks Approve, and the server signs an `ApprovalCredential` bound to the proposal hash, a spend cap and a 15-minute expiry. The Valio client refuses to call the order endpoint without a verifying ApprovalCredential. Valio's mock verifies the same VC against our DID document, so the gate holds on both sides.

## 5. Risk engine
Each detector writes a `RiskCredential`. Score = severity weight × confidence × recency. Aggregation is by max severity, not sum.
- **Geopolitical:** country index snapshot (labelled as static) plus Gemini news classification.
- **Regulatory:** EU consolidated sanctions list snapshot. CSDDD and EUDR flags when a supplier lacks a `CertificateCredential` for a relevant commodity, or the certificate is expired.
- **Concentration:** the shared-upstream query above. Single-source flag when a category has one incoming `SUPPLIES` edge.
- **Financial:** Context.dev company enrichment (headcount delta, funding) plus layoff and insolvency news.
- **Live events:** Context.dev monitors on recall, strike and outage pages.
- **Price premium:** (price − cheapest published alternative) / cheapest. Shown only where prices are published.
- Upstream alerts propagate: the buyer sees the risk, not the intermediate's supplier list.

## 6. Screens and graph view
1. Persona sign-in: hotel manager, Valio admin, supplier, auditor.
2. **My supply map:** Cytoscape, upstream on the left, customers on the right. Solid = agreed, solid with a check badge = audited, dashed = claimed, dotted = inferred with confidence %. Red edge overlay = risk severity. Grey node = unregistered. Hover shows "Signed by X, claimed, date".
3. Risk alert: evidence URLs, `RiskCredential` ID, Verify button.
4. Alternatives: cards with price range (published only), opt-in badge, anonymised "used by N% of sector" aggregate.
5. Procurement: current vs proposed supplier diff, price, lead time, Approve button, signed-VC preview.
6. Ledger: chronological credentials with issuer, type, hash-chain tick. Verify shows "signature valid / revoked / chain OK".
7. Supplier inbox: confirm edge (claimed → agreed).
8. Auditor console: stamp audited.

## 7. Demo script (timed beats, ~4 min)
- 0:00–0:25: hook slide, "Who is behind your dairy?" Sign in as the hotel manager.
- 0:25–1:00: supply map. Click the Valio edge, press Verify, shows "signed by Valio, claimed".
- 1:00–1:30: **live run.** "Scan now" triggers discovery (Exa plus Context.dev). A new dotted edge appears with source URLs and confidence. Pre-warmed cache is the fallback.
- 1:30–2:00: supplier persona confirms the edge, so claimed becomes agreed. Ledger entry appears.
- 2:00–2:20: auditor stamps audited.
- 2:20–2:50: **live webhook.** A staged change on a demo supplier page fires a Context.dev monitor. Risk alert on the dairy producer, with evidence link.
- 2:50–3:30: priced alternatives, opt-in only. Procurement proposal.
- 3:30–3:50: Approve. ApprovalCredential signed. Valio mock accepts the order after verifying it. Ledger shows the chain.
- 3:50–4:10: exception: partial availability forces a substitution, which needs a fresh signed approval.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards):** full flow in the demo. Need: buyers get a guaranteed human-approved order. Controls: ApprovalCredential gate plus Verify on the ledger. Exceptions: the substitution re-signs. Standards: W3C VC 2.0, `did:web`, JOSE, verifiable by Valio from our DID document.
- **Context.dev (15%):** discovery on live news and enrichment, monitor webhooks for real-timeness, every inferred edge cites a fetched URL.
- **Trust and privacy (10%):** the basis of each edge is visible and signed. Visibility is enforced in one function.
- **Concreteness (10%):** schemas, VC example and queries above.
- **Side bounties (10%):** Gemini (extraction and classification), Aiven (hosting, Postgres fallback), Codex (mock and tests), CRACI (SBOM CI).
- Cala: skipped unless the core is done by Saturday night.

## 10. Risks and cuts
- Cut order: Oxylabs, then Cala, then Modal/Verda, then vector search (fall back to keyword), then the substitution exception. Never cut: the signed approval gate, one live Context.dev run, the visible Verify button.
- Risks: ArcadeDB Cypher quirks (SQL and Postgres fallback). Demo key custody (labelled). Interop with third-party VC verifiers (not claimed beyond our DID document). Context.dev rate limits (cached responses). Unknown Valio mock shape (an adapter, assumed). The UI graph taking longer than planned (Cytoscape defaults).
- The VC layer costs about one engineer-day on the critical path. Cut Data Integrity proofs first (already out of scope).

## 11. Biggest weakness of this proposal
The cryptography is invisible in a 4-minute demo unless judges press Verify, and the VC layer could read as a gimmick if the core flow (map, alert, order) is weak. Key custody, DID resolution and the auditor are simulated, so the production path (EUDI wallet, real auditors, real DID hosting) is a roadmap claim, not something we demo.

# Entrant 40: Quorum (lens: multi-role approval)

## 0. Bold bet
Every side effect (order, edge confirmation, audit stamp, opt-in) is an approval that needs named humans on separate devices, with a hash-chained log. On stage, four live sessions (buyer, manager phone, supplier, auditor) react to one real web change, so judges see controls working across roles.

## 1. Summary and name
- Name: **Quorum**.
- A hotel chain buys through Valio Aimo. A Context.dev monitor detects a change on an upstream dairy page; the procurement agent drafts a switch; the request lands on the manager's phone; the order goes to Valio's mock API after approval; supplier and auditor act in their own sessions, and trust levels move with each approval.
- Assumptions:
  - A1: Context.dev monitors can be created by API with interval and webhook URL; the webhook includes changed content.
  - A2: Web Push works in an installed PWA on the demo phone; fallback is a single-use link.
  - A3: Venue Wi-Fi allows outbound push; the webhook receiver has a fixed public URL.

## 2. Architecture and DB choice
- **Aiven managed Postgres** as the only store: graph as adjacency tables, approvals as rows, audit chain as an append-only table; LISTEN/NOTIFY pushes state to all open sessions.
- **ArcadeDB not used:** approvals need transactional state; a second store adds failure modes.
- **One React PWA, four role routes** (`/buyer`, `/manager`, `/supplier`, `/auditor`), seeded demo logins, each scoped server-side.
- **Backend** on Aiven Runtime: SSE per session, approval decide, Valio mock client, webhook receiver. **Gemini Flash** for agents; **Context.dev** for monitors.
- Path: webhook → `change_event` → monitoring agent → `risk_signal` → procurement agent → `approval` (order) → Web Push to manager → decision → Valio order → NOTIFY to all sessions.

## 3. Data model and key queries
- `company(id, name, country, industry, registered, opted_in)`; `product(id, supplier_id, category, certs, cert_expiry, price_range null)`
- `edge(id, supplier_id, buyer_id, category, trust_level enum[inferred,claimed,agreed,audited], confidence, sources jsonb)`
- `approval(id, kind enum[order,edge_confirm,audit_stamp,opt_in], subject_id, payload jsonb, payload_hash, required_roles text[], status enum[pending,approved,rejected,expired], expires_at)`
- `approval_decision(approval_id, actor_id, role, decision, device, ts)`
- `link_token(token_hash, approval_id, role, expires_at, used_at)`: single-use, 15-minute links.
- `audit_event(seq, prev_hash, hash, actor, action, payload, ts)`: `hash = sha256(prev_hash || canonical payload)`; buyer screen shows "chain verified".
- Trust is derived from approvals: `claimed` on creation; `agreed` when the supplier's `edge_confirm` is approved; `audited` when an `audit_stamp` is approved.

Visibility, enforced in SQL per role:
- Buyer: own edges; upstream risk signals only; alternatives where `opted_in` and price published; industry aggregates only when n >= 5.
- Manager: approval payload, risk warning, proposal. No map.
- Supplier: own edges and own price publication.
- Auditor: dossier (certificates, sources) for edges it is asked to stamp. No map.

Key queries:
- **Upstream:** `WITH RECURSIVE` from the buyer over `edge`, depth <= 4, cycle-guarded.
- **Hidden concentration:** upstream grouped by company; flag `count(DISTINCT direct supplier) >= 2`.
- **Blast radius:** same walk forward from a failing company.
- **Approval inbox:** pending approvals where `required_roles` contains the caller's role.

## 4. Agents (discovery, monitoring, procurement)
Rule: agents propose; only humans approve. Agents hold no approval rights and each side effect creates an `approval` row.
- **Discovery.** Tools: Context.dev enrichment, news search, structured extraction. Output: `inferred` edges with confidence and evidence URLs; evidence must contain both names; confidence >= 0.6. Material edges create an `edge_confirm` approval for the supplier.
- **Monitoring.** Tools: Context.dev webhook and scrape; Gemini classifier returning `{type, severity, confidence, quote, source_url}`. Output: `risk_signal`; `high` needs two sources or one official source.
- **Procurement.** Trigger: `high` risk or published-price premium. Checks alternatives and Valio availability, proposes substitution on partial stock, creates an `order` approval with `required_roles = {manager}`, plus `{finance}` above EUR 2,000.

## 5. Risk engine
- Company score = max(severity weight x confidence) over signals, plus upstream propagation at 0.7 per tier.
- **Live events:** Context.dev monitors on recall and news pages (the demo trigger).
- **Geopolitical:** hand-entered country index (assumption) plus news search.
- **Regulatory:** sanctions list (assumption: CSV fetched at build time); certificate expiry; CSDDD flag where no `audited` edge exists. EUDR shown as not applicable to dairy.
- **Concentration:** single-source categories; shared upstream from the graph.
- **Financial:** Context.dev enrichment plus news keywords.
- **Price premium:** only where prices are published.

## 6. Screens and graph view
- **Buyer (laptop):** supply map, live alert feed, proposal status, audit log with chain badge.
- **Manager (phone PWA):** approval card: change, source URL, current vs proposed supplier, price delta, lead time; Approve / Reject with PIN; two-person status line.
- **Supplier:** edge confirmations (claimed → agreed); price-publication toggle.
- **Auditor (tablet):** edge dossier; stamp `audited`.
- **Graph:** arrows supplier → buyer, Valio at centre; solid = agreed, dashed = claimed, dotted = inferred (confidence), double = audited; node colour = risk; changed node pulses.

## 7. Demo script (about 4:00, four devices on stage)
- **0:00-0:25** Hook: four roles, one network. Buyer shows the supply map.
- **0:25-0:55** Live web: monitor list; discovery run with real public URLs.
- **0:55-1:25** We publish a recall notice on the watched DEMO dairy page. Webhook fires; alert appears on the buyer screen with latency (target under 10 s); manager's phone buzzes.
- **1:25-1:55** Manager opens the card: source URL, substitution for partial stock. Approves with PIN. The two-person line shows the order over EUR 2,000.
- **1:55-2:20** Valio mock order placed with approval ID and idempotency key; buyer log shows the chain.
- **2:20-3:05** Supplier confirms the edge (`claimed` → `agreed`); auditor stamps `audited`. Edge styles change live on the buyer screen.
- **3:05-3:25** "Verify chain" passes. Manager cannot see the full map; buyer cannot see unpublished prices.
- **3:25-4:00** Fallback: webhook replay, backup video.

## 8. 48h build plan (4 engineers)
- **Roles:** A = approvals, audit chain, Valio client. B = monitors, webhook, discovery. C = agents, risk engine. D = PWA, four role screens, Web Push.
- **M1 Friday night:** schema; webhook on public URL; monitor event creates `change_event`; approval created and decided via API.
- **M2 Saturday:** monitoring agent to `risk_signal`; proposal; manager card with push and fallback link; buyer map; Valio catalogue client.
- **M3 Saturday night:** supplier and auditor sessions; two-person rule; order on approval; hash-chain verify; SSE everywhere.
- **M4 Sunday morning:** freeze about 09:00; rehearse the four-device run three times; backup video.
- Side items: CRACI SBOM action; Codex only if actually used and logged.

## 9. Judging-criteria mapping
- **Valio (30%):** end-to-end order via mock API after approval; controls (20%): RBAC, two-person rule, idempotent order, hash-chained log; exceptions (15%): partial stock → substitution needs approval; buyer need (20%): alternatives with price and lead time; open standards (15%): JSON Schema approval payloads.
- **Context.dev:** a web change triggers a phone approval within seconds; source URLs on every card.
- **Trust and privacy (10%):** trust derived from approvals; per-role queries.
- **Bounties:** Gemini, Aiven, CRACI. Cala not claimed.

## 10. Risks and cuts
- **Push or Wi-Fi fails (A2/A3):** QR on the big screen opens the same single-use card link on the phone.
- **Four live sessions:** each device has a replay state; "switch to replay" on each.
- **Monitor timing (A1):** 60 s scrape fallback; webhook replay.
- **Cut order:** Cala; Exa; Oxylabs; Modal/Verda; second approver (static line); graph animation.

## 11. Biggest weakness of this proposal
Four live roles multiply the demo's failure surface for four engineers: one stalled device breaks the flow in front of judges. The two-person rule and hash chain look like decoration unless the verify step is shown clearly.

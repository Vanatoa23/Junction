# Entrant 11: Event Spine (lens: event-driven architecture)

## 0. Bold bet
Every claim, trust change, agent finding, risk score, approval and order is an immutable event on Aiven Kafka, so the audit trail is the event log itself and the demo can be replayed deterministically if live data misbehaves. Visibility and trust rules live in the projector, so privacy is enforced structurally rather than by UI checks.

## 1. Summary and name
**Tributary.** Companies declare supply edges; agents publish findings; a risk engine publishes scores; procurement proposes switches; a human approves; an order executor calls the Valio mock API. Nothing mutates state directly. Postgres is a projection of the event log, and the UI is a projection of Postgres plus a live SSE feed of the log.

## 2. Architecture and DB choice
- **Spine:** Aiven for Kafka (Aiven bounty). Fallback: Aiven Valkey Streams or local Redpanda, keeping identical topic names and envelope.
- **Components (all TypeScript/Node, one repo):**
  - Ingress: Context.dev monitor webhook receiver, Exa/Context.dev pollers, UI commands. All produce events.
  - Projector: consumes all domain topics, writes Postgres, enforces trust monotonicity and visibility.
  - Agent workers: discovery, monitor, procurement (separate consumer groups).
  - Risk engine: consumer with in-memory state rebuilt from topic replay on start.
  - Order executor: consumes `approvals`, calls Valio mock, emits `orders`.
  - API + SSE gateway: serves views from Postgres; fans out `audit.all` to browsers.
  - UI: React + Cytoscape.js.
- **Database: Aiven Postgres** as projection store. Recursive CTEs cover upstream traversal, concentration and blast radius. ArcadeDB is cut from core: it is not sponsor-hosted, adds a Docker service and a query language the team must learn, and Postgres handles the graph sizes here (under 2k nodes). ArcadeDB is a stretch only.
- **Envelope (every event):** `{id, type, schema_v, ts, actor, subject, payload, trust?, confidence?, source_urls[], visibility, idem_key}`.
- **Topics** (key = subject company id for ordering): `signals.web`, `edges.candidate`, `edges.trust`, `companies.registered`, `risk.signal`, `risk.score`, `procure.proposed`, `approvals`, `orders`, `audit.all` (mirror of all), `*.dlq`.

## 3. Data model and key queries
- **Tables:** `company(id, name, country, registered, visible_opt_in)`, `price_publish(company, sku, min, max, currency)`, `edge(id, src, dst, trust, confidence, sources jsonb, owner, visibility)`, `risk_score(company, type, score, path)`, `proposal`, `approval`, `order`, `audit` (projection of `audit.all`).
- **Trust rule:** rank only increases (`candidate` < `claimed` < `agreed` < `audited`). `agreed` needs confirm events from both `src` and `dst`. `audited` needs an auditor event. Projector rejects regressions and sends them to DLQ.
- **Visibility rule:** each edge carries `owner`. Buyer API reads only `v_buyer_edges` (own map), `v_risk` (risk warnings with path), `v_peer_usage` (count by industry, minimum group size 5), `v_alternatives` (where `visible_opt_in`), and prices from `price_publish`.
- **Upstream traversal (depth 3, Valio):**
```sql
WITH RECURSIVE up AS (
  SELECT src, dst, 1 AS d, ARRAY[dst] AS p FROM edge WHERE dst = $1
  UNION ALL
  SELECT e.src, e.dst, up.d+1, up.p || e.dst FROM edge e
  JOIN up ON e.dst = up.src
  WHERE up.d < 3 AND NOT e.dst = ANY(up.p))
SELECT * FROM up;
```
- **Hidden concentration** (upstream firm supplying >=2 direct suppliers):
```sql
SELECT s2.src AS shared_upstream, array_agg(DISTINCT s1.src) AS via
FROM edge s1 JOIN edge s2 ON s2.dst = s1.src
WHERE s1.dst = $1 GROUP BY s2.src HAVING count(DISTINCT s1.src) >= 2;
```
- **Blast radius:** same recursion as above, walking `src -> dst` downward from a failed node.
- **Alternatives:** companies in the same category, `visible_opt_in = true`, with a `price_publish` row, excluding current suppliers, ordered by midpoint price.

## 4. Agents (discovery, monitoring, procurement)
Shared rules: outputs are zod-validated; `confidence` in [0,1] and at least one `source_url` required (two for `inferred` edges). Failures go to `*.dlq` and show in the timeline. Agents never write Postgres, only events.
- **Discovery.** Trigger: 10-min schedule plus a "Run discovery now" button. Inputs: Context.dev news search and company enrichment (assumed endpoints per brief), Exa search as backup. Gemini with JSON-schema output extracts `{company, relation, country, confidence, quote, url}`. Output: `signals.web`, and `edges.candidate` with trust `inferred`.
- **Monitoring.** Context.dev monitors register per watched company/news query; webhook POSTs land on ingress and become `signals.web`. Scheduled sanctions check (public list, assumed format) and Gemini classification of each change into a risk type and severity, emitted as `risk.signal`.
- **Procurement.** Consumes `risk.score` above threshold on a supplier that feeds a buyer. Tools: Valio mock catalogue (assumed `/products`, `/availability`, `/leadtime`) and the alternatives query. Gemini drafts the rationale. Emits `procure.proposed` with line items. Exceptions: partial availability splits the proposal; no substitute emits `procure.escalated`.
- **Human approval and execution.** Approval is an event `approvals {proposal_id, proposal_hash, approver}`. The executor refuses any order without a matching approval, and calls the Valio mock order endpoint (assumed `/orders`) with `Idempotency-Key = proposal_id`. Result is `orders` plus audit.

## 5. Risk engine
- **Score:** per signal `c = severity x confidence x 0.5^(age_days/14)`. Company risk per type `= 1 - prod(1 - c)`.
- **Propagation:** buyer's exposed risk `= max(own, 0.5 x upstream risk)` per hop, with the path stored.
- **Types:**
  - Geopolitical: country index table (static, labelled assumption) plus news search keywords.
  - Regulatory: sanctions name match (fuzzy >0.9); certificate expiry dates from JSON docs; CSDDD flag stub. EUDR is not applied to dairy (it covers cattle, not dairy).
  - Concentration: shared-upstream query, severity = count/total.
  - Financial: Gemini classifies enrichment and news for layoffs, funding, insolvency.
  - Live events: recall, strike, outage keywords on live news (the demo beat).
  - Price premium: `(unit price - min visible alternative) / min`, only when published.

## 6. Screens and graph view
1. **Login:** demo hotel persona.
2. **Supply map:** Cytoscape graph, upstream on the left. Edge style by trust: dashed amber = `inferred` (confidence label), grey solid = `claimed`, dark solid = `agreed`, double gold = `audited`. Node border red/amber by risk. Unregistered nodes grey with "invite" badge. Clicking an edge shows source URLs.
3. **Risk alert:** highlighted path from alert to Valio and hotel, sources, confidence, "Find alternatives".
4. **Alternatives:** opted-in suppliers, published price range, lead time, certificate badges, peer-usage aggregate.
5. **Proposal and approval:** line items, split lines, Approve/Reject (approver recorded).
6. **Audit timeline:** live SSE ticker with actor type (agent/human/system), source URLs, "replay from offset".
7. **Supplier and auditor views:** confirm edge (claimed to agreed); stamp edge audited.

## 7. Demo script (about 4 min)
- 0:00 Problem: "We only see one step." 
- 0:20 Hotel logs in. Valio at centre; two `claimed` edges; one dashed `inferred` dairy producer, 0.78 confidence, two URLs.
- 0:55 Supplier tab confirms the edge; `claimed` becomes `agreed` on the hotel's map live via SSE.
- 1:20 **Live beat:** "Run discovery now" hits Context.dev news; fresh article becomes an `inferred` edge or risk within about 15 s, with its URL. Fallback: replay of Friday-recorded events.
- 1:50 Risk alert on the dairy producer propagates to Valio and the hotel; path highlighted.
- 2:20 Alternatives: opted-in only, published price range. Concentration card: "3 of your suppliers share upstream X."
- 2:50 Proposal: two substitute lines, one partial-availability split.
- 3:15 Manager approves; order placed via Valio mock; order id shown.
- 3:35 Timeline: every step with actor and source URLs. Replay from an offset.
- 3:50 Auditor stamps an edge `audited`. Privacy beat: the hotel sees only Valio's peer-usage aggregate, not its other customers.

## 9. Judging-criteria mapping
- **Valio (30%):** order only after approval event; exceptions (partial, substitution) are events; audit timeline is the log.
- **Feasibility (25%):** Kafka is extra ops; mitigated by replay mode and Valkey fallback.
- **Context.dev (15%):** monitor webhooks plus live news beat, URLs visible.
- **Trust and privacy (10%):** projector-enforced trust rank and visibility; peer aggregates with a minimum group size.
- **Concreteness (10%):** envelope, topics, SQL above.
- **Side bounties (10%):** Aiven (Kafka + Postgres), Gemini (extraction and rationale), CRACI in CI (near-zero effort). Codex only if used in development, stated honestly. Skip Cala, Modal, Oxylabs.

## 10. Risks and cuts
- **Cut order:** Oxylabs, Modal, Cala, ArcadeDB, price premium risk, live Exa. Last resort: swap Kafka for Valkey Streams with the same topic names.
- **Technical risks:** Aiven Kafka TLS/SASL from laptops (test Friday morning); webhook needs a public URL (tunnel, or rely on polling); async ordering bugs (key by subject); empty live news during the demo (pre-capture a real article Friday and replay it).

## 11. Biggest weakness of this proposal
Event-driven adds real infrastructure and debugging load over a monolith with a Postgres queue. Judges see the same UI either way, so the architecture only pays off if the team has the discipline to finish the projector and replay. Eventual consistency can make the screen lag by seconds, which is visible on stage. If Kafka fails on Saturday, we fall back and lose the bold bet.

Assumptions to verify: Context.dev endpoint names, Valio mock endpoint paths, and the sanctions list format.

# Entrant 52: Relay (lens: Team execution)

## 0. Bold bet
We treat the 48 hours as a distributed system: API contracts and mocks are frozen in the first hour, so four engineers never wait on each other, and every integration is checked at four fixed checkpoints. The product is deliberately modest; the win is a demo that works on Sunday because it was never more than one flag away from a fixture.

## 1. Summary and name
- **Relay**: a living supply-chain network. A hotel chain sees its supply map, a risk alert on an upstream dairy producer, priced alternatives and a procurement proposal. A manager approves, and the order goes to the Valio mock API. Every step is logged.
- Assumptions: Context.dev monitors and webhooks, Exa search and Gemini behave as the brief describes. Valio mock response shapes are unknown until Friday 19:00, so the contract is written against the brief and adjusted once, at checkpoint 1 only.
- Code freeze assumed at Sunday 09:00; confirm with organisers on Friday.

## 2. Architecture and DB choice
- **ArcadeDB** as the graph and document store (Docker, one container). Cypher for traversal. Postgres is not used: a second database adds sync work we cannot afford.
- Single Node/TypeScript monorepo: `api` (Fastify), `web` (React, Cytoscape.js), `agents` (module inside api, run as jobs), `mocks` (Valio, Context.dev, Gemini fixtures as one local server).
- Feature flags decide every external call: `GEMINI=fixture|live`, `CTX=fixture|live`, `EXA=fixture|live`, `VALIO=mock`. The demo runs with flags chosen per beat; a fixture always exists.
- Aiven Runtime hosts the app for the side bounty. Not on the critical path: if Runtime fails, the demo runs on a laptop.

## 3. Data model and contracts (frozen Friday 19:00)
Frozen before any feature code, as `contracts/openapi.yaml` plus shared TypeScript types:
- `GET /api/me` → `{did, role}`
- `GET /api/companies/:did/map` → `{nodes[], edges[{id, from, to, trust_level, confidence, sources[]}]}`
- `POST /api/edges/:id/confirm` (supplier) → edge with `agreed`
- `POST /api/edges/:id/audit` (auditor) → edge with `audited`
- `GET /api/alerts?viewer=` → `[{id, company_did, risk_type, severity, evidence_url, detected_at}]`
- `GET /api/alternatives?category=` → opted-in suppliers with published price ranges only
- `POST /api/proposals`, `POST /api/proposals/:id/approve` → `{approval_id, expires_at}`
- `POST /api/orders {proposal_id, approval_id}` → Valio mock response
- `POST /hooks/monitor` → webhook ingest (accepts fixture and live payloads)
- `POST /api/discovery/run` → SSE stream of `{company, edge, sources[]}`
- Valio mock: `GET /valio/products`, `GET /valio/availability`, `POST /valio/orders`

Graph schema: `Company {did, name, country, sector, registered, opted_in}`, `SUPPLIES {trust_level, confidence, sources[]}`, `Approval {id, proposal_hash, cap_eur, expires_at, signed_by}`, `Order {valio_id, proposal_id, approval_id, status}`. Trust and visibility are enforced in one API function, `visibleEdges(viewer)`.

Key query (Cypher sketch, check syntax Friday): `MATCH (b:Company {did:$me})<-[e:SUPPLIES*1..3]-(s) RETURN s, e` for upstream traversal. Blast radius: `MATCH p=(u:Company {did:$failed})-[:SUPPLIES*1..4]->(c) RETURN c.did, min(length(p))`.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery.** Input: company names. Exa search plus Context.dev enrichment. Gemini structured output: `{supplier, buyer, evidence_url, quote, confidence}`. Validation: quote must appear in fetched text. Written as `inferred` with sources. No human gate.
- **Monitoring.** Context.dev monitors on supplier status and recall pages, webhook to `/hooks/monitor`, 5-minute poll as backup. Gemini classifies the diff into a risk type and severity. Output: a `RiskSignal` with evidence URL.
- **Procurement.** Triggered by severity ≥ 4 or a published price premium. Builds an `OrderProposal` from Valio mock lookups. Human approval creates an `Approval` record bound to the proposal hash, 15-minute expiry. The Valio client refuses to order without it.
- Each agent has a fixture mode with the same output shape, so UI and tests never depend on a live call.

## 5. Risk engine
- Live events: recalls, strikes, outages from monitored pages. Recalls are floor severity 4.
- Regulatory: certificate expiry dates in supplier documents, rule-based, severity 4 when expired.
- Geopolitical: country index snapshot (static, labelled) plus news classification, capped at 3.
- Financial: news and status pages for layoffs or insolvency keywords, classified by Gemini.
- Concentration: computed from the graph (shared upstream and single-source categories).
- Price premium: published prices only.
- Score = severity × confidence. Alert if severity ≥ 3 and confidence ≥ 0.6. Buyers get the risky company's name, evidence URL and tier count, never the intermediate chain.

## 6. Screens and graph view
1. Sign-in: four personas, one click each.
2. Supply map: upstream left, Valio centre, customers right. Solid = agreed, dashed = claimed, dotted = inferred with confidence %. Red ring = open risk signal.
3. Alerts: newest first, source URL, quote highlighted.
4. Alternatives: cards with price range, opt-in badge.
5. Proposal and approval: current vs proposed, Approve button, approval record shown.
6. Ops log: every event (agent run, webhook, approval, order) with a timestamp and a Replay button.
7. Demo control panel (hidden behind a key): flags, reset seed, trigger fixture alert.

## 7. Demo script (timed beats, ~4 min)
- 0:00–0:25: hook, hotel chain signs in, supply map loads from seed.
- 0:25–0:55: click the Valio edge. Show claimed, one-sided. Supplier persona confirms → agreed.
- 0:55–1:25: auditor stamps audited. Edge shows the badge.
- 1:25–2:00: **live discovery.** Exa and Context.dev run, a new inferred supplier appears with source URLs and confidence.
- 2:00–2:40: risk alert on the dairy producer, from a fixture or a live monitor edit (chosen at 19:00 by the team, see plan).
- 2:40–3:10: alternatives with price ranges, opt-in only; proposal created.
- 3:10–3:40: manager approves; Valio mock accepts the order; ops log shows the chain.
- 3:40–4:00: exception: partial availability on the proposed product; the substitution needs a fresh approval.

## 8. 48h build plan (4 engineers, 4 milestones)
Engineers: A = core API and graph; B = agents and monitoring; C = procurement, Valio mock, approvals; D = web UI and demo ops. Each owns their contract endpoints.

Hour-by-hour (H0 = Fri 18:00):
- **H0–H1 (Fri 18:00–19:00):** freeze contracts, types and fixtures. Repo, Docker ArcadeDB, one-command start.
- **H1–H5 (19:00–23:00):** mocks first: Valio mock, fixture agents, seed JSON. D builds the map against fixtures. A builds schema and map endpoint. Checkpoint 1 (23:00): login → map renders from the API with no live calls.
- **Sleep (23:30–03:00):** two engineers sleep 3.5 hours each, staggered. One engineer stays awake on-call for merges and fixes, rotating at 01:00.
- **Sat 03:00–12:00:** B builds Context.dev monitor creation and the webhook ingest against a captured sample. C builds Valio client and approval record. Checkpoint 2 (12:00): one live discovery run writes an `inferred` edge into the graph.
- **Sat 12:00–18:00:** trust confirm and audit endpoints, alert feed, risk rules. Checkpoint 3 (18:00): full flow runs end to end in fixture mode.
- **Sat 18:00–22:00:** flip flags to live one at a time, each with fixture fallback. Rehearse the script once.
- **Sleep (23:00–03:00 Sun):** rotating again, same pattern.
- **Sun 03:00–07:00:** bug fixes only. Checkpoint 4 (07:00): full flow live in the agreed flag mode, backup video recorded.
- **Sun 07:00–09:00:** freeze at 09:00; two rehearsals with the final build; no merges after 08:30 except demo-blocking fixes.

Standing rules: merge to main only with a passing contract test; anything unfinished at the checkpoint is cut and noted in the ops log.

CRACI SBOM workflow set up Saturday (about 20 minutes). Codex used for the Valio mock and contract tests, logged in the repo.

## 9. Judging-criteria mapping
- **Valio (30%, 20%, 20%, 15%, 15%):** complete flow in the demo; approval record gates the order; the ops log shows every step; substitution exception; Valio mock is an OpenAPI contract, reusable.
- **Feasibility and demo reliability (25%):** the largest criterion for this lens. Fixtures and flags mean the demo has a working path at every checkpoint. Sleep schedule protects the 48-hour stretch.
- **Context.dev (15%):** live discovery and monitor webhook, source URLs on every inferred edge.
- **Trust and privacy (10%):** trust level on every edge; alerts exclude the intermediate chain.
- **Concreteness (10%):** contracts, schema and query sketches above.
- **Side bounties (10%):** Gemini (agents), Aiven (Runtime hosting), Codex (mock and tests), CRACI (SBOM CI). Cala skipped.

## 10. Risks and cuts
- Cut order, each with a go/no-go checkpoint: Cala and Oxylabs (cut at start), Aiven Runtime (cut at checkpoint 3 if unstable), live monitor edit (cut at checkpoint 4 if flaky, use fixture), substitution exception (cut at checkpoint 3).
- Risks: contract drift between engineers (mitigated by the frozen OpenAPI and contract tests), ArcadeDB Cypher quirks (fixture-backed UI means the demo still works), Context.dev payload shape unknown (captured on Saturday morning, adapter written then), integration fatigue on Saturday night (checkpoint 3 is the safety net).
- Sleep rotation is a risk in itself: a single missed merge window can block the team.

## 11. Biggest weakness of this proposal
The product is thinner than the lens-matched proposals. Judges may score the story and the risk engine lower because the build plan leaves less room for ambitious agents, and a strict fixture-first approach can make the live parts look like scripted replays if the flags are not flipped in time.

# Entrant 56: Warmline (lens: Latency and cost)

## 0. Bold bet
Warmline precomputes everything a judge can click (closures, risk scores, sorted alternatives, rationale drafts) and keeps the live web call to one bounded, streamed fetch, so every action answers in seconds without the agents looking slow. It wins because Context.dev explicitly scores latency and real-timeness, and a demo that never waits on a model reads as robust, while the cost meter shows the team spent almost nothing on a live run.

## 1. Summary and name
- Name: **Warmline** (data is warm before the judge arrives).
- The hotel chain opens its supply map instantly from a precomputed snapshot. A "Scan supplier" button streams one live Context.dev extraction and its news monitor result within about 8 seconds, with source URLs. A risk alert appears. The procurement agent streams a proposal in under 4 seconds. A manager approves, the Valio mock order returns in under 2 seconds, and every step is logged.
- Assumptions: Valio mock endpoints respond in under 500 ms (assumption; we measure it on Friday). Context.dev extraction on one page takes roughly 2 to 5 seconds (assumption; measured in M1).

## 2. Architecture and DB choice
- **Postgres on Aiven** as the store (Aiven bounty). Materialised views for precomputed results. **Valkey on Aiven** is optional, for a shared cache; start with an in-process cache so it is not a dependency.
- **ArcadeDB rejected**: a second engine adds setup risk, and a precomputed Postgres closure is faster for our fixed queries.
- Two paths, explicit in the code:
  - **Fast path (demo, under 8 s)**: one Context.dev structured extraction on one URL, one Gemini Flash classification, cache lookup first.
  - **Deep path (offline, before the demo)**: Exa search plus Context.dev batch extraction across the supplier list, Gemini Pro only for ambiguous cases. Results are stored as `inferred` with timestamps, then loaded into the snapshot.
- Streaming: FastAPI Server-Sent Events. Every agent step emits `{step, status, ms, source_url}`, so the UI shows progress rather than a spinner.
- Components: React frontend with a skeleton from the snapshot; FastAPI; Python agents; Context.dev SDK; Gemini; Valio mock client; a worker for the offline deep path.

## 3. Data model and key queries
- `company`, `site`, `supply_edge` as usual: `trust enum{inferred,claimed,agreed,audited}`, `confidence`, `visibility enum{private,aggregate,opted_in}`, `price_min/max` null unless published.
- `cache_entry(key text pk, value jsonb, source_url, sha256, fetched_at, ttl_s)`: keyed by URL + extraction schema version. Unchanged page hash means no LLM call.
- `llm_call(prompt_hash pk, model, in_tokens, out_tokens, cost_eur, latency_ms, result jsonb)`: rerunning an identical prompt costs nothing.
- `run_budget(run_id, context_calls, llm_calls, cost_eur, cap)`: hard stop at the cap.
- `evidence`, `audit_event` (hash chain), `risk_signal` as usual.
- **Trust and visibility**: DB trigger for trust transitions; buyer reads only through views `v_buyer_map`, `v_alternatives`, `v_industry_agg` (suppressed under 5).

Precomputed materialised views (refreshed on each edge or risk change, under 50 ms at demo scale):
```sql
CREATE MATERIALIZED VIEW up_closure AS
WITH RECURSIVE up(buyer, root, node, depth) AS (
  SELECT dst_company, src_company, src_company, 1 FROM supply_edge
  UNION ALL
  SELECT up.buyer, up.root, e.src_company, up.depth+1 FROM up
  JOIN supply_edge e ON e.dst_company = up.node WHERE up.depth < 4)
SELECT buyer, node, COUNT(DISTINCT root) AS paths FROM up GROUP BY buyer, node;
CREATE INDEX ON up_closure (buyer, node);

-- Hidden concentration: read from the view, not recomputed
SELECT node, paths FROM up_closure WHERE buyer = $buyer AND paths >= 2;

-- Alternatives, pre-sorted per category, filtered at read time
CREATE MATERIALIZED VIEW alt_index AS
SELECT a.category, a.company_id, a.price_min, a.lead_time_days, a.schemes
FROM v_alternatives a ORDER BY a.category, a.price_min NULLS LAST;

-- Blast radius: downstream closure of a failed supplier (depth-bounded, cached per supplier)
WITH RECURSIVE down(node, depth) AS (
  SELECT dst_company, 1 FROM supply_edge WHERE src_company = $failed
  UNION SELECT e.dst_company, down.depth+1 FROM down JOIN supply_edge e ON e.src_company = down.node WHERE down.depth < 5)
SELECT DISTINCT node FROM down;
```

## 4. Agents (discovery, monitoring, procurement)
Shared rules: every output is `{claim, source_url, snapshot_sha256, confidence}`; schema-constrained JSON; one retry; no write without evidence.
- **Discovery (deep, offline)**: Exa search by domain and date for each supplier, then Context.dev structured extraction (name, country, supplier mentions). Gemini Pro only when extraction confidence is under 0.6. Validation: two domains or one registry source; country matches. Output: `inferred` edges loaded into the snapshot before the demo.
- **Monitoring (fast, live)**: Context.dev monitor on the producer's news and registry pages, webhook to `/hooks/change`, plus a manual "Scan supplier" button that runs the same fast path. Cache check first: unchanged `sha256` returns the cached classification with no LLM call. Changed content: one Gemini Flash call, classifying type and severity. Output: `risk_signal` with the URL and the fetch time shown.
- **Procurement (fast, human-gated)**: reads `alt_index` (no SQL recomputation), keeps complete packs, and one Gemini Flash call writes the rationale citing evidence IDs. Streams the proposal. The approval-to-order path contains no LLM: approval writes the proposal hash, then a deterministic POST to Valio mock with `Idempotency-Key = proposal_id` (endpoint shape assumed). Partial availability falls back to the next alternative.

## 5. Risk engine
- Pure Python and SQL, no LLM in the scoring path; recalculated in under 100 ms on each event.
- Score = severity × confidence × recency decay (half-life 90 days). Company risk = max plus 0.2 × sum of the rest, capped at 1.
- **Regulatory**: expired certificate (0.9); sanctions name match (matching score); missing EUDR statement for soy or palm lines (0.8); missing CSDDD policy (0.5).
- **Concentration**: `up_closure` paths of 2 or more; severity scales with Valio volume share.
- **Geopolitical and live events**: monitor classifications from the cache, with a hand-set country table (labelled).
- **Price premium**: over 15% above the cheapest opted-in alternative, only when published.

## 6. Screens and graph view
1. **Supply map / graph**: Cytoscape, Valio centre. Direction arrows; trust colours (inferred dotted grey, claimed amber, agreed blue, audited green); red halo for open risk; dashed for unregistered.
2. **Latency bar**: a small status strip on every screen showing the last action's time and whether data came from snapshot, cache or live fetch, with the age of the data.
3. **Scan panel**: streamed steps with ms per step and the source URL for each.
4. **Risk alert**: evidence cards with URL, snapshot hash, fetch time.
5. **Alternatives and approval**: pre-sorted list from `alt_index`, price range (published only), rationale, approve or reject, order result.
6. **Audit trail** with "verify chain"; **supplier portal** for edge confirm and simulated auditor stamp.

## 7. Demo script (4 min)
- 0:00 Hotel login. Map loads from snapshot, under 1 s. Latency strip shows "snapshot, 0.4 s".
- 0:40 Click the dairy producer: concentration and expiry visible instantly from `up_closure` and the cache.
- 1:15 "Scan supplier": steps stream; Context.dev page fetch at about 3 s; URLs and timestamps appear; alert at about 8 s. Cached result is labelled if the live call fails.
- 2:00 Alternatives list, sorted from `alt_index`, opted-in only.
- 2:30 Proposal streams in under 4 s. Manager approves; Valio order returns under 2 s; audit row appears.
- 3:10 Supplier confirms the edge (claimed→agreed); auditor stamps (audited). Run cost shown: "3 live calls, 2 LLM calls, EUR 0.01".
- 3:40 Verify chain; aggregate suppressed under 5.

## 9. Judging-criteria mapping
- **Context.dev (15%)**: latency is measured and shown; fetch and monitor drive the alert; URLs and timestamps visible; "technical execution (latency and accuracy)" addressed directly.
- **Valio (30% demo, 20% need, 20% guardrails, 15% exceptions, 15% standards)**: reliable end-to-end order; deterministic order path and approval row; partial-availability fallback; idempotent order posting.
- **Feasibility (25%)**: one fast path, one deep path, no LLM in the order path, recorded backup.
- **Privacy (10%)**: buyer reads through views; aggregates under 5 suppressed.
- **Concreteness (10%)**: materialised views and closure queries above.
- **Side bounties**: Gemini Flash as the default model (cost); Aiven Postgres; CRACI; Codex only if used meaningfully. Skip Cala and Oxylabs.

## 10. Risks and cuts
- Cut order: Valkey (in-process cache instead); Exa deep path (use Context.dev batch only); webhooks (scheduled and manual scan kept); Gemini Pro (Flash everywhere); price premium; real auditor flow (button).
- Stale snapshot: every view shows its age; never presented as live.
- Context.dev latency or quota: cache, and a labelled recorded run as fallback.
- Gemini rate limits: cache hits and the `run_budget` cap prevent runaway calls.
- Materialised view refresh under load: refresh only on change and only for the demo buyer's rows.

## 11. Biggest weakness of this proposal
Precomputing and caching makes the "living network" partly staged, and judges may suspect the snapshot hides slow work. Flash-only extraction may be less accurate than a deep pass on messy pages. The cost and latency plumbing is invisible to judges, so it earns points only if the latency strip and run budget are shown clearly.

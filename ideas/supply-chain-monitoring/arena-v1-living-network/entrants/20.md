# Entrant 20: Tidewire (lens: network growth loop)

## 0. Bold bet
Every declared edge is an invitation, so the graph grows itself: a buyer naming a supplier creates a grey ghost node, Context.dev enriches it live, and the supplier claims its profile in one click and sees who already named it. We win on the most visible proof that the network is alive: judges watch the Valio graph grow while the hotel's risk alert fires.

## 1. Summary and name
**Tidewire**: a living supply-chain network where companies join by being named. A buyer declares suppliers and customers; unknown companies appear as ghost nodes, get enriched from the web, and receive a claim link showing who already named them. Claiming is free and reveals only edges that involve the claimant. Suppliers appear as alternatives only by opting in, so growth is driven by visibility, not spam.

## 2. Architecture and DB choice
- **Postgres 16 on Aiven** is the system of record: companies, edges, invitations, append-only `edge_event`. Reasons: recursive CTEs handle demo scale (under 5k nodes), `pg_trgm` gives fuzzy name matching, one DB to debug in 48h, and Aiven Runtime hosts the app.
- **ArcadeDB**: optional read-model for Cypher blast-radius queries, only if Sunday morning has slack. Off the critical path. Assumption: its Docker image runs on a laptop without setup days.
- **Growth feed**: Server-Sent Events on `/api/feed?after=<seq>`, polling `edge_event` every second. No Kafka. Aiven Valkey pub/sub is the upgrade path.
- **Components**: React + vis-network web app; Node/Express API; agent worker; Valio mock client; Context.dev and Gemini clients.

## 3. Data model and key queries
```sql
company(id uuid pk, name text, domain text unique null, country text, industry text,
  status text check (status in ('ghost','invited','registered','verified')),
  enrichment jsonb, source_urls text[], listing_opt_in bool default false)
edge(id uuid pk, from_id uuid, to_id uuid,          -- from = supplier, to = buyer
  trust text check (trust in ('inferred','claimed','agreed','audited')),
  confidence numeric null, sources jsonb, declared_by uuid, confirmed_by uuid null,
  audited_by text null, unique(from_id, to_id))
invitation(id uuid pk, company_id uuid, to_email text, token_hash text,
  invited_by uuid, status text, expires_at timestamptz)
edge_event(seq bigint identity pk, type text, company_id uuid, edge_id uuid,
  actor text, payload jsonb, created_at timestamptz default now())
```
- **Trust is monotonic**: `claimed` → `agreed` → `audited`. Edge rows hold the current level; `edge_event` keeps history.
- **Visibility is enforced in the API query layer**, not the UI. A viewer receives an edge only if its company is `from_id` or `to_id`. Risk warnings and aggregates are the only other outputs. Aggregates use `GROUP BY industry, supplier HAVING count(*) >= 5`.
- **Resolve** (on declaration): `SELECT id, status FROM company WHERE domain = $1 OR similarity(name, $2) > 0.7 LIMIT 1;`. No hit inserts a ghost.
- **Feed**: `SELECT * FROM edge_event WHERE seq > $1 ORDER BY seq LIMIT 200;`
- **Upstream traversal** (depth ≤ 4): recursive CTE over `edge` from the hotel's direct suppliers, following `to_id = node` and filtering `trust <> 'inferred' OR confidence >= 0.6`.
- **Hidden concentration**: `SELECT u.from_id AS upstream, array_agg(DISTINCT u.to_id) AS via, count(DISTINCT u.to_id) AS n FROM edge u WHERE u.to_id IN (SELECT from_id FROM edge WHERE to_id = $hotel) GROUP BY u.from_id HAVING count(DISTINCT u.to_id) >= 2;`
- **Alternatives**: `SELECT * FROM company WHERE listing_opt_in AND industry = $1` joined to published prices only.

## 4. Agents
Three agents, growth-focused, all writing to `edge_event`:
- **Discovery** (Gemini 2.5 Flash for extraction; Context.dev for data). Inputs: ghost nodes and registered domains. Tools: Context.dev company enrichment by domain, news search, structured extraction of "partners/customers" pages. Output: ghost nodes plus `inferred` edges with `confidence` and `source_urls`. Validation: show an edge only with at least one source URL and confidence ≥ 0.6; pre-fill an invite only with two or more sources. Human approval: discovered ghosts are never auto-invited. Invites go out only from the human-approved batch.
- **Monitoring**: Context.dev monitors on every registered domain, delivering webhooks to `/hooks/ctx`. A changed certifications or news page writes a `risk_signal` row and a feed event. For a reliable demo, a scripted trigger endpoint replays a recorded change.
- **Procurement**: proposes a switch on risk or premium; orders via the Valio mock only after manager approval. Alternatives come only from opted-in suppliers.
- **Job table**: `agent_job(id, kind, status, input, output, started_at)`, shown in the audit log.

## 5. Risk engine
Risks attach to edges, scored as `severity × confidence`. Ghost-supplier risks weigh at half. Detection:
- **Geopolitical**: country list plus Context.dev news keywords.
- **Compliance**: seeded sanctions list; missing or expired certificate when extraction finds no valid date.
- **Concentration**: the hidden-concentration query above.
- **Financial and live events**: news keywords (layoffs, insolvency, recall, strike) with source URLs. **Price premium**: only where prices are published.

## 6. Screens and graph view
1. **Claim landing** `/c/:token`: "Valio Aimo and Kestrel Hotels name you as a supplier." Shows only edges touching the claimant. Domain verification by magic link; the email shows in the UI, with no real send.
2. **Onboarding wizard** "Who do you buy from / sell to?": paste domains, accept discovery chips with source links, and watch a live preview graph on the right.
3. **Live network** (hero): Valio at centre, about 200 seeded nodes. New ghosts drop in grey and dashed; logos fill in as enrichment lands; edges draw in. Legend: solid = agreed, dotted = claimed, dashed = inferred, double = audited. Arrows run supplier → buyer. Red halo = open risk.
4. **Invite queue**: batch of ghosts with draft invite text, "Invite 3 companies" approval.
5. **Buyer map** (hotel, private): supply tree, risk card, opt-in alternatives with price ranges.
6. **Event log**: timeline of every growth, risk and order event with actor and source URL.

## 7. Demo script (4 min)
- **0:00** Live network, feed ticking. "This graph was alive before you arrived."
- **0:30** Hotel "Kestrel Hotels" (fictional) declares dairy supplier "Pohjola Dairy Co-op" (fictional). Grey ghost drops in; Context.dev fills country and logo in about 2 seconds, with source URL shown.
- **1:10** "Scan partners": discovery extracts real Finnish supplier names from a live partner page. They appear as `inferred` edges with confidence and URLs.
- **1:40** Switch to Pohjola's browser. Claim link shows "Kestrel and Valio name you." Verify domain, confirm edge: `claimed` → `agreed`, line goes solid.
- **2:15** Pohjola names its own farm supplier. Another ghost, another invite. Graph now spans four tiers.
- **2:40** Monitor webhook fires on Pohjola's certifications page. Red halo. Hotel risk card: two suppliers share one farm (concentration) and a certificate has expired.
- **3:05** Opt-in alternatives with price ranges. Procurement proposes a switch; manager approves; Valio mock order placed; log shows why.
- **3:40** Auditor stamps one edge `audited`; double line appears.
- **3:55** Close: "Every edge here was declared, confirmed, audited, or cited."

## 8. 48h build plan (4 engineers)

## 9. Judging-criteria mapping
- **Valio (30%)**: opt-in supplier pool feeds alternatives; approval gate before order; event log explains each action.
- **Feasibility (25%)**: one database, SSE, cuts defined in section 10.
- **Context.dev (15%)**: enrichment in the growth path, monitor webhook for real-time change, cited discovery URLs.
- **Trust and privacy (10%)**: invites show only the claimant's edges; monotonic trust; aggregates need five or more firms.
- **Side bounties**: Gemini extraction; Aiven Postgres and Runtime; CRACI in CI. Codex optional. Cala skipped.

## 10. Risks and cuts
- **Cut order**: ArcadeDB read-model → Gemini extraction (hand-written JSON fallback) → SSE (2-second polling) → monitor webhook (scripted trigger only).
- **Risks**: Context.dev latency or quota during the demo (pre-cache domains and label live calls with a timer); graph layout jitter with many nodes (freeze layout after the animation); venue Wi-Fi (run from a cached snapshot with a live toggle).

## 11. Biggest weakness of this proposal
The growth loop adds a lot of surface for 48 hours. If claim or onboarding breaks on stage, the story collapses to a static graph. Procurement and the Valio order path get the least polish, which costs points on the 30% criterion.

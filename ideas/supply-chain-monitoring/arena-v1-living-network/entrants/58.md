# Entrant 58: Registry-Anchored Network (lens: open company registries as ground truth)

## 0. Bold bet
Every node is anchored to an official identifier (Finnish Business ID from PRH/YTJ, a GLEIF LEI, or an OpenSanctions entity ID), so identity, legal status and sanctions screening come from registries, not from scraped text. Context.dev then finds the edges and the news, and each registry record carries a link to its source, so judges can check the ground truth themselves on stage.

## 1. Summary and name
- Name: **Anchorline**. Buyers see a supply map where every company is registry-verified. They get risk alerts, opt-in alternatives and published prices. Agents discover and monitor, and a manager approves each order before it goes to Valio's mock API.
- Stack: Node/TypeScript API (Fastify, SSE), Python workers for agents (Gemini, Context.dev SDK), React + Cytoscape.js, Aiven Postgres for all data, Valkey cache for registry responses, Aiven Runtime for hosting.
- Assumption: all registry access uses public endpoints. Bulk snapshots are used for the demo subset, so the live demo does not depend on API uptime.

## 2. Architecture and DB choice
- **Postgres on Aiven, not ArcadeDB.** Registry records are relational (one company, many identifiers, many snapshots, many sources). Upstream traversal is a recursive CTE capped at depth 4. Postgres is the lower-risk choice for 48 hours.
- Data flow:
  1. **Resolver** takes a name and domain, queries PRH (Finnish register, Business ID, status), GLEIF (LEI, legal name, parent relations) and OpenSanctions (match). Context.dev supplies the domain and enrichment.
  2. **Discovery** uses Context.dev search and scrape to find supply relations, then sends each counterparty to the resolver.
  3. **Edges** are written only when both endpoints have a resolved key. Edge confidence = relation evidence × identity score.
  4. **Monitoring** re-polls registry status and sanctions, and listens for Context.dev monitor webhooks.
  5. **Procurement** uses only resolved, active, sanctions-clear suppliers.
- Every registry response is stored as a snapshot with `source_url` and `fetched_at`, so every claim is traceable.
- Assumption: PRH open data returns name, Business ID, registration status and industrial code (TOL). GLEIF returns LEI, legal name, status and direct/ultimate parent relations where published. OpenSanctions match returns a score and entity ID. Verify each field in the Friday spike.

## 3. Data model and key queries
Tables:
- `company(id, name, domain, country, fi_business_id UNIQUE, lei UNIQUE, opensanctions_id, tol_code, registry_status, identity_score, registered, visible_alt, embedding)`
- `registry_snapshot(id, company_id, source PRH|GLEIF|OPENSANCTIONS|CONTEXT, external_id, fields jsonb, source_url, fetched_at)`
- `edge(id, supplier_id, buyer_id, trust trust_level, confidence, owner_id, visibility private|public, sources jsonb, supplier_confirmed, auditor_id, updated_at)`. `trust_level` is inferred < claimed < agreed < audited. A trigger blocks downgrades.
- `sanctions_hit(id, company_id, dataset, entity_id, score, status possible|dismissed|confirmed, reviewed_by)`
- `risk(id, company_id, type, score, confidence, evidence jsonb, observed_at)`
- `product(sku, supplier_id, name, price_min, price_max, price_published, certs jsonb, lead_time_days)`
- `audit_event(id, ts, actor, action, payload, prev_hash, hash)`

Privacy in the database: Postgres row-level security on `edge`: `USING (owner_id = current_setting('app.user_id') OR visibility = 'public')`. Aggregates come from a SECURITY DEFINER function that counts companies sharing a TOL code and suppresses groups under 5.

Key queries:
- **Upstream chain:**
```sql
WITH RECURSIVE up AS (
  SELECT supplier_id, buyer_id, trust, 1 AS depth, ARRAY[buyer_id] AS seen
  FROM edge WHERE buyer_id = $me
  UNION ALL
  SELECT e.supplier_id, e.buyer_id, e.trust, up.depth + 1, up.seen || e.buyer_id
  FROM edge e JOIN up ON e.buyer_id = up.supplier_id
  WHERE up.depth < 4 AND NOT e.buyer_id = ANY(up.seen)
) SELECT * FROM up;
```
- **Hidden shared upstream (registry ownership):** suppliers whose GLEIF ultimate parent is the same LEI, plus supply-edge overlap:
```sql
SELECT p.lei AS parent_lei, array_agg(DISTINCT c.name) AS direct_suppliers
FROM edge e JOIN company c ON c.id = e.supplier_id
JOIN registry_snapshot p ON p.company_id = c.id AND p.source = 'GLEIF'
WHERE e.buyer_id = $me
GROUP BY p.lei HAVING count(DISTINCT c.id) >= 2;
```
- **Blast radius:** recursive downstream walk from a failed supplier, returning affected buyers and hop count.
- **Alternatives:** `company` rows with `visible_alt=true`, same `tol_code` as the incumbent, `registry_status='active'`, no `sanctions_hit` with status `possible` or `confirmed`, and published prices, ordered by `embedding <=> $q`.

## 4. Agents
**Resolver (shared tool):** input is name and domain. Step 1: query PRH by name and city. Step 2: query GLEIF by name and country. Step 3: query OpenSanctions match with name, country and domain. Step 4: pick the best candidate by identity score (name similarity, city, domain agreement). Gemini chooses only between tied candidates and must give reasons. Output: a `company` row with keys, plus snapshots. Below 0.8 identity, the company stays unresolved and cannot carry a `visibility=public` edge.

**Discovery:** input is Valio's supplier list (40-supplier demo subset) and a seeded dairy list. Tools: Context.dev search, news and scrape with JSON schema (`supplies_to`, `product`, `source_url`). Gemini extracts relations. Validation: at least two source URLs, or one authoritative page plus a resolved counterparty. Output: `edge(trust=inferred, confidence, sources)`. Human approval is not required for inferred edges, but they cannot be used in procurement until a manager confirms them.

**Monitoring:** triggers are a 6-hourly cron, Context.dev monitor webhooks (`/hooks/context`), and PRH and GLEIF status diffs against snapshots. Each change writes a `risk` row. OpenSanctions is re-matched on every snapshot refresh. A new possible match opens a review item and does not auto-block.

**Procurement:** triggered by a risk ≥0.6 on a node in a buyer's chain, or a price premium above 15%. It finds alternatives, then Gemini drafts a proposal citing registry facts and URLs. The proposal waits for manager approval. On approval, it checks Valio availability and places the order through the Valio mock. Partial stock triggers a substitute from the next alternative. Every step writes an `audit_event`.

## 5. Risk engine
Score per type, with confidence. Registry evidence has priority over news.
- **Regulatory and sanctions:** confirmed match 1.0. Possible match 0.6 until reviewed (a dismissed match scores 0). Expired or missing certificate for a product in CSDDD or EUDR scope 0.5–0.8.
- **Financial health:** PRH status showing liquidation or bankruptcy 1.0 (assumption: status field carries this). GLEIF LEI lapsed 0.5. Context.dev news tags for layoffs 0.4, insolvency 0.7.
- **Concentration:** shared GLEIF parent among direct suppliers 0.6, plus shared supply-edge upstream count / 5.
- **Geopolitical:** country table snapshot plus Context.dev news in the last 30 days.
- **Live events:** recall, strike or outage tags from the Context.dev news monitor, 0.5–0.9.
- **Price premium:** premium / 0.3, only with published prices.
Upstream risk reaches buyers with 0.8 decay per hop, shown as "via tier-2".

## 9. Judging-criteria mapping
- **Valio (30/20/20/15/15):** approval gate before order; audit trail; exceptions (partial stock, sanctions review hold); open standards (public registry identifiers as keys, Business ID and LEI are open identifiers).
- **Context.dev:** search, scrape and monitors in the core flow; URLs on every inferred edge; webhooks for real-timeness; resolver turns web hits into verified nodes.
- **Trust and privacy:** RLS; monotonic trust; registry facts are public and carry no private map data; aggregates suppressed below 5.
- **Concreteness:** SQL on screen, registry panel fields, scoring rules.
- **Bounties:** Gemini (disambiguation, extraction, classification, rationale); Aiven (Postgres, Valkey, Runtime); CRACI (Action, SBOM); Codex (development). Cala is cut; its investor angle is a stretch goal only.

## 10. Risks and cuts
- **Cut order:** Cala, Oxylabs, Modal, Exa, Valkey (use in-memory cache), GLEIF parent lookup (keep the Finnish register), embeddings (use TOL-code filter), sanctions review queue (show results read-only).
- **Risks:** (1) Name matching produces false sanctions hits on stage. Mitigation: hits are always labelled "possible", are never auto-blocking, and the demo uses curated candidates. (2) Registry API outage during the demo. Mitigation: bulk snapshots for the demo subset. (3) Field assumptions wrong (PRH status, GLEIF parents). Mitigation: Friday spike; drop the field and keep the link. (4) Context.dev latency. Mitigation: pre-warm and cache. (5) Dataset licences for OpenSanctions. Assumption: hackathon use is fine; check before any public release.

## 11. Biggest weakness of this proposal
Registries anchor nodes and identities, but not supply relations. Edges still come from web scraping, so the "ground truth" pitch covers less of the graph than it sounds. Coverage is also uneven: PRH is Finland only, and GLEIF covers only firms that hold an LEI, which excludes many small suppliers. The resolver adds a visible step to the discovery flow and can fail or slow the live run.

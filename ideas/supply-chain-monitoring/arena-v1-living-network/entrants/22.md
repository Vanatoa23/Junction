# Entrant 22: Trellis, consent-scoped supply network (lens: Privacy engineering)

## 0. Bold bet
Visibility is enforced in Postgres (row-level security plus three audited SECURITY DEFINER functions), so no API handler, agent or LLM prompt can leak a private map by accident. Every buyer-facing aggregate passes a k>=10 gate, and upstream names appear only where the supplier has granted disclosure, which makes consent a live, demoable mechanic.

## 1. Summary and name
- Name: **Trellis** (supply networks grow along consented links).
- Companies declare buying and selling edges; the graph grows through invitations. Each company sees its own map, risk alerts about its exposure, peer-anonymised industry usage, opted-in alternatives and published prices only.
- Agents discover, monitor and propose switches. A human approves every order, which goes to the Valio mock API.
- Stack: TypeScript (Fastify API, React + Cytoscape.js), Postgres on Aiven, Gemini function-calling agents, Context.dev for live web data, Valio mock as a separate OpenAPI service.

## 2. Architecture and DB choice
- **Postgres (Aiven) only** for the demo. ArcadeDB stays out of the core: visibility rules would have to be re-implemented in a second engine, doubling the leak surface. Stretch only: a read-only ArcadeDB Cypher blast-radius view fed from already-filtered projections.
- Upstream traversal uses recursive CTEs to depth 4. The demo needs depth 2 to 3.
- Components: API (every read opens a transaction and runs `SET LOCAL app.viewer = $org`); agent worker (Gemini; each run uses a DB role bound to one org); Context.dev client; Valio mock; audit writer.
- Flow: request, JWT, org id, transaction-scoped setting, RLS, response. Every response writes an `access_audit` row.
- Assumption: Aiven Postgres supports RLS and pgcrypto (standard Postgres features).

## 3. Data model and key queries
- `company(id, name, kind[registered|unregistered], industry_code, country, alt_opt_in)`
- `edge(id, from_id, to_id, declared_by, trust_level[inferred|claimed|agreed|audited], confidence, source_urls jsonb)`
- `edge_confirmation(edge_id, org_id, role[declarer|counterparty|auditor], at)`. A trigger sets trust_level: both parties confirmed gives `agreed`, auditor gives `audited`. The app role has no UPDATE privilege on `trust_level`.
- `listing(supplier_id, product_id, price_min, price_max, published, alt_visible)`
- `disclosure_grant(grantor, grantee, scope[upstream_risk|alt], revoked_at)`
- `access_audit`: append-only (REVOKE UPDATE, DELETE), with prev_hash and hash for a chain.

Policies (deny by default; no policy means no rows):
```sql
CREATE POLICY party_read ON edge FOR SELECT
  USING (current_setting('app.viewer')::uuid IN (from_id, to_id));
CREATE POLICY listing_read ON listing FOR SELECT
  USING (published OR alt_visible AND supplier_id IN
         (SELECT id FROM company WHERE alt_opt_in) OR supplier_id = current_setting('app.viewer')::uuid);
```
A buyer never sees a supplier's upstream edges. That is enforced by policy, not by application code.

SECURITY DEFINER functions (the only code that bypasses RLS, each returning minimum output):
- `fn_exposure(viewer)`: for each direct supplier S, returns the risk signal and the upstream name only if `disclosure_grant(S -> viewer, 'upstream_risk')` exists. Otherwise it returns "input of S" with no name.
- `fn_shared_upstream(viewer)`: counts shared upstream inputs over granted edges only and sets `partial=true` when any contributing supplier has not granted. It under-reports by design.
- `fn_industry_usage(viewer, supplier)`: counts peers in the viewer's industry_code, excluding the viewer. Returns NULL when n < 10, otherwise a band `floor(n/5)*5 .. +4`. Results are cached 24h per (viewer, supplier) so differencing across queries is blunted.

Key queries:
- Own map: RLS-filtered recursive CTE over `edge`. Tier 2 comes only from `fn_exposure`.
- Blast radius: from a failed supplier, walk visible downstream edges to the viewer's own customers.
- Alternatives: `listing` filtered by product_id under RLS, with published price bands.

## 4. Agents (discovery, monitoring, procurement)
Common rules: each run gets a short-lived token bound to one org. Tools are typed functions only. Output is an `agent_proposal` row, never a direct write to `edge` or `orders`. Outbound queries carry public entity names only, never map data.
- **Discovery.** Inputs: public company names from Valio catalogue and news. Tools: Context.dev company enrichment, news search, structured scrape. Output: `inferred` edge with confidence and at least one source URL. Validation: reject without a URL; show only confidence >= 0.6; sanctions name match against a local CSV snapshot (assumption).
- **Monitoring.** Context.dev monitors on public pages and news for entities in the viewer's visible tree. Webhook if reachable, otherwise 60s polling. Output: `risk_signal(entity_id, type, severity, source_url)`. Signals are entity-level and carry no edge data.
- **Procurement.** Inputs: alert, `fn_exposure` result, opted-in listings, published prices, Valio catalogue. Tools: Valio `GET /products`, `GET /availability`, and `POST /orders`, the last only with an approval token. The token is HMAC-signed, expires in 5 minutes and is bound to the proposal hash. Every tool call and prompt hash is logged.

## 5. Risk engine
- Entity risks from public sources: geopolitical (country tables), sanctions (fuzzy match), regulatory (certification expiry, CSDDD and EUDR flags), financial and live events (Context.dev news keywords), price premium (published listings only).
- Exposure score per viewer: `entity_severity x 0.6^depth x confidence`, computed inside `fn_exposure`.
- Concentration: `fn_shared_upstream`, as above.
- Redaction gate: the alert-writing LLM receives only the function output. After generation, every named entity in the text must appear in the allowed set. Otherwise the alert is blocked and the block is logged.

## 6. Screens and graph view
1. Persona switcher (hotel, Valio, supplier, auditor).
2. My map: own suppliers and customers. Tier-2 nodes render as grey "hidden input" with a risk badge unless disclosed.
3. Alerts: cards with source URLs and a "why you see this" panel that names the rule and grant that allowed the row.
4. Alternatives: opted-in suppliers with a "published" price range badge.
5. Industry usage: band only, or an honest "suppressed (<10 peers)" state.
6. Proposal, approval, order receipt.
7. Audit log, including rows such as "14 rows hidden by policy".
8. Valio consent panel: toggle `upstream_risk` grants.

Graph encoding: arrow = direction; solid = agreed or audited, dashed = claimed, dotted = inferred; line width = confidence; node colour = max exposure; shield = audited.

## 7. Demo script (4 minutes)
- 0:00 Hotel logs in. Valio shows as an agreed supplier; its upstream appears as hidden inputs.
- 0:40 Open "why can't I see this?": the policy trace, then the audit log showing rows hidden by policy.
- 1:10 Risk alert on dairy producer D (live Context.dev fetch, source URL shown). Its name appears because Valio toggles the grant on a second screen. Toggling off masks it again, live.
- 1:50 Two opted-in dairy alternatives with published price ranges. Industry usage band "10-14 peers".
- 2:20 Procurement proposes a switch with price delta, lead time and certification. Manager approves. Order goes to the Valio mock; receipt shows the audit hash.
- 3:00 A supplier confirms an edge (claimed to agreed) on a second browser. An auditor stamps an edge audited.
- 3:30 Live discovery run finds a company from news, added as inferred with two URLs.
- 4:00 Leak-test harness: 40 endpoint checks across personas, all green.

## 9. Judging-criteria mapping
- Valio (30% demo): buyer reaches a mock order. Controls (20%): approval token, org-bound agent role, audit chain, "denied by policy" log. Exceptions (15%): out-of-stock triggers a substitution from opted-in listings. Open standards (15%): OpenAPI for the mock, JSON Schema for proposals.
- Context.dev (15%): live discovery and monitors inside the core flow, with source URLs.
- Trust and privacy (10%): explicit consent grants, k-gate, leak harness.
- Gemini bounty: agents. Aiven bounty: hosted Postgres with RLS. CRACI: CI from day one. Codex: used for leak-test cases and migrations, noted in commits. Cala: cut.

## 10. Risks and cuts
- Cut order: ArcadeDB stretch, then webhooks (polling only), then vector search (category match only), then hash chain (plain append-only table), then auditor UI (single button).
- RLS misconfiguration: mitigated by deny-by-default and the leak harness.
- SECURITY DEFINER functions: keep to three, reviewed line by line.
- LLM alert text leaking names: redaction gate, with a fallback template if blocked.
- Context.dev rate limits: cache fixtures and keep a pre-fetched backup.
- k=10 needs enough synthetic peers per industry bucket. Assumption: Valio data has industry codes.

## 11. Biggest weakness of this proposal
The privacy rules make the buyer's picture thinner. Without consent grants, tier 2 stays anonymous, so the demo's "wow" depends on Valio toggling a grant live, which is a fragile moment on stage. The design also rests on one engine's RLS correctness, and the redaction gate for LLM output is heuristic. This is a privacy-first prototype, not a graph-database showcase.

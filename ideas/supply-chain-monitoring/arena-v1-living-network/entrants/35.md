# Entrant 35: Explainable Exposure Engine (lens: Risk scoring rigor)

## 0. Bold bet
Every risk number is a deterministic, versioned formula over stored evidence rows, and the LLM only maps text to a fixed severity rubric, so any score can be re-derived and explained line by line. Risk moves upstream-to-downstream through explicit per-hop decay and trust multipliers, so a judge can see why a hotel is warned about a dairy producer it has never heard of, and why that warning is not critical.

## 1. Summary and name
- Name: **Fathom** (the depth of your supply chain, measured).
- Product: buyers see explainable risk on their suppliers and upstream chain, with propagation weighted by how far and how trusted each link is. Alerts lead to a Gemini-drafted procurement proposal that a manager approves before a Valio mock order.
- Prize stack: Valio (aim 1st), Context.dev (live scan feeds the factors), Gemini (severity classification), Aiven (Postgres, Valkey), Codex (golden-test suite), CRACI (CI with SBOM).

## 2. Architecture and DB choice
- **Postgres** (Aiven) for everything: graph as edge tables, propagation via recursive CTEs, evidence as rows. Few hundred nodes, so no graph engine needed. ArcadeDB rejected for 48h: no bounty, new query language.
- **Scoring service** (TypeScript, pure functions, no I/O) reads evidence and config, writes `node_risk` and `risk_factor`. Pure functions make it unit-testable.
- **Valkey**: caches the latest `node_risk` per node and the SSE channel for alerts.
- **Context.dev** monitors and news search write `signal` rows via webhook. Each signal triggers an incremental recompute of the affected node and its downstream nodes (depth ≤ 4).
- Hosting on Aiven Runtime (assumption: available); fallback is a laptop with a tunnel for webhooks.

## 3. Data model and key queries
- `scoring_config(version, risk_type, factor, weight, half_life_days, active)`. Every score stores the config version it used.
- `signal(id, node_id, type, url, domain, fetched_at, severity, quality, classifier_quote)`.
- `risk_factor(id, node_id, risk_type, factor, weight, severity, quality, recency, contribution, signal_id, config_version)`. Contribution = weight × severity × quality × recency.
- `node_risk(node_id, risk_type, own, computed_at, config_version)`, where own = 1 − Π(1 − contribution).
- `edge(src_id, dst_id, trust, confidence, share)`. Direction: src sells to dst. Trust and visibility enforced by RLS on `viewer_company`.
- `trust_event`, `approval`, `order`, `tool_call` as usual (trust transitions are append-only).

Decay and trust table (config, not code):
- Per-hop decay α = 0.85.
- Trust multiplier β: audited 1.0, agreed 0.9, claimed 0.75, inferred 0.6 × edge confidence.
- Recency = 0.5^(age_days / half_life). Half-lives: news 14 days, recall 60 days, sanctions and certification facts none (1.0).

Propagation, downstream from origin o to buyer b (max over paths per origin to avoid double counting shared roots):
```sql
WITH RECURSIVE prop(origin, node, depth, factor, path) AS (
  SELECT id, id, 0, 1.0::float, ARRAY[id] FROM company
  UNION ALL
  SELECT p.origin, e.dst_id, p.depth+1,
         p.factor * 0.85 * CASE e.trust
           WHEN 'audited' THEN 1.0 WHEN 'agreed' THEN 0.9
           WHEN 'claimed' THEN 0.75 ELSE 0.6 * e.confidence END,
         p.path || e.dst_id
  FROM prop p JOIN edge e ON e.src_id = p.node
  WHERE p.depth < 4 AND NOT e.dst_id = ANY(p.path))
SELECT p.origin, p.node AS buyer, max(p.factor) AS best_factor
FROM prop p WHERE p.node = $buyer GROUP BY p.origin, p.node;
```
Buyer exposure from origin o: own(o) × best_factor. Buyer aggregate: 1 − Π_o(1 − exposure_o). Equivalent in TypeScript for the scoring service; the SQL is used in the explain endpoint and the golden tests.

Concentration (buyer-level, a separate risk type):
```sql
SELECT r.root, count(DISTINCT s.src_id) AS k
FROM edge s JOIN ... -- direct dairy suppliers of $supplier
```
Expressed as: for supplier S, group its upstream reach (depth ≤ 3) by root; for roots with k ≥ 2 direct suppliers, factor = 0.9 × min(1, (k−1)/2) × own_any(root).

## 4. Agents (discovery, monitoring, procurement)
All three use **Gemini** via function calling; Gemini never outputs a score.
- **Discovery**: tools `contextdev.companyEnrich`, `contextdev.newsSearch`, `contextdev.extract(url, schema)`. Output candidate `inferred` edges with confidence = source quality × name-match check on the source text. Reject edges without a source URL containing both names. Cap confidence at 0.9.
- **Monitoring**: Context.dev monitors and webhooks on supplier domains and news queries. On change, `extract` pulls certifications, recall notices and status. Gemini assigns a severity from a rubric with anchors (0.0 none, 0.3 mention, 0.6 operational impact, 0.9 official recall or sanction) and must return the supporting quote. Quote must appear verbatim in the fetched text, otherwise the signal is dropped.
- **Procurement**: triggered when a node's exposure ≥ 0.6, or a price premium > 10% over published opted-in alternatives. Tools `valio.productLookup`, `valio.availability`, `valio.quote`, `valio.substitutions` (assumption: quote and order endpoints exist in the mock). Output: proposal with quote ID, `quote_hash`, rationale and citations to factor IDs.
- Guardrails: €2,000 spend cap; opted-in suppliers only; quote valid 10 minutes; no order without an approval whose `quote_hash` matches. Every tool call writes `tool_call`.

## 5. Risk engine
Five intrinsic types, one derived type. Each factor is a row, so the UI can print its arithmetic.
- **Geopolitical**: country index from seed (weight 0.3, severity = index/100, quality 1.0); conflict or trade-restriction news (weight 0.6, rubric severity, quality from source).
- **Regulatory**: sanctions exact match (weight 1.0, severity 1.0), fuzzy match (severity = similarity, threshold 0.92; assumption: EU consolidated list loaded at build); certification expired (weight 0.5); EUDR commodity without geolocation certificate (weight 0.4); CSDDD flag without due-diligence statement (weight 0.2).
- **Financial**: insolvency news (weight 0.9), layoffs news (weight 0.4).
- **Live events**: recall (weight 0.9), strike (0.5), outage (0.4), negative news (0.25).
- **Concentration** (derived): 0.9 × min(1, (k−1)/2) × own(root), where k is the number of a supplier's direct suppliers that share the root. Concentration amplifies a risky root and is zero for a healthy root.
- **Price premium** (not in `own`): premium = (p − p_alt)/p_alt, score = min(1, premium/0.25). Reported as its own badge.
- Quality of a source: official registry or recall agency 1.0; company's own page 0.8; news on two or more domains 0.8; single news item 0.5; LLM inference only 0.3.
- Bands: info < 0.3, warn 0.3–0.6, critical ≥ 0.6. Alerts require at least one factor row, so no evidence means no alert.

Worked example (demo numbers):
- Dairy producer D: recall, severity 0.9, quality 0.9 (official notice), recency 0.87 (2 days). Contribution 0.9 × 0.9 × 0.87 = 0.70 → own(D) = 0.70, critical.
- D sells to processor A with edge `inferred`, confidence 0.8 (factor 0.85 × 0.48 = 0.41). A sells to Valio (`agreed`, factor 0.77). Valio sells to the hotel (`agreed`, factor 0.77).
- Hotel exposure from D = 0.70 × 0.41 × 0.77 × 0.77 ≈ 0.17, watch band, with the path shown.
- Valio's dairy concentration: k = 3 processors share D, so 0.9 × 1.0 × 0.70 = 0.63, critical. This is the alert the hotel sees, and it names D as root.

## 6. Screens and graph view
- **Supply map**: arrows upstream to downstream. Edge style by trust (dashed inferred with confidence label, solid claimed, thick agreed, double audited). Node colour = max band of own and exposure. Upstream beyond tier one shows as risk path only.
- **Risk drawer** (the rigour showcase): table of factors per type with weight × severity × quality × recency = contribution, the config version, the source URL with fetch time, and the classifier quote.
- **Exposure path view**: path from root to hotel with each factor, trust label and multiplier.
- **Alternatives**: opted-in suppliers, published price range, peer usage aggregate (k ≥ 5).
- **Proposal**: current vs proposal, guardrail checklist, Approve or Reject.
- **Audit timeline**: tool calls, sources, approval, order ID.
- **Supplier and auditor views**: confirm edges (claimed → agreed); stamp audited.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards)**: order via mock; alternatives and premium badge; approval bound to quote hash; substitutions and escalation; OpenAPI client and JSON Schema proposals.
- **Context.dev**: live scan feeds factors with URLs; monitor webhooks trigger incremental recompute (real-timeness); timings shown.
- **Gemini (€4k)**: severity classification with rubric and verbatim quote check, plus procurement function calling.
- **Aiven (€1k)**: Postgres with RLS, Valkey cache and pub/sub, Runtime hosting.
- **CRACI**: GitHub Actions on CRACI runners, CycloneDX SBOM and vulnerability scan.
- **Codex**: scoring golden tests and config validation, logged in PR descriptions.
- **Concreteness and trust model**: SQL above, factor tables, per-origin dedupe prevents double counting, visibility at the buyer level.

## 10. Risks and cuts
- Cut first: Cala (not in this design), then the price-premium badge, then discovery auto-invites (seed manually), then SSE (poll every 5 s).
- Never cut: deterministic factor rows, the live scan with URLs, the approval gate, and the concentration alert.
- Risks: decay constants look arbitrary to judges (mitigate: document as calibrated config, show sensitivity); webhook reachability; rubric anchors ignored by Gemini (quote check drops them); RLS leaks.

## 11. Biggest weakness of this proposal (be honest)
The constants (α = 0.85, β table, concentration weight 0.9) are judgement calls, not calibrated against outcomes, and a sharp judge can challenge them. The demo's critical alert depends on the concentration weight, so it is partly a design choice shown on screen rather than an empirical result. Also, the scoring stack is less visually flashy than a graph-first build.

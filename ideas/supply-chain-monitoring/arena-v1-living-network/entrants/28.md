# Entrant 28: Relay, one TypeScript app that ships in a day (lens: TypeScript monolith)

## 0. Bold bet
One Next.js repo, one database, one deploy, and every agent is a Vercel AI SDK tool loop, so the team spends Saturday on the supply graph and the demo rather than on infrastructure. A working, rehearsed flow beats a distributed design that breaks on stage.

## 1. Summary and name
- **Relay**: a living supply-chain network where the hotel chain sees its supply map, gets a live risk alert on an upstream dairy producer, compares opted-in alternatives with published price ranges, approves a procurement agent's switch, and sees the Valio mock order and its audit trail.
- Name rationale: relay passes a signal up the chain, which is what the risk alerts do.

## 2. Architecture and DB choice
- **Stack:** Next.js (App Router, TypeScript), Server Actions for UI mutations, Route Handlers for webhooks and streaming, Drizzle ORM, Zod for every boundary, Tailwind plus shadcn/ui, Cytoscape.js for the graph.
- **Agents:** Vercel AI SDK (`streamText`, `generateObject`, tools) with Gemini (`gemini-2.5-flash`, assumed model id; verify on day one).
- **Database: Postgres on Aiven only.** Recursive CTEs cover upstream traversal at 3 to 4 tiers, and one database keeps transactions simple. ArcadeDB is not used; it adds a second store and a sync problem with no demo payoff within 48h. Stretch only: a Cypher blast-radius screen if time allows.
- **Valkey on Aiven** for caching Context.dev responses (with as-of timestamps) and the agent run lock.
- **Hosting:** Vercel (one deploy, preview per PR). Assumption: Aiven Postgres is reachable from Vercel over TLS.
- **Scheduling:** Vercel cron hits `/api/cron/monitor` every few minutes. Context.dev monitors post to `/api/webhooks/contextdev`. Both write `risk_signals` rows.
- **Repo layout:** `app/` (pages, actions, route handlers), `lib/db` (schema, queries), `lib/visibility.ts`, `lib/agents/` (discovery, monitor, procurement), `lib/risk/`, `lib/valio/` (mock client), `scripts/seed.ts`.

## 3. Data model and key queries
- `companies(id, name, country, registered bool, sanctions_hit, industry)`
- `edges(id, from_id, to_id, kind='buys_from', trust enum(inferred, claimed, agreed, audited), confidence numeric, sources jsonb, confirmed_from bool, confirmed_to bool, audited_by, created_by_agent)`
- `products(id, company_id, category, price_min, price_max, published bool, delivery_days)`
- `optins(company_id, category)` for alternatives visible to buyers.
- `risk_signals(id, company_id, rule_id, severity, sources jsonb, as_of)`
- `orders(id, buyer_id, product_id, qty, status enum(proposed, approved, placed, rejected, partial), payload_hash, approved_by)`
- `audit_events(id, ts, actor, action, payload jsonb)`, insert-only by convention.
- **Visibility** lives in one TypeScript function, `visibleGraph(viewerId)`, which is the only path to graph data for UI and agents. Buyers get their own edges, risk rows for suppliers and upstream, opted-in alternatives, published prices, and aggregates computed in SQL with `HAVING count(*) >= 5`. Other companies' edges never leave the function. Unit-tested with three fixtures.
- **Upstream traversal:**
  `WITH RECURSIVE up(id, depth) AS (SELECT from_id, 1 FROM edges WHERE to_id = $1 UNION SELECT e.from_id, up.depth+1 FROM edges e JOIN up ON e.to_id = up.id WHERE up.depth < 4) SELECT * FROM up;`
- **Hidden concentration:** join `up` to direct suppliers, `GROUP BY upstream_id HAVING count(DISTINCT direct_supplier) >= 2`.
- **Blast radius:** same CTE downstream from a failed supplier, counting buyers reached.
- **Alternatives:** `SELECT p.* FROM products p JOIN optins o USING (company_id) WHERE p.category = $cat AND p.published ORDER BY price_min`.

## 4. Agents (discovery, monitoring, procurement)
Each agent is one `streamText` call with a small toolset and `stopWhen: stepCountIs(6)`. Tools are plain TypeScript functions with Zod inputs.
- **Discovery.** Tools: `contextSearchNews(query)`, `contextEnrich(domain)`, `upsertInferredEdge(...)`. Prompt asks for company name, direct supplier, and evidence URLs. Output validated with `generateObject` against an `InferredEdge` Zod schema. Validation: at least two source URLs, the company name must appear in fetched page text, and confidence is capped at 0.8 for single-source. Writes only `inferred` edges. The UI run console streams each tool call with its URL.
- **Monitoring.** Cron or webhook calls `monitorCompany(id)`. Context.dev change events become `risk_signals` with source URLs. The agent summarises with `generateText` into one sentence; it never edits edges.
- **Procurement.** Tools: `listAlternatives(productId)` (visible only), `proposeSwitch(...)`, which inserts an `orders` row with `status='proposed'` and an audit event. There is no tool that calls Valio. Approval is a Server Action, `approveOrder(orderId)`, that checks the manager role, calls the Valio mock `POST /orders` with an idempotency key, and records `placed` or `partial`.
- Assumption: Valio mock exposes product, availability and order endpoints as described in the brief; confirm payload shape in the first hour.

## 5. Risk engine
TypeScript rule modules, each returning `{rule_id, severity, score, sources[], as_of}`:
- `sanctions`: name match against a seeded sanctions list; hit is critical.
- `regulatory`: certificate expiry dates in product data; CSDDD and EUDR flags from a seeded country and commodity table.
- `geopolitical`: country score table weighted by spend.
- `concentration`: the upstream CTE above.
- `live_events`: Context.dev news search with keyword rules (recall, strike, insolvency), each with a URL.
- `financial`: Context.dev company enrichment fields such as funding and headcount change.
- `price_premium`: only when published alternatives exist; premium = price / cheapest published − 1.
Gemini writes the explanation text only; scores are deterministic and unit-tested.

## 6. Screens and graph view
- **Login:** persona switch (hotel buyer, Valio manager, supplier, auditor). Seeded accounts.
- **Supply map:** Cytoscape graph with arrows for direction, dashed for inferred, solid for agreed, double line for audited, red border for open risk. Click an edge for confidence and sources.
- **Risk feed:** cards with rule ID, severity, source link and as-of time.
- **Alternatives:** table with price range, delivery days, opt-in badge.
- **Agent run console:** live stream of tool calls and URLs.
- **Approvals:** proposed switch, price delta, policy reason, approve button.
- **Audit log:** filterable table of audit events.
- **Supplier and auditor actions:** confirm an edge (claimed to agreed) and stamp audited.

## 7. Demo script (4 min)
- 0:00–0:25 Hotel login; supply map shows only its own chain and aggregates.
- 0:25–1:00 Run Discovery live: console streams Context.dev calls with URLs; new inferred supplier appears with confidence.
- 1:00–1:35 Risk feed alerts on upstream dairy producer; open source link.
- 1:35–2:10 Alternatives with price ranges; a non-opted-in supplier is absent.
- 2:10–2:45 Procurement proposes switch; manager approves; Valio mock order placed.
- 2:45–3:10 Partial availability returns; substitution proposed and approved.
- 3:10–3:40 Supplier confirms edge (claimed to agreed); auditor stamps audited.
- 3:40–4:00 Audit log replay; close on the full loop.
- Fallback: recorded video of the same run.

## 9. Judging-criteria mapping
- Valio end-to-end (30%): request, human approval, mock order, partial and substitution path.
- Buyer need (20%): risk, alternatives and a switch in one screen.
- Guardrails and auditability (20%): approval as the only order path, audit events, source URLs.
- Exceptions (15%): partial availability re-enters the flow.
- Open standards and production path (15%): Zod-typed contracts, idempotency keys, Postgres.
- Context.dev (15%): live discovery and monitor webhook with URLs and as-of times.
- Trust and privacy (10%): single visibility function, aggregates with minimum group size.
- Side bounties: Gemini (agents), Aiven (Postgres and Valkey), CRACI (CI and SBOM, near-zero effort), Codex if used meaningfully in development.

## 10. Risks and cuts
- Cut first: ArcadeDB, Cala, Modal, Oxylabs, Exa, Websets.
- Context.dev latency or rate limits in the live run. Mitigation: Valkey cache with as-of time, and a warm run before the pitch.
- Vercel serverless timeouts for long agent runs. Mitigation: cap at six steps; stream results.
- Monolith coupling makes one bug block everyone. Mitigation: each lib module has its own tests and can be stubbed.

## 11. Biggest weakness of this proposal (be honest)
Agents run inside request handlers, so there is no durable job queue. A deploy or timeout mid-run loses the run, and the approval path depends on a single in-process check rather than a formal policy layer. The graph is also plain Postgres, which underuses the graph database the brief highlights.

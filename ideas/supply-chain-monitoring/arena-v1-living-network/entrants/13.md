# Entrant 13: Chainglass (lens: demo storytelling)

## 0. Bold bet
We write the 4-minute pitch first and let every screen, edge and API call exist only to serve a beat in it, so the system is exactly as big as the story. The one live element is a real Context.dev news pull that paints a new red risk node onto the hotel's map while the judges watch, not a background job they have to trust.

## 1. Summary and name
- **Chainglass**: a hotel buyer looks through its supplier glass one tier deeper and finds the risk before it reaches the kitchen.
- Story: Hotel chain "Pohjan Hotellit" (dummy) buys dairy through Valio Aimo. Its map shows 5 direct suppliers. Live discovery finds that 3 of them share one upstream milk-powder plant. A strike notice arrives. The procurement agent proposes a switch to an opted-in alternative at a published price. A manager approves. The order goes through the Valio mock API. Everything is logged.
- Scope rule: if a feature is not in the 4-minute script, it is cut.

## 2. Architecture and DB choice
- **DB: Postgres (Aiven managed) only.** Use recursive CTEs for upstream traversal, `pgvector` for alternative search (assumption: Aiven Postgres has pgvector enabled; check on Friday, fallback is a precomputed category-embedding column), and a JSONB column for sources. ArcadeDB is rejected for 48h: it adds a second store and a new query language for no demo beat we cannot do in SQL. Mention it as the production-path story only.
- **Stack**: one TypeScript monorepo. Fastify API, Postgres, a worker process for agents, React + Vite + Cytoscape.js for the graph. Gemini (function calling) for agent reasoning and text extraction.
- **Components**: web app → API (auth as seeded personas, no real auth) → Postgres. Agent worker polls a `jobs` table (no Kafka). Context.dev is called from the worker, with a webhook endpoint for monitors if time allows, otherwise polling every 60s.
- **Event log**: one `audit_events` table, append-only, each row storing a hash of the previous row. Cheap and credible for the "auditability" criterion.

## 3. Data model and key queries
- `company(id, name, country, nace, registered bool, opted_in_alt bool, embedding vector, is_dummy bool)`
- `product(id, company_id, sku, name, category, price_public numeric null, price_range_public jsonb null)`
- `supplies(id, from_id, to_id, product_id null, trust enum[inferred|claimed|agreed|audited], confidence numeric null, sources jsonb, declared_by, confirmed_by_from bool, confirmed_by_to bool, audited_by null)`
- `risk_signal(id, company_id, type, severity, confidence, source_url, detected_at, status)`
- `audit_events(id, at, actor, action, payload jsonb, prev_hash, hash)`
- **Trust rule**: trust is derived, not typed. `claimed` if one side declared; `agreed` if both flags true; `audited` if `audited_by` set; `inferred` if `declared_by` is the agent. A trigger recomputes it.
- **Visibility rule**: a single SQL view `v_visible_edges(viewer)`. A company sees its own edges, plus the upstream chain only for risk signals, plus aggregates from `v_industry_usage` (grouped, minimum cohort of 5), plus alternatives where `opted_in_alt` and prices where `price_public` is not null. Every API route reads through this view. No route queries `supplies` directly.
- **Upstream traversal**:
  `WITH RECURSIVE up AS (SELECT from_id, to_id, 1 d FROM supplies WHERE to_id = $valio UNION ALL SELECT s.from_id, s.to_id, up.d+1 FROM supplies s JOIN up ON s.to_id = up.from_id WHERE up.d < 4) SELECT * FROM up;`
- **Hidden concentration**: `SELECT p.from_id, count(DISTINCT d.from_id) n FROM up p JOIN supplies d ON d.to_id = $buyer_direct ... GROUP BY p.from_id HAVING count(DISTINCT d.from_id) >= 2;`
- **Blast radius**: recursive downstream from a failed node, joined to `product` rows the buyer orders.
- **Alternatives**: `SELECT id FROM company WHERE opted_in_alt AND category = $cat ORDER BY embedding <=> $ref LIMIT 5`, then filter to published price ranges.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery (live, the wow)**: input is a company name or a Valio supplier list. Tools: Context.dev company enrichment and news search. Output: candidate `inferred` edges with `confidence` and `sources` (URLs). Validation: Gemini must quote a sentence from a source URL; an edge without a quoted source is dropped. Human sees it as a suggestion, not an edge, until the hotel confirms.
- **Monitoring**: input is each registered and inferred company. Tool: Context.dev news search with a 60s poll (webhook monitor only if spare time). Output: `risk_signal` rows. Validation: severity and confidence from Gemini, with the source URL required.
- **Procurement**: input is a risk signal plus the buyer's SKUs. Tools (assumed Valio mock endpoints, labelled as assumptions): `GET /products/search`, `GET /prices`, `GET /availability`, `POST /orders`. Output: a switch proposal (SKU, from, to, price delta, lead time, certificate match). It never calls `POST /orders` until a `proposal.approved` row exists. Exception path: partial availability returns a substitution proposal, which needs its own approval.

## 5. Risk engine
- **Concentration**: deterministic SQL from section 3. No LLM. Score = number of direct suppliers sharing the upstream node, weighted by SKU count.
- **Live events**: Context.dev news search on each upstream company name, Gemini classifies to strike, recall, outage or negative news. Severity from rules, confidence from the model.
- **Regulatory**: sanctions and EUDR flags come from a seeded dummy list, labelled as such. No live sanctions claim.
- **Financial health**: one scored signal from Context.dev company enrichment (layoffs or insolvency keywords). Shown only if it is in the script.
- **Geopolitical and price premium**: seeded for the demo. Price premium is computed from published prices only.

## 6. Screens and graph view
- **Map (default)**: Cytoscape graph centred on Pohjan Hotellit. Edge colour = trust level (dashed grey inferred, solid blue claimed, solid green agreed, double-line gold audited). Node border red = active risk. Arrows point to the buyer. Upstream nodes are visible only as risk nodes, with no edge to a private customer.
- **Risk card**: source URLs, confidence, blast radius (SKUs and dollars).
- **Alternatives**: opted-in suppliers, price range bars, and the industry aggregate ("used by 38% of 40 peers").
- **Approval**: proposal diff, "Approve" and "Reject" buttons. Approving writes the audit row first, then calls the order.
- **Audit log**: the timeline with hash chain indicator.
- **Supplier view**: a second login (dummy supplier). Shows "Confirm edge" button, which flips `claimed` to `agreed`.
- **Auditor view**: stamp button, which sets `audited`.

## 7. Demo script (timed beats)
- **0:00 Hook (20s)**: Slide of the Valio Aimo graph with one visible tier. "Who is behind your milk?"
- **0:20 Login (30s)**: Log in as Pohjan Hotellit. Map shows 5 direct suppliers, all green.
- **0:50 Live pull (40s)**: Click "Discover upstream". The worker calls Context.dev live. A new dashed node appears with source URLs visible on screen. Tension: a rival dairy co-op is named in a strike article.
- **1:30 The reveal (40s)**: Hidden concentration. Three suppliers turn red-bordered. Their shared upstream plant "Maitokaari Oy" (dummy) lights up. Risk card shows the strike source, blast radius of 14 SKUs.
- **2:10 Alternatives (30s)**: Procurement agent lists 3 opted-in alternatives with price ranges. Industry aggregate shown. Non-opted-in suppliers are invisible, which we say out loud.
- **2:40 Approval (40s)**: Agent proposal. Manager clicks Approve. Order posts to Valio mock API, confirmation number returns.
- **3:20 Trust (30s)**: Switch to supplier view, confirm edge (claimed to agreed). Switch to auditor, stamp (agreed to audited). Map updates live.
- **3:50 Close (10s)**: Open audit log. "Every step traceable."

## 9. Judging-criteria mapping
- **Valio (30% + 20% + 20% + 15% + 15%)**: Beats 2 to 5 are request → approval → order with fixed prices. Audit log at beat 7 covers auditability. Substitution exception is in the script as a rehearsed side branch. Open standards claim: REST plus JSON, no proprietary schema.
- **Context.dev (15%)**: Live pull at beat 3 with source URLs. Monitoring poll shows real-timeness. Structured enrichment in risk scoring.
- **Trust and privacy (10%)**: Trust and visibility are enforced in the view. Beat 4 shows the hidden-to-buyer rule on screen.
- **Concreteness (10%)**: Schema and queries above are the actual code.
- **Side bounties**: Gemini (main LLM, beat 3). Aiven (managed Postgres with pgvector, beat 4). Codex as a dev tool, logged in the README. CRACI in CI on day one, near-zero effort.

## 10. Risks and cuts
- **Cut first**: geopolitical scoring, financial health, price premium beyond published ranges, webhooks, Cala, ArcadeDB.
- **Risk 1**: Context.dev live call fails on stage. Mitigation: cache a real response from Friday night, show the cached one labelled "cached 14:02" if the live call fails. This is disclosed on screen, not hidden.
- **Risk 2**: Valio mock API shape differs from our assumption. Mitigation: a thin adapter, and a local stub that mirrors the assumed shape.
- **Risk 3**: Gemini tool loop is slow or flaky. Mitigation: deterministic SQL for the concentration result, and Gemini only for classification.
- **Risk 4**: Scope creep into the map. Mitigation: a fixed 4-minute script that the team rehearses from Saturday.

## 11. Biggest weakness of this proposal (be honest)
The story is built around one dummy hotel and one planted upstream plant. A judge who tests the product with their own company will find almost nothing, which hurts the "survives judges trying it" requirement. The live pull is also the single point of failure for the wow moment, and the cache fallback weakens the claim that it was live.

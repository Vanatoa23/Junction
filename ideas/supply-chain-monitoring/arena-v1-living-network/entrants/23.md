# Entrant 23: Breakfast Board (lens: hotel chain buyer deep-dive)

## 0. Bold bet
Most entrants will show a supplier graph and attach a buyer afterwards. We start from the buyer's week: six hotels, weekly pars, menu cycles and 05:30 kitchen delivery windows, and translate every graph fact into "which breakfast item, which hotel, by when". That makes the risk alert and the one-click approval read like real procurement work, which scores the 30% Valio fit and the buyer-need points.

## 1. Summary and name
- Name: **Breakfast Board**.
- A hotel-chain procurement manager logs in and sees a dish-first view: which menu items use which Valio products, which supplier and upstream dairy producer sit behind each product, and which hotels run short if a risk lands. Agents watch for risks, propose substitutes that fit the delivery window and price ceiling, and place the Valio order only after one human approval.
- Assumptions (labelled): hotel menus, pars and windows are seeded synthetic data. The Valio mock API exposes product, price, availability, lead time and substitution fields. We confirm this on Friday in the first hour.

## 2. Architecture and DB choice
- Components: React web app (buyer UI, plus a supplier-confirm page for phone demo) → Node/TypeScript API → agent worker (Gemini with tool calls) → Valio mock client → Context.dev client (discovery, monitors, news).
- Store: **Postgres** (Aiven managed, side bounty) for everything transactional: pars, menus, windows, visibility flags, proposals, orders, audit log. Graph queries use recursive CTEs over an edge table.
- ArcadeDB: stretch only. Adopt it only if the Docker image runs in under an hour; otherwise it is cut. Reason: the buyer screens need relational truth (pars, windows, approvals) far more than deep traversal, and a hybrid doubles the demo failure surface.
- Live data: Context.dev monitors POST webhooks to `/hooks/context`, exposed through a tunnel. Fallback is a "Scan now" button that calls Context.dev directly, so the live beat never depends on the tunnel.

## 3. Data model and key queries
- Nodes: `Company` (registered | unregistered | inferred), `Site` (hotel), `Menu`, `Dish`, `Ingredient`, `Product` (Valio SKU), `Producer` (upstream farm or dairy).
- Edges: `SUPPLIES {trust, confidence, sources[], visible}` between companies; `USES {qty_per_cover}` Dish→Ingredient; `FULFILLED_BY` Ingredient→Product; `MADE_BY` Product→Producer; `PAR {weekly_qty}` Site→Product; `WINDOW {days, open, cutoff}` Site→Supplier.
- Trust is a column on every edge. `agreed` requires both company IDs to confirm. `audited` requires an auditor-account stamp row.
- Visibility is enforced by role views. Buyer sees: risk rows, aggregate counts, opted-in alternatives (`supplier.opted_in = true`) and published prices only (`price_published = true`). A hotel's pars and menus are never exposed to other companies.
- Key queries:
  - Upstream: `WITH RECURSIVE up AS (SELECT ... FROM edges WHERE dst = :product AND kind='MADE_BY' UNION ALL ... depth <= 4)`.
  - Hidden concentration: group the buyer's direct suppliers by upstream `Producer`, flag producers with `count(distinct supplier) >= 2`.
  - Blast radius: `Producer P` → Products → Ingredients → Dishes → `PAR` rows, summed per hotel.
  - Alternatives: `Product` with same `ingredient_class`, `lactose_free` matching, `opted_in` supplier, published price, `lead_time <= window.cutoff`, ordered by price.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery**. Input: Valio dairy catalogue. Tools: Context.dev company enrichment and news search (Exa optional). Output: inferred `Producer` nodes and `SUPPLIES` edges written as `inferred`, each with confidence and two source URLs. Edges with fewer than two sources are dropped. No approval needed to view, but the UI badges them as inferred.
- **Monitoring**. Input: all `Producer` and dairy-supplier companies. Tools: Context.dev monitors on producer pages and news. Output: `risk_signal` rows (type, severity 1–5, source URL, timestamp). Cron every 15 minutes in the demo.
- **Procurement**. Input: a risk signal plus site pars, windows and menus. Steps: find alternatives (query above), compute 7-day quantity per site, check premium against ceiling, write a draft `proposal` with one reason per line. It never submits. On approval it calls the Valio mock order endpoint with an idempotency key and logs every step.
- Exceptions handled: partial availability becomes a substitute line with a reason; a missed delivery window becomes an alternative day.

## 5. Risk engine
- Score = severity × reach × urgency.
  - Severity (1–5) from signal type: recall 5, sanction 5, insolvency 4, strike 3, news 2.
  - Reach: share of the chain's weekly dairy par that passes through the affected producer, across hotels.
  - Urgency: days until stock-out (on-hand ÷ daily par) compared with supplier lead time. Stock-out before lead time is red.
- Sources by type:
  - Geopolitical: country-risk table plus Context.dev news search.
  - Regulatory: sanctions list (CSV import), certificate expiry dates on product documents. CSDDD and EUDR flags are seeded attributes (assumption).
  - Concentration: computed from section 3.
  - Financial: news search for layoffs or insolvency, Context.dev company fields.
  - Live events: recall and strike news from monitors.
  - Price premium: published prices only.
- Each risk card shows the top three source URLs and one plain sentence: "Yogurt bowl at 3 hotels is at risk within 9 days."

## 6. Screens and graph view
1. **Week board** (home): dairy items × six hotels, coloured by cover count, with a risk banner.
2. **Risk alert**: Producer → Product → Dish → hotels affected, source URLs, "Ask procurement agent".
3. **Alternatives**: supplier, trust badge, opted-in tick, published price range against current price, lead time against window, lactose-free flag.
4. **Approval sheet**: proposed lines with reasons, total against ceiling, one Approve button, then the order reference.
5. **Audit log**: timeline of agent steps, tool calls and source URLs.
6. **Graph view** (secondary): ego graph around Valio and one hotel's product. Edge style shows trust (dashed inferred, solid claimed, double agreed, badged audited). Red halo marks risk. Arrows show direction. Upstream links of other companies are not drawn.

## 7. Demo script (4 min)
- 0:00–0:30 Log in as the chain's procurement manager. Week board shows six hotels.
- 0:30–1:10 Risk alert fires: a seeded signal plus a live Context.dev monitor hit on a real dairy news page. Source URLs are visible.
- 1:10–2:00 Click through: Dish "yogurt bowl" → Valio product → producer. Concentration: three direct suppliers share one upstream co-op.
- 2:00–2:40 Alternatives: opted-in suppliers, published price ranges, one fits the window.
- 2:40–3:20 Procurement proposal, one approval, Valio mock order placed, audit log shown.
- 3:20–3:50 Phone: supplier confirms the edge (claimed → agreed). Auditor stamps it (audited).
- 3:50–4:10 Live discovery run: a new inferred producer appears with confidence and URLs.
- Backup: pre-recorded video, cut to the same beats.

## 9. Judging-criteria mapping
- Valio end-to-end (30%): approved order through the mock API with idempotency key.
- Buyer need (20%): pars, windows and menus of a real hotel buyer's week.
- Autonomy and controls (20%): proposal-only agent, human approval, audit log, role-scoped visibility.
- Exceptions (15%): partial availability substitutes, window misses.
- Open standards (15%): JSON proposal schema, OpenAPI description of the mock client, Postgres.
- Context.dev: monitors and discovery run live in the core flow, with source URLs.
- Side bounties: Gemini (agent LLM), Aiven (Postgres, runtime hosting), CRACI (GitHub Actions runner, near-zero effort). Cala skipped (no founder or investor angle in this demo).

## 10. Risks and cuts
- Cut first: ArcadeDB, Kafka, Cala, the full graph view. Keep only the ego graph.
- Biggest technical risks: unknown Valio mock schema (mitigated by Friday check), webhook tunnel failure (mitigated by scan button), LLM latency (mitigated by cached proposal for the seed).

## 11. Biggest weakness of this proposal
The dish-first framing leans on invented menu and par data, and judges may read the product as a procurement app rather than a living network. We keep discovery and the graph visible in the demo, but the graph is the weaker screen.

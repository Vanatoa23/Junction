# Entrant 21: Keel, the network suppliers join to get found (lens: Supplier-side value)

## 0. Bold bet (2 sentences: what makes this proposal different and why it wins)
Most entrants treat suppliers as a data source; Keel makes the supplier portal the engine of growth, giving suppliers discovery, a verified badge and buyer demand in return for confirming edges and publishing prices. Every buyer-side result in the demo depends on a supplier action, so judges watch the supplier side make the buyer story work.

## 1. Summary and name
- Name: **Keel**.
- Two apps on one API: **Buyer Console** (Hotel Kestrel (demo), buying through Valio Aimo) and **Supplier Portal** (Nordhem Dairy Co-op (demo), a fictional upstream dairy producer).
- Supplier value:
  - **Discovery**: opted-in suppliers appear in a buyer's alternatives only when category and risk match.
  - **Verified badge**: *Verified* (domain checked, unexpired certificate parsed from PDF), *Audited* (simulated auditor stamp), *Transparent* (prices published).
  - **Published prices**: chosen per SKU; buyers see ranges built only from published points.
  - **Demand signal**: anonymised count of buyers alerted on the supplier's category, suppressed below k=5.
  - **Risk fix loop**: the supplier sees its own risk signals and the document that clears each one.
- Assumption: suppliers pay nothing in the prototype.

## 2. Architecture and DB choice
- **Postgres only** (Aiven managed, which also counts for the Aiven bounty). No ArcadeDB in the build.
- Reason: opt-ins, price publication and confirmations are relational and transactional. The demo graph is about 60 nodes and at most 4 upstream hops, so recursive CTEs are instant.
- Components: Fastify API; pg-boss jobs; Gemini function calling; Context.dev enrichment, news, PDF parsing and monitors (`/hooks/context`); Valio mock client; React + Cytoscape.js; SSE.
- Flow: Context/Exa → discovery → inferred edges → monitors → `risk_signals` → SSE → proposal → approval → Valio `POST /orders` → `audit_log`.

## 3. Data model and key queries
- `orgs(id, name, kind, domain, domain_verified_at, registered, is_demo)`
- `edges(id, from_org, to_org, category, trust, confidence, source_urls jsonb, confirmed_from, confirmed_to, audited_at)`. Trust is set by a trigger: audited if `audited_at`; agreed if both confirmed; claimed if one side declared; else inferred.
- `visibility(org_id, scope, opted_in)`; `price_points(supplier_id, sku, unit_price_eur, min_qty, published)`; `certificates(supplier_id, type, expires_on, status)`
- `risk_signals(org_id, type, severity, confidence, source_url, observed_at, status)`
- `proposals(id, buyer_id, lines jsonb, status, approved_by, valio_order_ref, idempotency_key)`; `audit_log(…, prev_hash, hash)`, a hash chain.

`visible_edges(viewer)` is the single visibility function. Demand uses `HAVING count(*) >= 5`. Three privacy tests run in CI.

```sql
-- Upstream traversal, cycle-safe, depth <= 4
WITH RECURSIVE up(org, depth, path) AS (
  SELECT from_org, 1, ARRAY[to_org, from_org] FROM edges WHERE to_org = $1
  UNION ALL
  SELECT e.from_org, up.depth+1, up.path || e.from_org
  FROM up JOIN edges e ON e.to_org = up.org
  WHERE up.depth < 4 AND NOT e.from_org = ANY(up.path))
SELECT org, MIN(depth) AS depth FROM up GROUP BY org;
```
- **Hidden concentration**: run the CTE for each direct supplier of buyer B, then `GROUP BY org HAVING COUNT(DISTINCT supplier) >= 2`.
- **Blast radius**: the same CTE downward from failing org F.
- **Alternatives**: opted-in suppliers in category C with a valid certificate, excluding X's upstream; min and max of published prices.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery**: input a domain or category; tools Context.dev enrichment and news, Exa second source; output an unregistered org plus `inferred` edge with `source_urls`. Validation: 2 distinct sources, or confidence >= 0.6 with a resolving domain.
- **Monitoring**: Context.dev monitors on supplier compliance pages; output a `risk_signals` row with URL, timestamp and before/after diff. Severity comes from a rule table; the LLM only explains.
- **Procurement**: input an open upstream signal plus order lines; tools Valio `GET /products`, `/availability`, `/lead-times`, `POST /orders` (endpoint shapes an **assumption** until the mock docs are read). Output: substitutes, price delta %, partial-fill plan. Partial stock splits the order; late lead times are flagged.
- **Approval**: proposal stays `pending` until the manager clicks Approve; only then does `POST /orders` run, with `Idempotency-Key = proposal.id`. The agent cannot approve.

## 5. Risk engine
- Score = severity × confidence × exposure (share of buyer spend routed through the node). High >= 70, medium 40-69.
- **Geopolitical**: country band from a public index (**assumption**: static table) plus region news for conflict and trade terms.
- **Regulatory**: EU sanctions list (**assumption**: CSV download), fuzzy match >= 0.9 via `pg_trgm`. EUDR: in-scope commodity with no valid DDS certificate. CSDDD: no due-diligence page found. Expired certificates.
- **Concentration**: single source per category, plus shared upstream (query above).
- **Financial**: Context.dev headcount deltas (drop > 15%) and news keywords (insolvency, restructuring).
- **Live events**: Context.dev news for recall, strike, outage, ranked by recency.
- **Price premium**: only when both prices are published. (paid - best alternative) / alternative; flag above 10%.
- Demo: Nordhem's organic certificate expired and the monitor caught the page change. 85 × 0.9 × 0.95 = 73, high.

## 6. Screens and graph view
- **Buyer Console**: supply map (upstream left); risk inbox; alternatives with price ranges; proposal with Approve / Reject; audit timeline.
- **Supplier Portal**: domain verification; connection inbox (Confirm: claimed → agreed); price sheet with per-SKU publish toggle; certificate PDF upload with badge update; opt-ins and demand counts; my risks with a fix button.
- **Graph**: line style = trust (inferred dashed grey with confidence; claimed dotted; agreed solid; audited thick with shield). Node colour = highest open risk. Unregistered nodes are hollow with an invite tag.

## 7. Demo script (timed beats, about 4 min)
1. **0:00-0:25** Hotel Kestrel's supply map.
2. **0:25-0:55** Nordhem confirms the Valio edge (claimed → agreed) and publishes prices.
3. **0:55-1:30** Live discovery: Context.dev adds three dashed inferred nodes with clickable URLs.
4. **1:30-2:00** Monitor webhook fires on Nordhem's certificate page; the risk appears in the buyer inbox and on Nordhem's "My risks" tab at once.
5. **2:00-2:40** Buyer alert (73); concentration flag. Alt Dairy (demo) shows a Transparent badge and price range.
6. **2:40-3:20** Proposal with premium check; partial stock splits the order; manager approves; Valio reference returned.
7. **3:20-3:45** Audit timeline with source URLs. Auditor stamps the edge Audited.
8. **3:45-4:00** Privacy panel: what Nordhem cannot see; the k=5 view.

## 9. Judging-criteria mapping
- **Valio (30%)**: request → approve → order via the mock, with audit trail; partial stock (15%); approval gate and hash chain (20%).
- **Buyer need (20%)**: risk alert, published-price alternatives, EUDR evidence.
- **Feasibility (25%)**: one database, pre-seeded suppliers.
- **Context.dev (15%)**: enrichment, news, monitor webhook, PDF parse, all live.
- **Trust and privacy (10%)**: trigger-derived trust, opt-in, k=5.
- **Side bounties**: Gemini, Aiven, CRACI. Cala cut.

## 10. Risks and cuts
- **Cut order**: Cala, ArcadeDB, Oxylabs, Modal, Exa (keep Context.dev), then portal screens 5-6.
- **Risks**: Context.dev latency on stage (pre-warm, label cache); webhook needs a public URL (polling backup); Valio mock shapes assumed; cold-start supplier side (seeded suppliers).

## 11. Biggest weakness of this proposal (be honest)
The supplier value is shown, not proven. No real supplier opts in within 48 hours, so the network effect is staged, and the demand screen may look empty unless enough buyers are seeded to pass k=5.

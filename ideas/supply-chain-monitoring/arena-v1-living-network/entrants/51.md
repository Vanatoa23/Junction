# Entrant 51: Pulse (lens: operational performance signals)

## 0. Bold bet
Risk shows up first in the delivery numbers, weeks before any news story, so the monitoring agent watches daily fill rate, on-time rate and lead time as time series and only then asks the web to explain the anomaly. Every alert is a measured drop plus a sourced cause, and shared-upstream concentration is detected from correlated supplier dips even where the graph is incomplete.

## 1. Summary and name
- **Pulse**: a hotel buyer sees its supply network as a living graph, and its suppliers' delivery health as a pulse line. When a dairy source starts shorting deliveries, the system finds the common upstream, cites a strike notice, and proposes a switch.
- Persona: "Pohjan Hotellit" (dummy) buying through Valio Aimo.
- Live moment: a replayed delivery feed streams nine days of new order outcomes onto the timeline while the judges watch, the detector fires, and the Context.dev news run executes live against the flagged company.

## 2. Architecture and DB choice
- **Postgres on Aiven** for everything: graph edges, metrics, anomalies, risks, proposals, audit. One store, one backup story.
- **Time series in plain Postgres**: a daily table partitioned by month, BRIN index on `day`. Daily grain is enough for 180 days and 30 suppliers. ClickHouse on Aiven is a stretch only (assumption: it works without setup days).
- **ArcadeDB rejected**: its time-series and traversal features are attractive, but a second engine adds setup risk. Keep it as the production slide.
- **Stack**: TypeScript monorepo, Node worker with timers, Express API, React + Cytoscape.js + a small SVG sparkline component. Gemini for classification and summary text only.
- **Data flow**: Valio mock order-outcome feed → `supplier_metric_day` → detector SQL → `anomaly` → monitoring loop (Context.dev) → `risk` → procurement loop → Valio mock order after human approval → `audit`.

## 3. Data model and key queries
- `supplier_metric_day(buyer_id, supplier_id, sku_group, day, ordered_qty, delivered_qty, orders_n, on_time_n, lead_days_median)`. PK on all but metrics. Only the buyer's own order outcomes are written here; this is the privacy boundary.
- `upstream_of(supplier_id, upstream_id, depth)`: materialised from the edge graph by recursive CTE on each refresh.
- `anomaly(id, buyer_id, supplier_id, metric, detected_day, z, baseline, current, state)`.
- `web_signal(id, company_id, url, title, published_at, kind, confidence, fetched_at)`.
- `risk(id, buyer_id, company_id, severity, anomaly_ids[], web_signal_ids[], state)`.
- `edge(from_id, to_id, state, confidence, sources jsonb)` with trust states `inferred | claimed | agreed | audited`. Trust changes only through `edge_event` rows, never direct updates.
- `audit(id, at, actor, action, ref, payload jsonb, prev_hash, hash)`, append-only.
- **Visibility**: the buyer's API reads only its own `supplier_metric_day` rows, plus `risk` rows, plus anonymised `industry_usage` aggregates (cohort of at least 5 buyers). The upstream plant has no metric rows visible to the buyer; it appears only as a risk warning.
- **Anomaly detector** (runs per buyer, per supplier, per metric):
  `WITH d AS (SELECT supplier_id, day, delivered_qty::float/NULLIF(ordered_qty,0) fr FROM supplier_metric_day WHERE buyer_id=$b),
  base AS (SELECT supplier_id, avg(fr) m, stddev(fr) s FROM d WHERE day BETWEEN $asof-104 AND $asof-15 GROUP BY 1),
  cur AS (SELECT supplier_id, avg(fr) m FROM d WHERE day BETWEEN $asof-13 AND $asof GROUP BY 1)
  SELECT c.supplier_id, (c.m-b.m)/NULLIF(b.s,0) AS z FROM cur c JOIN base b USING (supplier_id) WHERE (c.m-b.m)/NULLIF(b.s,0) < -3;`
  Lead-time creep uses the same shape on `lead_days_median`, with z > 3. Rule: flag only if the condition holds on 3 consecutive daily runs, to avoid one-day noise.
- **Shared upstream from correlated dips**:
  `SELECT u.upstream_id, count(DISTINCT a.supplier_id) n, min(a.detected_day) first_day FROM anomaly a JOIN upstream_of u ON u.supplier_id=a.supplier_id WHERE a.state='open' AND a.metric='fill_rate' GROUP BY 1 HAVING count(DISTINCT a.supplier_id) >= 2 AND max(a.detected_day)-min(a.detected_day) <= 3;`
- **Blast radius**: downstream from the flagged upstream through `edge`, joined to the buyer's SKU lines, summing order value over the last 90 days.
- **Alternatives**: opted-in suppliers in the same category with published price bounds and their own `supplier_metric_day` aggregate for the buyer's SKUs, if any. No cross-buyer operational data is shown.

## 4. Agents (discovery, monitoring, procurement)
Each agent is a bounded tool-calling loop (max 6 steps) with a zod-validated output.
- **Discovery** (runs at setup and on demand)
  - Input: a supplier name.
  - Tools: `ctx_company(name)`, `ctx_news(query, since)`, `add_candidate_edge`.
  - Output: candidate `inferred` edges with confidence and source URLs.
  - Validation: each candidate must carry a verbatim quote from a fetched page; code checks substring presence, not the model.
- **Monitoring** (scheduled every 60s in demo, plus the replay trigger)
  - Input: open anomalies and the upstream sets of flagged suppliers.
  - Tools: `query_anomalies`, `ctx_news(upstream_name, since=last_run)`, `write_web_signal`, `write_risk`.
  - Output: a risk that must cite at least one anomaly id and one URL, or it is not written. Severity is set by a fixed table: operational anomaly alone is amber; anomaly plus web event is red.
  - Prompt in short: "Summarise the cause in one sentence using only the supplied URLs. Do not infer a cause the sources do not state."
  - Assumption: Context.dev monitor webhooks are optional; the scheduled `ctx_news` call is the default real-time loop.
- **Procurement** (on red risk)
  - Input: risk plus buyer SKUs for the affected supplier.
  - Tools: read-only `valio_search`, `valio_price`, `valio_availability`, `make_proposal`. `valio_order` is not in the tool list.
  - Output: `proposal` in state `proposed`. Approval is a separate human event; only then a non-agent function places the order at the quoted fixed price with an idempotency key.
  - Assumed mock shapes (label on slide): `GET /orders?supplier=&from=&to=` returns delivered and promised quantities and dates; `GET /availability/{sku}`; `POST /orders`.

## 5. Risk engine
- **Operational (deterministic)**: fill-rate drop z below -3, lead-time creep z above 3, on-time rate drop; three consecutive runs required.
- **Concentration (deterministic)**: correlated dips across direct suppliers sharing an upstream, within 3 days.
- **Live events (LLM-classified)**: Context.dev news classified into a closed enum (strike, recall, outage, negative news). Each signal needs a URL.
- **Regulatory and geopolitical**: seeded dummy flags, labelled "seeded" in the UI. No live sanctions claim.
- **Financial health**: one optional Context.dev enrichment field, shown only if it appears in the script.
- **Price premium**: buyer's price minus cheapest published bound, only where published.

## 6. Screens and graph view
- **Network**: Cytoscape canvas, buyer at centre, arrows toward the buyer. Edge style encodes trust (dashed inferred, solid claimed, double agreed, gold ring audited). Node colour encodes risk (amber or red ring). Selecting an edge shows its confidence and source URLs.
- **Pulse panel**: per-supplier sparklines for fill rate and lead time over 180 days, with the detected anomaly band shaded.
- **Feed control**: "Replay last 9 days" button streams delivery outcomes into the time series, labelled "replayed synthetic Valio feed".
- **Risk card**: anomaly evidence, web source URLs, blast radius in SKUs and euros.
- **Proposal and ledger**: state rail, diff, approve button; audit timeline with hash check.
- **Partner view**: role switch for supplier confirm and auditor stamp.

## 9. Judging-criteria mapping
- **Valio (30 / 20 / 20 / 15 / 15)**: beats 4 to 7 deliver request, approval and fixed-price order. Delivery time series is the buyer's need in measurable form. Ledger covers auditability. Partial availability covers exceptions. Assumed REST and idempotency keys cover open standards.
- **Context.dev (15%)**: live `ctx_news` at beat 3 with URLs; continuous monitoring is real-timeness; quote validation is sourcing.
- **Trust and privacy (10%)**: the buyer sees only its own operational data and the upstream risk, never upstream metrics; trust changes only through events.
- **Concreteness (10%)**: detector SQL and shared-upstream SQL are the implementation.
- **Side bounties**: Gemini for classification and summaries; Aiven Postgres as the single store; Codex for test generation; CRACI in CI from day one.

## 10. Risks and cuts
- **Cut order**: webhooks, Cala, Exa, financial health, geopolitical scoring, ClickHouse, ArcadeDB.
- **Risk: synthetic history looks fake**. Mitigation: noise and weekly seasonality in the generator; state the planted event openly.
- **Risk: Valio order-history shape differs**. Mitigation: adapter; stub mirrors our assumption.
- **Risk: live news empty or slow**. Mitigation: cached Friday response, labelled with timestamp.
- **Risk: z-score false positives**. Mitigation: 3-run confirmation and a fixed threshold, tested on the seeded data.

## 11. Biggest weakness of this proposal (be honest)
The operational signal depends on realistic-looking synthetic delivery history that we generate ourselves, so the detector proves only that it finds the event we planted. A sharp judge will say the anomaly is staged, and the replay feed makes the staging visible.

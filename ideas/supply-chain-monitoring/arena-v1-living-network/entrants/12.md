# Entrant 12: Bounty Stack Ledger (lens: Bounty stacker)

## 0. Bold bet
Every side bounty is earned by a step already on the critical path, so the stack costs no extra screens: Gemini runs all three agents, Context.dev powers the live scan in the buyer's core flow, and Valio's order path is the procurement agent's only write action. Seven partners, four workstreams, and a written cut-line that protects the Valio order and live-scan beats.

## 1. Summary and name
- Name: **Supplyline**.
- Product: a hotel buyer sees its supply map, gets a live risk alert on an upstream dairy producer with source URLs, compares opted-in alternatives with published prices, and approves a Gemini-proposed switch that is placed through the Valio mock API and logged step by step.
- Targeted prize stack: Valio (aim 1st, €4k), Context.dev (€2k/€500 challenge plus €750/€250 bounty), Gemini (€4k), Aiven (€1k), CRACI (near-zero effort), Codex (credits, if usage is logged). Cala is a stretch only.

## 2. Architecture and DB choice
- **Postgres on Aiven** is the single system of record: graph as edge tables, multi-tier traversal via recursive CTEs, visibility via row-level security (RLS). Graphs here are a few hundred nodes, so SQL is enough.
- **ArcadeDB: rejected** for the 48h build. It has no bounty and adds a new query language and setup risk. It stays only as a documented post-hackathon option.
- **Aiven Valkey**: 60s cache for Valio lookups and a `live.events` pub/sub channel feeding the UI over SSE.
- **Aiven Runtime** hosts the Node app (assumption: available on the hackathon plan; fallback is a laptop plus tunnel for webhooks).
- Stack: TypeScript, Fastify, React with Cytoscape.js, Gemini SDK, Context.dev JS SDK, Valio client generated from their OpenAPI spec (assumption: spec provided).
- Live path: Context.dev monitor or news search → webhook `/hooks/contextdev` → `signal` row → Valkey publish → UI alert.
- Agent path: Gemini function calls → Valio tools → `proposal` → human `approval` → `order` → `tool_call` log.

## 3. Data model and key queries
- `company(id, name, kind[registered|unregistered|seed], country, industry_code, opted_in_visible)`
- `edge(id, src_id, dst_id, trust[inferred|claimed|agreed|audited], confidence, declared_by, confirmed_by[], audited_by)`. Direction: src sells to dst.
- `edge_source(edge_id, url, fetched_at, snippet)`. Required for `inferred`; no source, no edge.
- `trust_event(edge_id, from, to, actor, at)`. Append-only.
- `price_point(company_id, product_id, unit_price, published bool)`. RLS returns only `published = true`.
- `signal`, `risk(type, score, evidence_signal_ids[])`, `tool_call(run_id, step, tool, input, output, source_urls[])`, `approval(proposal_id, quote_hash, expires_at, decision)`, `order`.
- RLS: policies key off `current_setting('app.viewer_company')`. Buyers read their own edges plus risk and upstream-path views only. Supplier-view and auditor-view variants are separate views.

Key queries:
```sql
-- Upstream traversal, depth <= 4, cycle-safe
WITH RECURSIVE up(id, depth, path) AS (
  SELECT src_id, 1, ARRAY[dst_id, src_id] FROM edge WHERE dst_id = $me
  UNION ALL
  SELECT e.src_id, up.depth+1, up.path || e.src_id
  FROM up JOIN edge e ON e.dst_id = up.id
  WHERE up.depth < 4 AND e.src_id <> ALL(up.path))
SELECT id, min(depth) FROM up GROUP BY id;

-- Hidden concentration: upstream nodes shared by >= 2 direct suppliers
WITH RECURSIVE reach(root, id, depth) AS (
  SELECT src_id, src_id, 0 FROM edge WHERE dst_id = $me
  UNION
  SELECT r.root, e.src_id, r.depth+1 FROM reach r JOIN edge e ON e.dst_id = r.id WHERE r.depth < 3)
SELECT id, count(DISTINCT root) AS shared_by FROM reach
WHERE depth > 0 GROUP BY id HAVING count(DISTINCT root) >= 2;

-- Blast radius: downstream reach of a failed supplier
WITH RECURSIVE down(id, depth) AS (
  SELECT dst_id, 1 FROM edge WHERE src_id = $failed
  UNION
  SELECT e.dst_id, d.depth+1 FROM down d JOIN edge e ON e.src_id = d.id WHERE d.depth < 4)
SELECT count(DISTINCT id) FROM down;

-- Alternatives: opted-in, published price only
SELECT c.name, min(pp.unit_price), max(pp.unit_price)
FROM price_point pp JOIN company c ON c.id = pp.company_id
WHERE pp.product_id = $p AND pp.published AND c.opted_in_visible
GROUP BY c.name;

-- Peer usage aggregate, k-anonymity threshold k = 5
SELECT count(DISTINCT e.dst_id)::float / nullif(
  (SELECT count(*) FROM company WHERE industry_code = $ind AND kind = 'registered'), 0)
FROM edge e JOIN company c ON c.id = e.dst_id
WHERE e.src_id = $supplier AND c.industry_code = $ind
HAVING count(DISTINCT e.dst_id) >= 5;
```
- Alternatives by vector search are a stretch (pgvector); category and Valio substitution rules cover the demo.

## 4. Agents (discovery, monitoring, procurement)
All three use **Gemini** as the single LLM, with function calling and JSON-schema structured output.
- **Discovery**: input is a company name and Valio supplier list. Tools: `contextdev.companyEnrich`, `contextdev.newsSearch`, `contextdev.extract(url, schema)`. Output: candidate `inferred` edges with confidence and URLs. Validation: reject unless a source text contains both names; confidence is capped at 0.9. Unregistered nodes get an invite.
- **Monitoring**: Context.dev monitors on supplier domains and news queries, with webhooks on change. On webhook, `extract` pulls certifications, recall notices and status. Gemini classifies into risk types; signals below 0.6 confidence are stored but not alerted.
- **Procurement**: triggers on a risk or a price premium. Tools: `valio.productLookup`, `valio.availability`, `valio.quote`, `valio.substitutions`, alternatives query (assumption: quote and order endpoints exist in the mock). Output: proposal with items, quote ID, price, lead time, certifications, rationale and citations.
- Guardrails: €2,000 spend cap (policy row), only opted-in suppliers, quote valid 10 minutes, and no order without an approval whose `quote_hash` matches. Partial availability triggers a substitution with the same certifications; if none exists, the item escalates to the manager.
- Every tool call writes a `tool_call` row, which feeds the "why" timeline.

## 5. Risk engine
Rules first, Gemini only for text classification. A risk without evidence IDs never alerts.
- **Geopolitical**: static country-risk seed × supplier country, plus a live `newsSearch` for conflict, sanctions or export-ban terms.
- **Regulatory**: sanctions list matched by name (assumption: EU consolidated list loaded at build); certification expiry from extracted data; EUDR and CSDDD flags from seeded attributes.
- **Concentration**: the shared-upstream query (≥2 direct suppliers), and single-source flag per product.
- **Financial health**: `companyEnrich` plus news on layoffs or insolvency, classified by Gemini.
- **Live events**: recalls, strikes, outages from `newsSearch` and monitors.
- **Price premium**: (our price − cheapest published opted-in alternative) / alternative > 10%.
- Score is the max of components. Bands: info < 0.4, warn < 0.7, critical ≥ 0.7.

## 6. Screens and graph view
- **Persona login**: hotel buyer, supplier, auditor.
- **Supply map**: Cytoscape, arrows run upstream to downstream. Edge style: dashed for `inferred` (label shows confidence), solid for `claimed`, thick solid for `agreed`, double for `audited`. Node colour is max risk. Beyond the first tier, upstream nodes appear as risk paths only.
- **Alert panel**: risk type, confidence, source URLs with fetch times, shared-upstream count, blast radius.
- **Alternatives**: opted-in suppliers, published price range, peer usage aggregate (k ≥ 5).
- **Proposal**: current vs proposed side by side, guardrail checklist, Approve or Reject.
- **Audit timeline**: tool calls, sources, approval, order ID.
- **Supplier view**: confirm pending edges (claimed → agreed), toggle opt-in and price publication.
- **Auditor view**: queue, stamp `audited`.
- **Live strip**: Context.dev events via SSE.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards)**: working mock order; alternatives with price range; hash-bound approval, spend cap and `tool_call` log; substitution and escalation; OpenAPI client and JSON Schema proposals with trace IDs.

## 10. Risks and cuts
- Cut order: Cala panel → auto-invites (seed manually) → price-premium rule → SSE (poll every 5 s).
- Never cut: the Valio order path, approval binding, the live scan with source URLs, and visibility enforcement.
- Risks: webhooks need a public URL (fallback to polling); Valio mock quirks; Gemini rate limits (one call per signal, cached); Aiven Runtime availability (laptop fallback); RLS leaks (test as each persona); a seven-partner story can read as a checklist.

## 11. Biggest weakness of this proposal (be honest)
The bounty spread is the product's weakness: Cala is effectively an add-on and will likely earn nothing, and Codex and CRACI credit depends on judges accepting thin evidence. The live Context.dev alert depends on external sites and quotas, and a misclassified real news item could sink the live moment, so the cached replay has to be rehearsed.

# Entrant 59: Tessera, a paid compliance network that bootstraps on Valio's own suppliers (lens: Path to production and business model)

## 0. Bold bet (2 sentences: what makes this proposal different and why it wins)
Valio does not buy a graph; it buys fewer EUDR and CSDDD evidence chases and fewer supply surprises, so the network starts with Valio's 700 suppliers answering one questionnaire they must answer anyway. The demo shows a named payer, a bootstrap mechanism and a price, which earns the production-path points that most entrants leave to a slide.

## 1. Summary and name
- Name: **Tessera** (one tile of a shared mosaic; name check pending).
- Tessera is a compliance-first supply network. Each supplier answers one questionnaire; the answers become confirmed edges and reusable evidence for every buyer.
- Payers (prices are **assumptions** for pitch only):
  - **Valio**, primary: EUR 15 per monitored supplier per month (about EUR 125k a year at 700 suppliers), plus 0.5% of value on agent-routed switches.
  - **Buyers**: free risk alerts; paid compliance pack, bundled by Valio.
  - **Suppliers**: free to join; pay only audit fees, passed to the auditor.
- Bootstrap: Valio adds the questionnaire to its supplier terms (a business decision, **assumption**). Answers name upstream and downstream companies, who become invitees.

## 2. Architecture and DB choice
- **Postgres on Aiven** (managed backups and HA, the production-credible option; also the Aiven bounty). Row-level security (RLS) enforces tenant isolation: buyers and suppliers are tenants. No ArcadeDB: the production risk is isolation and audit, which Postgres handles well, and the demo graph is about 60 nodes.
- Stack: Fastify API with OpenAPI; pg-boss jobs; Gemini function calling; Context.dev (enrichment, news, PDF parse, monitors via `/hooks/context`); React with Cytoscape.js; SSE.
- **Valio adapter**: `ValioAdapter` interface with `MockValio` as implementation. Production swap is one class.
- Evidence stored as a Verifiable-Credential-shaped JSON envelope (**assumption**: format only).
- CRACI SBOM scanning in CI from day one.

## 3. Data model and key queries
- `orgs(id, name, kind, domain, tenant_id, registered)`
- `edges(id, from_org, to_org, category, spend_share, trust, confidence, source_urls jsonb, confirmed_from, confirmed_to, audited_at)`. Trust set by trigger: audited if `audited_at`; agreed if both confirmed; claimed if one side declared; else inferred.
- `questionnaire_answers(supplier_id, question_code, answer jsonb, evidence_url)`: the bootstrap engine.
- `visibility`, `price_points`, `certificates`, `risk_signals`, `proposals(…, approvals jsonb, idempotency_key)`, `audit_log(…, prev_hash, hash)`, `subscriptions(tenant_id, plan, monitored_suppliers)`.
- RLS: `edges` readable only when the caller's org is an endpoint. Buyers read a `buyer_edges` view that hides suppliers' customer lists. Valio admins see aggregates only.

```sql
-- Exposure: share of a buyer's spend reaching each upstream node, depth <= 4
WITH RECURSIVE chain(org, depth, weight) AS (
  SELECT from_org, 1, spend_share FROM edges WHERE to_org = $1
  UNION ALL
  SELECT e.from_org, c.depth+1, c.weight * e.spend_share
  FROM chain c JOIN edges e ON e.to_org = c.org
  WHERE c.depth < 4)
SELECT org, SUM(weight) AS exposure FROM chain GROUP BY org ORDER BY exposure DESC;
```
- **Hidden concentration**: the same chain per direct supplier; keep orgs where `COUNT(DISTINCT supplier) >= 2`, ranked by summed exposure.
- **Blast radius**: the chain downward from failing org F, summing spend reached.
- **Alternatives**: `visibility.scope='listing' AND opted_in`, a valid DDS certificate for the category, not in X's upstream set, with min and max of published prices.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery**: triggered by questionnaire answers naming a company. Context.dev enrichment confirms the domain; news corroborates. Output: `inferred` edge with `source_urls`. Validation: domain resolves and 2 sources, or confidence >= 0.6.
- **Monitoring**: Context.dev monitors on compliance pages and news; nightly sanctions re-check (**assumption**: downloadable CSV). Output: `risk_signals` with before/after diff. Severity from a rule table; the LLM explains only.
- **Procurement**: tools are `ValioAdapter` products, availability, lead times and orders. Output: proposal with substitutes, price delta, compliance result and partial-fill plan.
- **Approval**: pending until a buyer manager approves; above EUR 5k a second approver (configurable). Then `placeOrder` runs with `Idempotency-Key = proposal.id`. The agent cannot approve.

## 5. Risk engine
- Compliance is a **gate**, not a score: a line with an in-scope commodity and no valid DDS certificate cannot be ordered, whatever the score.
- Otherwise score = severity × confidence × exposure; high >= 70.
- **Regulatory**: sanctions fuzzy match >= 0.9 (`pg_trgm`); EUDR gate above; CSDDD gap when the monitor finds no due-diligence page; expired certificates.
- **Geopolitical**: country band from a public index (**assumption**) plus region news.
- **Concentration**: single source per category, plus shared upstream.
- **Financial and live events**: Context.dev headcount change and news on insolvency, recalls, strikes.
- **Price premium**: only with published prices; flag above 10%.
- Demo: Nordhem's organic certificate expired. 85 × 0.9 × 0.95 = 73, high.

## 6. Screens and graph view
- **Buyer Console**: supply map; risk inbox; alternatives; proposal with approvals; audit timeline; compliance pack export.
- **Supplier questionnaire**: about 20 questions, answered once, reused for all buyers.
- **Valio Admin**: onboarding funnel, revenue meter, exception queue.
- **Graph**: left to right is upstream to downstream. Line style = trust (inferred dashed with confidence; claimed dotted; agreed solid; audited thick with shield). Node colour = highest open risk. Unregistered nodes hollow with an invite tag.

## 9. Judging-criteria mapping
- **Valio (30%)**: adapter order flow, two-person approval, compliance gate, hash-chained log.
- **Buyer need (20%)**: compliance evidence, alerts, published-price alternatives.
- **Feasibility (25%)**: one database, one adapter, scripted seed.
- **Context.dev (15%)**: questionnaire-triggered discovery, monitors, PDF parse, all live.
- **Trust and privacy (10%)**: RLS, trigger-derived trust, k >= 5.
- **Concreteness (10%)**: schema, SQL, screens.
- **Production path (within Valio's open-standards criterion)**: adapter swap, OpenAPI, VC-shaped evidence.
- **Side bounties**: Gemini, Aiven, CRACI. Cala cut.

## 10. Risks and cuts
- **Cut order**: Cala, ArcadeDB, Oxylabs, Modal, Exa, PDF export (JSON bundle only).
- **Risks**: Valio mock docs incomplete (adapter isolates this); RLS leak of a customer list (automated tests gate the demo); Context.dev latency (pre-warm, label cache); business numbers are assumptions and shown as such.

## 11. Biggest weakness of this proposal (be honest)
The business model is asserted, not validated. No Valio buyer or supplier has agreed to pay or onboard, and the questionnaire bootstrap depends on a Valio policy decision that cannot happen inside the hackathon. The Valio Admin screens also add a third screen set on a four-person team.

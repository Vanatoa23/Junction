# Entrant 43: Greenlane, sustainability-ranked alternatives (lens: Sustainability comparison)

## 0. Bold bet
Alternatives are not sorted by price; they are ranked by a transparent, buyer-weighted score that combines price, carbon from real delivery distance, and certificates weighted by how well they are verified. Every number on screen links to its evidence, so the procurement agent's switch proposal is explainable line by line, which is the one thing a judge on the Valio "controls" criterion will check.

## 1. Summary and name
- Name: **Greenlane** (the lane a food order travels, and the green choice on it).
- Buyers see a ranked list of opted-in alternatives for a product, with price, lead time, delivery km, estimated kg CO2e per order, and certificate status. Procurement proposes a switch when a risk or price premium appears; a manager approves, and the order goes through the Valio mock API.
- Stack: TypeScript (Fastify API, React screens), Postgres on Aiven, Gemini function-calling for agents, Context.dev for live certificate and news checks, Valio mock as a separate OpenAPI service.

## 2. Architecture and DB choice
- **Postgres (Aiven) as the primary store.** Ranking needs joins, weighted sums and simple geometry, all standard SQL. Haversine is a plain SQL function, so PostGIS is not required (assumption: Aiven Postgres runs plain functions, which it does).
- **ArcadeDB: not in the core.** Its strengths (multi-tier traversal, vector search) are not needed for a ranking of tens of candidates. Stretch only: ArcadeDB time-series for delivery lead-time history.
- Components: API; ranking service (pure SQL plus a typed TypeScript scorer, so the same logic runs in tests); agent worker (Gemini tool calls); Context.dev client; Valio mock; `ranking_run` audit writer.
- Flow: buyer or agent requests alternatives for product P; API reads opted-in listings and certificates; scorer writes a `ranking_run` with inputs hash and per-criterion contributions; UI renders the same record.

## 3. Data model and key queries
- `company(id, name, kind[registered|unregistered], lat, lon, country, alt_opt_in)`
- `edge(id, from_id, to_id, trust_level[inferred|claimed|agreed|audited], confidence, source_urls jsonb)`, with confirmations in `edge_confirmation`. Trust level is set by trigger, never by the app.
- `certificate(id, company_id, scheme, scope, issued, valid_until, trust_level, evidence_url, checked_at)`. Schemes in the demo: organic (EU), MSC (fish), RSPO (palm oil), EUDR deforestation-free declaration, Finnish eco-label.
- `product(id, category, unit, kg_per_unit, co2e_kg_per_kg, origin_country)`
- `listing(supplier_id, product_id, price_eur, lead_time_days, published, alt_visible)`
- `route(supplier_id, hub_id, distance_km, mode)`: road distance estimate, not a claim.
- `ranking_run(id, viewer_id, product_id, weights jsonb, inputs_hash, result jsonb, created_at)`: append-only.

Ranking query (lower score is better):
```sql
WITH cand AS (
  SELECT l.supplier_id, l.price_eur, l.lead_time_days, p.co2e_kg_per_kg, p.kg_per_unit,
         round(1.25 * haversine(c.lat, c.lon, $hub_lat, $hub_lon)) AS km
  FROM listing l
  JOIN company c ON c.id = l.supplier_id
  JOIN product p ON p.id = l.product_id
  WHERE l.product_id = $product AND l.published AND l.alt_visible AND c.alt_opt_in
), cert AS (
  SELECT company_id,
         max(CASE trust_level WHEN 'audited' THEN 1.0 WHEN 'agreed' THEN 0.8
                              WHEN 'claimed' THEN 0.5 ELSE 0.2 END) AS cert_w,
         bool_or(scheme = 'EUDR' AND valid_until > now()) AS eudr_ok
  FROM certificate WHERE valid_until > now() GROUP BY company_id
), scored AS (
  SELECT cand.*, coalesce(cert.cert_w, 0) AS cert_w, coalesce(cert.eudr_ok, false) AS eudr_ok,
         cand.co2e_kg_per_kg * cand.kg_per_unit * cand.km * 0.00006 AS co2e_order_kg  -- assumption: 60 g/tkm
  FROM cand LEFT JOIN cert ON cert.company_id = cand.supplier_id
)
SELECT *, 0.35*price_eur/min(price_eur) OVER () + 0.25*co2e_order_kg/min(co2e_order_kg) OVER ()
        + 0.20*km/min(km) OVER () + 0.20*(1 - cert_w) AS score
FROM scored
WHERE ($require_eudr = false OR eudr_ok)
ORDER BY score;
```
Weights are per viewer policy and stored in `ranking_run`, so a judge can change them live and see the order flip.

Key queries beyond ranking: upstream traversal over RLS-visible edges; blast radius (downstream visible customers of a failed supplier); certificate expiry sweep (`valid_until < now() + 30 days`).

## 4. Agents (discovery, monitoring, procurement)
Common rules: short-lived token per org; typed tools only; output is a proposal row, never a direct write to orders.
- **Discovery.** Input: product category and region. Tools: Context.dev search and structured scrape of public certificate registries and supplier pages. Output: `inferred` certificate and company candidates, each with `evidence_url` and confidence. Validation: no URL, no record; certificate valid dates must parse; confidence below 0.6 is hidden.
- **Monitoring.** Input: all certificates with `valid_until` within 60 days, and all alternatives on the viewer's watchlist. Tools: Context.dev monitors (webhook if reachable, else 60s polling) and news search for recalls or strikes. Output: `risk_signal` rows, and a certificate status change that re-runs ranking.
- **Procurement.** Input: current supplier, ranking run, Valio availability and lead times. Tools: Valio `GET /products`, `GET /availability`, `POST /orders` (only with approval token, HMAC-signed, 5 minutes, bound to proposal hash). Output: proposal card showing score delta and each criterion's contribution. Partial availability: split the order across the top two ranked candidates, each ranked separately.

## 5. Risk engine
- Sustainability risk is a first-class score input, not a separate alert stream: expired or missing certificate (hard filter when required), certificate status change, and recall or strike news from Context.dev.
- Carbon: `kg CO2e per order = co2e_factor x kg x km x 60 g/tkm` (assumption: road freight factor; product factors come from the Valio synthetic dataset or a labelled dummy table).
- Geopolitical and sanctions risks feed a hard filter on alternatives (sanctioned or conflict-zone origin excluded) and a penalty otherwise.
- Price premium: current price vs best published alternative, shown only where prices are published.
- Certificate trust: an `inferred` certificate counts 0.2 and shows a "not verified" badge, so a scraped claim cannot beat an audited one.

## 6. Screens and graph view
1. Product page: ranked alternatives table, with a weight slider per criterion and a "why this rank" expander.
2. Certificate card: scheme, scope, validity countdown, trust badge, evidence URL, last checked time.
3. Proposal: current vs proposed, score delta, carbon delta in kg, split-order option.
4. Route map: hub and supplier pins with km and mode lines.
5. Graph view: direction arrows; solid for agreed or audited, dashed for claimed, dotted for inferred; node colour = certificate status (green valid, amber expiring, red expired); shield for audited.
6. Audit log: each ranking run and proposal, with inputs hash and approver.

## 7. Demo script (4 minutes)
- 0:00 Hotel buys dairy through Valio. Current supplier shows an expiring certificate (amber).
- 0:40 Open alternatives: ranked list by default; drag the carbon weight, and the order flips live.
- 1:20 Live Context.dev check of an alternative's certificate page: status and source URL appear, card turns from "not verified" to "audited" after the simulated auditor stamps it.
- 2:00 Procurement proposal: price +4%, carbon -18%, 40 km shorter route. Manager approves; order goes to Valio mock; receipt shows the `ranking_run` hash.
- 2:50 Exception: one candidate out of stock; order splits across ranks two and three automatically.
- 3:30 Supplier confirms an edge (claimed to agreed) on a second browser.
- 3:50 Audit log: every score input traceable to a URL or a database row.

## 9. Judging-criteria mapping
- Valio (30% demo): buyer reaches a mock order with a ranked alternative. Sustainability comparison is one of the optional extras, so it is covered.
- Valio controls (20%): approval token, ranking audit, weights recorded per run.
- Valio exceptions (15%): out-of-stock split across ranked candidates; delivery distance constraint via hub.
- Valio open standards (15%): OpenAPI for mock, JSON Schema for proposals, certificate fields following plain scheme names.
- Context.dev (15%): live certificate and news checks in the core ranking path, with source URLs and a visible status change.
- Trust and privacy (10%): alternatives limited to opted-in suppliers; certificate trust weighting.
- Gemini bounty: agents. Aiven bounty: hosted Postgres. CRACI: CI from day one. Codex: used for scorer tests, noted in commits. Cala: cut.

## 10. Risks and cuts
- Cut order: ArcadeDB time-series stretch, then webhooks (polling only), then weight sliders (fixed weights shown), then route map (distance table only), then audit UI (JSON view).
- Carbon factors are estimates: label every figure as an estimate with its factor source.
- Certificate scraping may be unreliable: keep a pre-fetched fixture set for the demo, with live fetch as the visible extra.
- Synthetic Valio data may lack per-product carbon or coordinates: dummy table fills the gap, labelled.

## 11. Biggest weakness of this proposal
The carbon numbers are rough. Distance times mass times a single road factor ignores packaging, cold chain and mode choice, so a judge who knows life-cycle assessment could challenge them. The ranking is also only as good as its certificate data, and most certificates in the demo will be seeded or fixtures rather than genuinely live.

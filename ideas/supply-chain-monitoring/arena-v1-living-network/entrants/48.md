# Entrant 48: Substitute Finder, Vector-Ranked Alternatives (lens: alternatives via vector similarity)

## 0. Bold bet
The procurement agent never asks a language model to invent a substitute: it runs a hard-filtered vector search over opted-in, published catalogues, then ranks candidates with a transparent weighted score that judges can move with sliders on screen. That turns "find a cheaper, compliant supplier" into a measurable, reproducible query, which is what the Valio exception-handling and buyer-need criteria actually reward.

## 1. Summary and name
- **Substitute Finder**, a module inside a living supply network. Companies declare suppliers, the graph grows through discovery, and the alternatives engine answers "who else can supply this SKU, at what price, how soon, with what trust?"
- Persona: Nordic Harbour Hotels (fictional) buying dairy through Valio Aimo.
- Assumptions: Valio mock exposes product, price, stock and lead time by GTIN. Sustainability certificates are structured fields on the mock product.

## 2. Architecture and DB choice
- **Postgres on Aiven with pgvector** is primary. Vector, relational and visibility rules sit in one transaction, so the filter-then-rank query runs in one round trip. Assumption: Aiven Postgres exposes the `vector` extension; verify on Friday, 15 minutes.
- **ArcadeDB** has native HNSW vector search and is a fallback only if pgvector is unavailable. Splitting vectors into a second store would break the single-query visibility guarantee.
- **Stack:** Next.js (App Router, TypeScript) for UI and API routes. Agents are TypeScript jobs in the same repo, using the Context.dev JS SDK and the Gemini SDK. Single language cuts integration time for four people.
- **Embeddings:** Gemini embedding model, 768 dimensions (assumption: model name and dimension verified on Friday). Embeddings are precomputed when records change, never on the demo critical path.

## 3. Data model and key queries
- `product(gtin pk, name, description, gpc_brick, unit_code, certs text[], allergens text[], jsonld)`, GTIN check digits validated on insert.
- `product_embedding(gtin pk, vec vector(768), text_hash)`. Embedded text: name, description, brick title, certifications, unit. Re-embed only when `text_hash` changes.
- `supplier_offer(id, seller_party_id, gtin, price_min, price_max, currency, unit_code, lead_days, in_stock, published bool, source_url, observed_at)`.
- `party(id, gln null, name, country, opt_in_visible bool)`.
- `edge(seller_id, buyer_id, gtin, trust{inferred,claimed,agreed,audited}, confidence, visibility)`. Trust is derived from `confirmation` rows, not stored by hand.
- `alt_run(id, incumbent_gtin, buyer_id, weights jsonb, created_at)` and `alt_candidate(run_id, gtin, seller_id, sim, score, reasons jsonb)`. Every ranking is persisted, so the audit trail can show why an option was offered.
- **Visibility:** the candidate query reads only `supplier_offer.published` and `party.opt_in_visible`. It never reads `edge`, so a buyer's private supplier map cannot leak into alternatives by construction.

Candidate retrieval (hard filters first, then vector order):
```sql
SELECT o.gtin, o.seller_party_id, o.price_min, o.lead_days, o.in_stock,
       1 - (pe.vec <=> q.vec) AS sim
FROM product_embedding pe
JOIN product p USING (gtin)
JOIN supplier_offer o ON o.gtin = p.gtin AND o.published
JOIN party s ON s.id = o.seller_party_id AND s.opt_in_visible
CROSS JOIN (SELECT vec FROM product_embedding WHERE gtin = :incumbent) q
WHERE p.unit_code = :unit AND p.gpc_brick = ANY(:bricks)
  AND p.allergens @> :required_free AND p.certs @> :required_certs
  AND p.gtin <> :incumbent
ORDER BY pe.vec <=> q.vec LIMIT 50;
```
- `:bricks` is the incumbent brick plus its sibling bricks, one hop in the GPC tree (cross-brick substitution is an exception path, see section 4).

## 4. Agents (discovery, monitoring, procurement)
- **Discovery (live Context.dev).** Input: a supplier's public product page or catalogue URL. Context.dev structured extraction returns product name, description, unit, price and certifications, with `source_url` and `observed_at`. We embed, write `supplier_offer` as `published` only when the page shows a public price (brief rule), otherwise store as `inferred` and hide prices. Output: new candidate visible on the alternatives screen within about 10 seconds of the run.
- **Monitoring.** Context.dev monitors on incumbent product and supplier pages and on recall or strike news. A webhook on change re-extracts the page, updates `supplier_offer.in_stock` and `price_*`, and raises a `risk_signal` if a recall term matches. Gemini classifies the change into a typed record with a confidence score. Fallback: a recorded change replayed through the same webhook path.
- **Procurement.** Trigger: risk signal on incumbent or price premium above threshold. Steps: (1) run the candidate query; (2) rerank (section 5); (3) Gemini writes a one-paragraph rationale that may cite only fields in the candidate record; (4) draft a UBL-shaped order to the best feasible candidate, quantity split across suppliers if stock is partial. Output: `order_draft` in `pending_approval`. Valio mock order is placed only after a manager approves the draft's exact payload hash. Every step writes an `audit_event`.

## 5. Risk engine (alternatives ranking)
Ranking is a weighted score, all terms normalised 0 to 1:
- **Similarity** = cosine, pass only if `sim >= 0.82` (tuned on seed pairs before demo).
- **Price** = `min_price / candidate_price`, using the midpoint when a range is published.
- **Availability** = `min(1, stock / requested_qty)`.
- **Lead time** = `1 - min(lead_days, 7) / 7`.
- **Trust** = 0.4 if `inferred`, 0.7 if `claimed`, 1.0 if `audited` or certified by a field on the product. Proposed switch becomes `claimed` on the buyer's side on approval.
- Default weights 0.35 / 0.25 / 0.20 / 0.10 / 0.10. The UI exposes them as sliders; moving them re-ranks in place through a cached query.
- Price premium risk: `(incumbent_price - best_candidate_price) / best_candidate_price`, shown only when both are published.
- Concentration and geopolitical risks feed the incumbent's penalty, not the candidate score, so the ranking explains itself.

## 6. Screens and graph view
- **Alternatives panel:** table with rank, supplier, sim, price range, unit, lead time, stock, trust badge, source URL chip, and a "why" line from the stored `reasons`.
- **Weight sliders:** live re-rank with the top three visibly swapping.
- **Substitution view:** incumbent vs candidate side by side, with certification and allergen diff.
- **Approval:** draft order, split lines, payload hash, approve or reject.
- **Supply graph (Cytoscape):** arrow direction seller to buyer, dotted `inferred`, solid `claimed`, double `agreed`, thick `audited`; node colour by risk. Alternatives appear as dashed candidate nodes linked to the incumbent's brick, never to the buyer's private edges.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards):** end-to-end order; alternatives with published prices; approval and persisted ranking reasons; partial stock and cross-brick substitution; GTIN validation, UN/ECE Rec 20 units.
- **Context.dev (15%):** live extraction, monitor webhook, source URLs and `observed_at` on every candidate.
- **Trust and privacy (10%):** candidate query never touches `edge`.
- **Concreteness (10%):** SQL, weights, thresholds, timed script.
- **Side bounties:** Gemini (embeddings, rationale, classification), Aiven (Postgres with pgvector), CRACI (CI), Codex if meaningful. Cala skipped.

## 10. Risks and cuts
- **Cut order:** supply graph (keep as static view), ArcadeDB fallback, Exa, Cala, Oxylabs, Modal. Keep candidate query, sliders and approval.
- **Risks:** pgvector unavailable on Aiven (fallback: ArcadeDB HNSW or in-memory cosine over 500 rows, which is fine for demo size). Embedding quality on bilingual Finnish and English names (add translated name field). Synthetic catalogue too small for good neighbours (hand-craft 10 dairy SKUs). Extraction latency on live page (pre-warm the page).

## 11. Biggest weakness of this proposal
The module is strongest on one screen, alternatives. It says little about the wider graph, and the graph is what the brief calls the product. If the supply map looks thin, judges may see an excellent feature rather than a living network. The sanity of embedding-based similarity on a small synthetic catalogue is also not proven until the Friday check.

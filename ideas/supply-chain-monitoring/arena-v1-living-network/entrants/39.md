# Entrant 39: Triage Inbox (lens: alert inbox first, graph as drill-down)

## 0. Bold bet
Every other entrant will open on a map; we open on a ranked inbox of everything that needs a human decision today: risk alerts, agent proposals, edge confirmations and discovery reviews. The graph becomes the explanation behind an inbox item, which keeps the product feeling like a working tool rather than a visualisation, and makes approvals, exceptions and audit the centre of the demo.

## 1. Summary and name
- Name: **Triage**.
- A buyer logs in to a single prioritised inbox. Each card is a decision with a score, a "why now" sentence, source URLs and a deadline. Agents create cards; humans clear them. Approving a proposal places the order through the Valio mock API. Drilling into a card opens the relevant slice of the supply graph.
- Assumptions (labelled): the Valio mock API exposes product, price, availability, lead time, substitution and delivery-day fields. Confirmed in the first Friday hour; if not, we use a local JSON mock with the same shape.

## 2. Architecture and DB choice
- Components: React app (inbox, detail, graph drill-down) → Node/TypeScript API → agent worker (Gemini function calling) → Valio mock client → Context.dev client.
- Store: **Postgres** (Aiven managed) is the single source of truth. Inbox, proposals, orders, edges, visibility and audit all live there. ArcadeDB is cut: the inbox is a relational priority queue and does not need graph storage. Graph queries are recursive CTEs over an `edge` table, which is enough for four hops.
- Realtime: Postgres `LISTEN/NOTIFY` pushes new inbox items to the browser over server-sent events, so a Context.dev hit appears on screen without a refresh.
- Live data: Context.dev monitors POST to `/hooks/context`. A "Scan now" button calls the same handler directly, so the demo does not depend on a public tunnel.

## 3. Data model and key queries
- Tables: `company` (status: registered | unregistered | inferred), `product`, `producer`, `edge` (src, dst, kind, trust, confidence, sources jsonb, visible bool), `inbox_item` (kind, subject_ref, score, why_now, due_at, status, evidence jsonb), `proposal` (lines jsonb, total, ceiling, status), `order_ref`, `audit_event` (payload, prev_hash, hash).
- Trust: column on `edge`. `agreed` requires confirmations from both company IDs. `audited` requires an auditor-account row in `edge_stamp`.
- Visibility: role-scoped views. A buyer reads `v_buyer_risk`, `v_aggregate_usage` (counts over at least five companies, never names), `v_alternatives` (opted-in suppliers only) and `v_published_price`. A company's own edges are never in a buyer view.
- Key queries:
  - Inbox: `SELECT * FROM inbox_item WHERE buyer_id=$1 AND status='open' ORDER BY score DESC, due_at ASC LIMIT 20`.
  - Upstream: `WITH RECURSIVE up(src,dst,depth) AS (SELECT src,dst,1 FROM edge WHERE dst=$valio UNION ALL SELECT e.src,e.dst,up.depth+1 FROM edge e JOIN up ON e.dst=up.src WHERE up.depth<4) SELECT * FROM up;`
  - Hidden concentration: for the buyer's direct suppliers, group by upstream `producer` and keep groups with `count(DISTINCT supplier) >= 2`.
  - Blast radius: producer → products → `par` rows, summed weekly per site.
  - Alternatives: `v_alternatives` joined to `par`, filtered by `lead_time <= window_cutoff`, ordered by published price.

## 4. Agents (discovery, monitoring, procurement)
- **Monitoring**: input: all producers and dairy suppliers. Tools: Context.dev monitors (producer pages, news). Output: `risk` inbox item with severity, source URL and timestamp. Runs every 15 minutes and on webhook.
- **Procurement**: input: open risk item, pars, windows, ceiling. Tools: alternatives query, Valio availability and price calls. Output: `proposal` inbox item with one reason per line. It never submits. Exceptions: partial availability produces a revised proposal item linked to the original; a missed window produces an alternative-day line.
- **Discovery**: input: Valio dairy catalogue. Tools: Context.dev company enrichment and news search. Output: `discovery` inbox items for new inferred producers and edges, each with confidence and two source URLs. Edges with fewer than two sources are discarded before they reach the inbox.
- Human approval: only `proposal` and `confirm` items can place or change anything. Each approval writes an audit event and calls Valio with an idempotency key.

## 5. Risk engine
- Inbox score (0–100) = severity × exposure × urgency.
  - Severity 1–5 by signal type: recall 5, sanction 5, insolvency 4, strike 3, negative news 2.
  - Exposure: euros per week of the chain's par that flows through the affected producer, scaled to 100 at the chain maximum.
  - Urgency: 1.0 if days to stock-out is below supplier lead time, 0.6 if within twice the lead time, otherwise 0.3.
- Types and feeds:
  - Geopolitical: country-risk table plus Context.dev news search.
  - Regulatory: sanctions CSV import; certificate expiry dates on product documents; CSDDD and EUDR flags as seeded attributes (assumption).
  - Concentration: computed from the query in section 3, raised once per upstream producer.
  - Financial: news search for layoffs or insolvency, Context.dev company fields.
  - Live events: recall and strike pages from monitors.
  - Price premium: only when the seller has published a price; raised when the current price exceeds the cheapest opted-in alternative by more than 8%.
- Each card carries the top three source URLs and a one-sentence "why now".

## 6. Screens and graph view
1. **Inbox** (home): filter chips (Risks, Approvals, Confirm, Discovery). Cards show score, kind, "why now", deadline and sources. A count header reads "3 need a decision today".
2. **Item detail**: evidence, sources, and the actions that apply to this kind.
3. **Proposal review**: lines with reasons, per-line accept or reject, total against ceiling, one Approve button, and the Valio order reference.
4. **Confirm page** (phone): a supplier confirms an edge (claimed → agreed). The auditor account stamps an edge (audited).
5. **Audit log**: hash-chained event timeline with a "verify chain" button.
6. **Graph drill-down**: opens from any card, centred on that card's subject. Edge style encodes trust (dashed inferred, solid claimed, double agreed, badged audited). Red halo marks risk. Arrows show direction. Other companies' upstream links are not drawn.

## 7. Demo script (4 min)
- 0:00–0:30 Login. Inbox shows three decisions: a red risk, a proposal, a discovery.
- 0:30–1:05 Risk card arrives live: a Context.dev monitor fires on a real dairy news page. Source URLs visible.
- 1:05–1:50 Drill into the risk: graph opens centred on the upstream producer. Concentration card: three direct suppliers share one co-op.
- 1:50–2:30 Proposal card: alternatives with published prices, one partial-availability line revised automatically.
- 2:30–3:05 Approve. Valio mock order placed, audit event appended, order reference shown.
- 3:05–3:30 Phone: supplier confirms edge (claimed → agreed). Auditor stamps it (audited).
- 3:30–4:00 Discovery card: new inferred producer with confidence and URLs. Accept creates the edge.
- Backup: pre-recorded video following the same beats.

## 9. Judging-criteria mapping
- Valio end-to-end (30%): inbox approval results in a real mock order with an audit trail.
- Buyer need (20%): a single prioritised queue matches how a procurement manager works.
- Autonomy and controls (20%): agents only write inbox items; approval gates; hash-chained audit.
- Exceptions (15%): partial availability revised proposal; window miss alternative day.
- Open standards (15%): JSON proposal schema, OpenAPI description of the Valio client, Postgres.
- Context.dev (15%): monitors and discovery feed the inbox live, with source URLs.
- Side bounties: Gemini (agent LLM), Aiven (Postgres and runtime), CRACI (CI runner, low effort). Cala skipped.

## 10. Risks and cuts
- Cut first: ArcadeDB, Kafka, Cala, full-network graph. Keep only the drill-down ego graph.
- Biggest technical risks: Valio mock schema unknown (checked Friday); webhook tunnel failure (scan button fallback); LLM latency (cached proposal for the seeded scenario).

## 11. Biggest weakness of this proposal
The inbox is a strong buyer workflow but can feel like a task app, so judges may not see the living network unless the discovery card and drill-down land well. Our fallback is to make the graph drill-down open automatically on the first risk card.

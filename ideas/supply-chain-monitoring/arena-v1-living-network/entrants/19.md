# Entrant 19: ChainCheck, Sanctions-First Chain Screen (lens: Sanctions screening first)

## 0. Bold bet
Every company in the graph, including every upstream company behind Valio's suppliers, is screened against real open sanctions data (OpenSanctions plus the EU Financial Sanctions File) on every edge change and on a schedule. The demo's first alert is a traceable compliance fact with a source URL, not an LLM guess, and that is the hardest part of the brief for a rival to fake.

## 1. Summary and name
- Name: **ChainCheck**.
- Product: a living supply-chain graph where each company carries a sanctions and ownership screen across its whole upstream closure. Buyers see risk warnings, aliases and opted-in alternatives. They never see a seller's private map. Agents discover, monitor and propose switches; a manager approves each order, which goes to the Valio mock API.
- Assumptions: OpenSanctions bulk data is usable for the hackathon under its non-commercial terms. A commercial licence is needed for production, and we say so in the pitch. The EU FSF is available as a bulk XML download, or via OpenSanctions dataset `eu_fsf` if the direct download is awkward.

## 2. Architecture and DB choice
- **Primary store: Postgres on Aiven** with `pg_trgm` and `unaccent`. Upstream traversal uses recursive CTEs, depth capped at 6, with a path array to stop cycles. Fits one query language, one engine, one managed service.
- **ArcadeDB: stretch only.** Blast-radius queries can move to Cypher on Sunday morning if the core is done. Not on the critical path, because running a second store doubles the failure modes.
- Components: Next.js UI; FastAPI backend; `screen` worker in the same repo; agents as Gemini function-calling loops; Context.dev SDK for enrichment, news and monitors; Valio mock API client.
- Flow: edge write, then enqueue screen jobs for both endpoints and the upstream closure, then match against the `sanction_entity` index, then write `screening_run` and `risk_signal`, then push to the UI over SSE.
- Index loader (script, run once plus a daily delta): reads OpenSanctions FollowTheMoney JSON for `sanctions` and `eu_fsf`. Keeps Organization, Company, LegalEntity, Person, plus Ownership and Directorship. Stores name, normalised name, aliases, country, reg_no, dataset, source_url and dataset version.

## 3. Data model and key queries
- `company(id, name, norm_name, country, reg_no, domain, registered, optin_visible)`
- `supply_edge(id, from_id, to_id, kind, trust, confidence, sources jsonb, declared_by, confirmed_by, audited_by)`. `trust` is one of inferred, claimed, agreed, audited.
- `sanction_entity(...)` as above, plus `ownership(owned_id, owner_id, share)`.
- `screening_run(id, company_id, dataset_version, score, status, created_at)`
- `sanction_hit(id, run_id, sanction_entity_id, score, method, decision, reviewed_by)`
- `risk_signal(id, company_id, type, severity, score, source_urls jsonb, trust, created_at)`
- **Visibility is enforced in SQL views, not the UI.** `v_buyer_edges` returns only edges where the buyer is `to_id`, plus edges from registered suppliers that the seller chose to show. A seller's private map never reaches a buyer query. `v_public_alternatives` filters on `optin_visible` and published prices only.

Queries:
```sql
-- Upstream closure of :root with depth and cycle guard
WITH RECURSIVE up(id, depth, path) AS (
  SELECT e.from_id, 1, ARRAY[e.to_id, e.from_id] FROM supply_edge e WHERE e.to_id = :root
  UNION ALL
  SELECT e.from_id, up.depth+1, up.path || e.from_id
  FROM up JOIN supply_edge e ON e.to_id = up.id
  WHERE up.depth < 6 AND NOT (e.from_id = ANY(up.path))
) SELECT id, MIN(depth) AS depth FROM up GROUP BY id;

-- Sanctions candidates on that closure (score = 0.7 name + 0.2 country + 0.1 reg_no)
SELECT c.id, s.id, similarity(c.norm_name, s.norm_name) AS sim
FROM company c JOIN sanction_entity s ON s.norm_name % c.norm_name
WHERE c.id IN (SELECT id FROM up) AND similarity(c.norm_name, s.norm_name) >= 0.6;
```
- **Hidden concentration:** run the closure per direct supplier, then `GROUP BY upstream_id HAVING COUNT(DISTINCT direct_supplier) >= 2`.
- **Blast radius:** reverse closure from a failed node, returning downstream buyers with depth.
- **Alternatives:** supplier edges in the same category, `optin_visible = true`, price published, and a clean chain screen. Order by price midpoint.

## 4. Agents (discovery, monitoring, procurement)
- **Discovery.** Inputs: root company, Valio supplier list, a free-text name typed live by the judge. Tools: Context.dev company enrichment and news search (method names to verify on day 1); OpenSanctions screen. Output: new company as unregistered, edge as `inferred` with confidence and URLs. Validation: at least two source URLs or one official register entry. Screen before insert. A hit does not block the insert but raises a `risk_signal` and a review item.
- **Monitoring.** Triggers: daily OpenSanctions delta (assumption: versioned delta files exist); Context.dev monitors with webhooks on supplier domains for sanctions, recall, insolvency and strike keywords; a manual "re-screen chain" button. Output: `screening_run` and `risk_signal`. Each signal stores URL plus a snapshot hash.
- **Procurement.** Trigger: severity at or above high on an upstream node the buyer depends on. Gates in order: (1) alternative passes the full-chain screen; (2) `optin_visible`; (3) published price; (4) human approval row written by the manager. Only then does the Valio mock order call run. Each step is logged.

## 5. Risk engine
- **Sanctions (primary):** name match on every closure node, plus ownership hop depth 2 (owner at 50% or more of a listed entity is a labelled indicator, not a legal finding). Score = match score x 100. At 90 or above: critical. 75 to 90: review queue.
- **Compliance:** certification expiry from Valio catalogue attributes. CSDDD flag from supplier declaration. EUDR does not apply to dairy, and we do not claim it does.
- **Geopolitical:** static country table with cited sources, plus news keywords from Context.dev.
- **Concentration:** shared-upstream and single-source queries from section 3.
- **Financial health:** Context.dev enrichment changes (headcount drop, insolvency news). Assumption: enrichment exposes these fields.
- **Live events:** Context.dev news monitor on supplier names.
- **Price premium:** Valio price against opted-in alternatives, only where prices are published.
- Severity is the max of critical signals, else a weighted sum. Every signal shows its trust level. A sanctions hit changes risk, not edge trust.

## 6. Screens and graph view
1. Hotel home: chain nodes screened, open hits, open alerts, last dataset version.
2. Supply map (Cytoscape.js): incoming edges left, outgoing right. Edge style by trust: dashed inferred, solid claimed, double agreed, thick audited. Node badges: red sanctions, amber risk, grey unregistered. Hover shows confidence and source URLs.
3. Alert detail: "Nordic Dairy Co-op (DEMO)" with owner chain, match score, list entry, source link and dataset version. Buttons: false positive, confirm, escalate.
4. Alternatives: cards with price range, certificates, opt-in badge and "screened clean" badge.
5. Approval: proposal, evidence, approve or reject.
6. Audit log: timeline of screens, agent runs, approvals and orders, each with dataset version.
7. Supplier view: confirm edge (claimed to agreed). Auditor view: stamp (agreed to audited).

## 7. Demo script (about 4 minutes)
- **0:00–0:25** Hook: "Sanctions lists check your direct supplier. Nobody checks the dairy behind the dairy." Valio at the centre.
- **0:25–1:00** Hotel login. Supply map, trust styles, and a note that the seller's private map stays hidden.
- **1:00–1:40** Risk alert on the upstream dairy producer. Red badge, ownership chain, match score, OpenSanctions source URL and dataset version. We use a DEMO overlay entity in a clearly marked list, so no real company is shown as listed.
- **1:40–2:10** Live beat: judge types a new supplier name. Context.dev enriches it, the screen runs, and the node appears as `inferred` with confidence and URLs. Target: under 10 seconds.
- **2:10–2:40** Supplier confirms edge (claimed to agreed). Simulated auditor stamps it audited.
- **2:40–3:20** Procurement agent proposes a substitute: opted in, price range, screened clean. Manager approves, Valio mock order is created, order ID shown.
- **3:20–3:50** Exception: partial availability. A substitute that fails the chain screen is rejected, with the reason in the log.
- **3:50–4:00** Close: production path (commercial licence, delta feed).

## 9. Judging-criteria mapping
- **Valio (30%):** approval-gated order through the mock API. Guardrails: full-chain screen gate and audit log. Buyer need: upstream exposure. Exceptions: substitutes must pass the same screen. Open standards: FollowTheMoney schema, plus a licence path to production.
- **Feasibility (25%):** Postgres only, bulk files, demo overlay guarantees the story.
- **Context.dev (15%):** enrichment, news and webhook monitors in the core flow, plus the live beat.
- **Trust and privacy (10%):** sanctions hits change risk, not edge trust. Buyers see warnings only. Alternatives are opt-in.
- **Concreteness (10%):** queries and screen states above.
- **Side bounties (10%):** Gemini, Aiven, Codex, CRACI. Cala skipped: no founder or investor angle in the core.

## 10. Risks and cuts
- Cut order: ArcadeDB stretch, price premium, ownership hop (keep direct name match), Codex log, live news monitor (fall back to a manual refresh).
- Risks: fuzzy false positives on common Finnish names (mitigate with country and reg_no weighting and a review queue); OpenSanctions licence terms; Context.dev latency or rate limits (cache results, pre-warm the live target); EU FSF file format changes; defamation if real listed names appear as suppliers (DEMO overlay only in the demo).

## 11. Biggest weakness of this proposal
Name-based screening is a weak substitute for identifiers. Without VAT or business IDs, the demo depends on the match score, and a judge may spot a false positive or a missed hit. The ownership signal is an indicator, not a legal finding. The screen is only as current as the dataset version we loaded, so a stale load would undercut the "live" claim.

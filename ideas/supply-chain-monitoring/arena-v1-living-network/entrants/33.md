# Entrant 33: Tripwire (lens: Change-detection monitors)

## 0. Bold bet
Risk is treated as a change event, not a snapshot: every watched supplier page or news query is a Context.dev monitor, and a webhook turns a page edit into a classified, sourced, upstream-routed alert in under 15 seconds. We win the real-timeness and live-data criteria with a demo the judges trigger themselves, and the procurement gate stays human.

## 1. Summary and name
- **Tripwire**: a supply-chain network where risk is detected by watching the public surfaces of companies (recall pages, certification pages, news, status pages) and reacting to what changes. A hotel buyer gets an alert on an upstream dairy producer within seconds, with the source diff and URL, then sees priced alternatives and approves a switch that goes to Valio's mock API.
- Assumptions: Context.dev monitors fire a webhook with the page URL, the changed text or diff, and a timestamp. The payload shape is unverified, so the ingest adapter is written against a saved sample on Friday. Webhook signing is assumed; if absent, we use a shared path secret.

## 2. Architecture and DB choice
- **ArcadeDB primary** for graph, `Watch`, `ChangeEvent` and `RiskSignal` documents, plus signal history as time-series. One store for traversal and signal storage.
- **Pipeline:** Context.dev monitor → `POST /hooks/ctx` (ingest, store raw payload in `ChangeEvent`, idempotency key) → queue (Aiven Valkey if it provisions in time, else an in-process queue with the same interface) → monitoring agent (Gemini) → risk scoring → upstream fan-out → privacy filter → SSE push to UI and procurement trigger.
- Hosting: app on Aiven Runtime. Demo supplier pages are hosted on the same Runtime, so they are public URLs that Context.dev can really monitor.
- Fallback: if Valkey is not available, the in-process queue stays. If ArcadeDB is unstable, the same schema moves to Postgres; the pipeline code uses a repository interface.

## 3. Data model and key queries
Vertices:
- `Watch {id, company_did, url, kind: recall|cert|news|status|site, ctx_monitor_id, last_hash, interval_s}`
- `ChangeEvent {id, watch_id, event_key, received_at, source_url, diff_excerpt, raw_ref, status: new|classified|dropped|routed}`
- `RiskSignal {id, company_did, risk_type, severity 1-5, confidence, evidence_url, quote, effective_date, valid_until, change_event_id, created_at}`
- `Company {did, name, country, sector, registered, opted_in, published_prices}`

Edge `SUPPLIES {trust_level, confidence, sources[]}` with trust levels as in the brief. Trust is shown on the edge, not used to suppress alerts: an inferred edge still routes a risk, marked as inferred.

Idempotency: `event_key = sha256(watch_id + diff_hash)`. A repeated webhook with the same key is dropped and logged.

Key queries (Cypher sketch, verify in ArcadeDB on Friday):
- Buyers affected by a supplier change: `MATCH p=(s:Company {did:$changed})-[:SUPPLIES*1..4]->(b:Company {registered:true}) RETURN b.did, min(length(p)) AS tiers`
- Latest signal per company: `MATCH (r:RiskSignal {company_did:$did}) WHERE r.valid_until > $now RETURN r ORDER BY r.created_at DESC LIMIT 5`
- Hidden concentration: `MATCH (b:Company {did:$me})<-[:SUPPLIES]-(d)<-[:SUPPLIES]-(u) WITH u, collect(DISTINCT d.name) AS via WHERE size(via) >= 2 RETURN u, via`
- Alternatives: `opted_in` companies in the sector, joined to published prices only.

## 4. Agents (discovery, monitoring, procurement)
- **Monitoring (this lens).** Input: a `ChangeEvent` with diff text and source URL. Gemini structured output: `{is_risk_event, risk_type, severity, confidence, effective_date, quote}`. Validation: `quote` must be a substring of the diff text and the source URL must match the watch. Failures are stored as `dropped` with reason, so judges can see rejected noise. Output: `RiskSignal`, signed by the monitor's `did` for provenance.
- **Monitor registry.** On watch creation, the API calls Context.dev to create a monitor for the URL and stores `ctx_monitor_id`. Interval 5 minutes as a backup poll. Monitors are created once per URL on Friday and reused, so the demo has no setup latency.
- **Discovery (supporting).** Exa news search plus Context.dev company enrichment seed new `inferred` edges with source URLs; each new company gets its own watch on its status or news page, so discovery feeds monitoring.
- **Procurement.** Subscribes to `RiskSignal` with severity ≥ 4 or a published-price premium. Builds an `OrderProposal` from Valio mock product, availability and lead-time lookups, plus opted-in alternatives. The manager approves in the UI; approval is recorded with the proposal hash and a 15-minute expiry. The Valio client places the order only with a valid approval record.

## 5. Risk engine
The engine is mostly the monitoring agent's classifier, with deterministic rules layered on top:
- **Live events (primary):** recall, strike, outage and negative news from watched pages. Severity from Gemini, floor 4 for recalls.
- **Regulatory:** certification pages with expiry dates. A rule raises severity to 4 when `valid_until` passes, and the watch fires a re-check.
- **Geopolitical:** news watches on a country or port query. Severity capped at 3 unless a sanctions snapshot match exists.
- **Financial:** news and status pages for layoffs or insolvency keywords, classified by Gemini. Optional Cala lookup for funding data if time allows.
- **Concentration:** computed from the graph, not from web changes. Shared upstream triggers a signal when a new supplier added by discovery matches an existing one.
- **Price premium:** only published prices; shown as a signal, not an alert.
- Score = severity × confidence × recency. Alert threshold is severity ≥ 3 and confidence ≥ 0.6.

Privacy at fan-out: the buyer receives the risky company's name, the evidence URL and the tier count. The intermediate chain and other customers are never sent.

## 6. Screens and graph view
1. **Watch wall (ops view):** each watch with its last check, last hash change and status. Used by judges to see real monitoring.
2. **Supply map:** upstream on the left, Valio at centre, customers right. Dashed edges are claimed, dotted are inferred with confidence. Red overlay marks nodes with an open signal; severity sets the ring width.
3. **Alert feed (live):** newest first, with `detected in N s`, source URL, diff excerpt and the quote highlighted. Each card links to the `ChangeEvent`.
4. **Alert detail:** risk type, severity, evidence, tier count, and the Proposed switch button.
5. **Approval:** current versus proposed supplier, price range, lead time, Approve button, approval record shown.
6. **Change log:** raw webhook payloads, dropped events and reasons, and a Replay button that re-runs a stored payload through the pipeline.

## 7. Demo script (timed beats, ~4 min)
- 0:00–0:20: pitch. "Supplier risk changes on a web page before it reaches a dashboard."
- 0:20–0:50: supply map as the hotel chain. Watch wall shows 12 live monitors, each with a last-checked time.
- 0:50–1:30: **live trigger.** The presenter edits the hosted "recall notice" page for an upstream dairy producer. Context.dev fires the monitor. The alert card appears with `detected in ~10 s`, the diff excerpt and the source URL.
- 1:30–2:00: open the alert. Tier count is 2. Show that the intermediate's other customers are hidden (privacy rule).
- 2:00–2:30: procurement proposal with visible alternatives and price ranges (opt-in and published only).
- 2:30–3:00: manager approves. Valio mock accepts the order after checking the approval record. Change log shows the full chain.
- 3:00–3:30: **live discovery run** with Exa and Context.dev. A new inferred supplier appears with source URLs, and its status page gets a watch automatically.
- 3:30–4:00: exception: the replay button re-runs a rejected payload to show the grounding check dropping a hallucinated quote.
- Backup: if the live edit fails, the Replay button runs the stored payload from the first rehearsal, and the pre-recorded clip is the last fallback.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards):** full flow in the demo. Need: the buyer gets early warning and alternatives. Controls: approval record gates the order, and every step is in the change log. Exceptions: the grounding check rejects bad signals, and a replay shows it. Standards: webhooks and JSON payloads, plus a clean order interface.
- **Context.dev (15%):** monitors and webhooks in the core flow, live edit to alert in about 10 s, every alert cites the diff URL. Real-timeness is the centre of the demo.
- **Trust and privacy (10%):** trust level shown on each edge; buyer alerts omit the intermediate chain.
- **Concreteness (10%):** schemas, queries, payload handling and timings above.
- **Side bounties (10%):** Gemini (classifier), Aiven (Runtime hosting, Valkey queue), Codex (ingest tests and mock), CRACI (SBOM CI). Cala optional for funding data only.

## 10. Risks and cuts
- Cut order: Cala, Oxylabs, Modal/Verda, Exa Monitors, the price-premium signal, the concentration signal from discovery. Never cut: the live webhook beat, the grounding check, the approval gate.
- Risks: Context.dev monitor latency or payload shape (mitigated by the Friday capture and a replay fallback). Rate limits on monitor creation (create all monitors Friday). Gemini output variance (structured schema plus a rule fallback). Live edit failing on stage (replay plus clip).
- The pipeline is the critical path. Keep the in-process queue unless Valkey provisions cleanly by Saturday noon.

## 11. Biggest weakness of this proposal
The whole story depends on Context.dev monitor behaviour we have not verified: timing, payload shape and whether a text edit on our own page triggers it reliably. If the live beat fails on stage, the demo leans on replay and a recording, and the judges may see a scripted demo. The Valio side is thinner than the monitoring side, so the order flow must be kept simple.

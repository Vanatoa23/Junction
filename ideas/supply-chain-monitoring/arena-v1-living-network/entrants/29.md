# Entrant 29: Chainwright, Python API and Agents with a Typed React Front (lens: Python FastAPI backend + React/Vite frontend split)

## 0. Bold bet
The API contract is the product's spine: Pydantic models in FastAPI generate one OpenAPI file on Friday, and the React app compiles against generated TypeScript types, so the two halves never block each other. All agents, data and risk logic live in one Python codebase, which gives judges one auditable place to read what the system does.

## 1. Summary and name
- **Chainwright**: a living supply network where companies and edges are stored as typed records, trust levels are derived from confirmations, and agents run as Python jobs that propose, but never place, orders.
- Demo persona: Nordic Harbour Hotels (fictional) buying through Valio Aimo.
- Assumptions: Valio mock API is REST/JSON with product, availability and order endpoints. Its shape is pinned in a local `valio_mock.yaml` we write on Friday.

## 2. Architecture and DB choice
- **Components:**
  - `api/`: FastAPI, SQLAlchemy 2.0, Alembic. Serves REST and webhooks.
  - `agents/`: plain Python worker process, polling a `job` table. Gemini via `google-genai` with Pydantic response schemas.
  - `web/`: React 18, Vite, TanStack Query, Cytoscape.js for the graph, `openapi-typescript` for types.
  - `contracts/openapi.yaml`: generated from FastAPI, committed, the only shared artefact between web and api.
- **Database: Postgres on Aiven.** Relational tables for identity, edges and orders; JSONB for evidence and UBL/JSON payloads; recursive CTEs for upstream and downstream traversal at demo scale. Aiven also gives the side bounty.
- **ArcadeDB: not used on the critical path.** Its supply-chain Cypher examples can be a stretch dashboard if the core is green by Sunday 09:00. Two primary stores would split the team's debugging time.
- **Job queue:** Postgres `job` table with `SELECT ... FOR UPDATE SKIP LOCKED`. No Kafka, no Celery.
- **Flow:** Context.dev webhook to `POST /webhooks/contextdev` writes `event` and enqueues a `monitor` job. Worker classifies, writes `risk_signal`, enqueues `procure` on threshold. Procurement writes `order_draft` in `pending_approval`. The UI approves through `POST /orders/{id}/approve`, which enqueues `place_order`.

## 3. Data model and key queries
- **Tables (SQLAlchemy models mirror Pydantic schemas one-to-one):**
  - `party(id, gln char13 unique null, name, country, vat_id, status{unregistered,invited,registered}, opt_in_visible bool)`
  - `product(gtin char14 pk, name, gpc_brick, unit_code)`
  - `edge(id, seller_id, buyer_id, gtin null, confidence null, visibility)`, unique per (seller, buyer, gtin)
  - `confirmation(edge_id, party_id, role{seller,buyer,auditor}, at)`
  - `trust`: a column on `edge`, recomputed in the service layer on every confirmation insert, in one function `derive_trust(edge)` with unit tests. Never set by hand.
  - `evidence(id, subject_type, subject_id, source_url, retrieved_at, excerpt, agent_run_id)`
  - `price_publication(gtin, seller_id, price_min, price_max, currency, unit_code, published)`
  - `risk_signal(id, party_id, kind, severity, confidence, score, evidence_id, status)`
  - `order_draft(id, buyer_id, seller_id, payload jsonb, payload_sha256, status, approved_by, approved_hash)`
  - `audit_event(id, ts, actor, verb, object_ref, body jsonb)`, append-only, enforced by a revoked UPDATE/DELETE grant
- **Visibility is enforced in the API layer:** a FastAPI dependency `scope_for(viewer)` returns a SQL view that exposes only the viewer's edges, risk signals on upstream parties, aggregates, opted-in alternatives and published prices. Routes never query base tables directly. Pytest asserts that a private edge of another party never leaks.
- **Upstream traversal:**
```sql
WITH RECURSIVE up AS (
  SELECT seller_id, buyer_id, 1 d, ARRAY[buyer_id, seller_id] p, seller_id hop1
  FROM edge WHERE buyer_id = :b
  UNION ALL
  SELECT e.seller_id, e.buyer_id, up.d+1, up.p || e.seller_id, up.hop1
  FROM edge e JOIN up ON e.buyer_id = up.seller_id
  WHERE up.d < 5 AND NOT e.seller_id = ANY(up.p))
SELECT seller_id, count(DISTINCT hop1) AS via FROM up GROUP BY seller_id HAVING count(DISTINCT hop1) >= 2;
```
- **Blast radius:** the same recursion run downstream from a failing party, joined to `order_line` volumes.
- **Alternatives:** `price_publication` joined on `gpc_brick`, filtered to `opt_in_visible` and `published`, ordered by `price_min`.

## 4. Agents (discovery, monitoring, procurement)
- **Shared contract:** each agent is a Python function `run(job) -> AgentResult`, where `AgentResult` is a Pydantic model. Every item carries `source_url`, `retrieved_at` and `confidence`. Below 0.6 becomes a candidate, not an edge. Every tool call writes `audit_event`.
- **Discovery:** Inputs: seed list, Context.dev company enrichment, news search, structured JSON extraction of supplier pages. Output: `party` (unregistered) and `edge` (`inferred`, confidence, URLs). Validation: GS1 mod-10 check on GLN/GTIN. Web sources never create a GLN (assumption: GEPIR access is unavailable).
- **Monitoring:** Context.dev monitors plus webhooks on supplier pages and news queries. Gemini returns a typed `RiskClassification`. Sanctions match against an offline EU and OFAC snapshot using normalised name and country (assumption).
- **Procurement:** Inputs: risk signal, alternatives, Valio mock stock and prices. Output: UBL 2.1 Order payload with Peppol customisation ID (verify before demo) and UN/ECE Rec 20 units, serialised as JSON for the Valio mock (assumption: it accepts JSON). Partial availability substitutes within the same GPC brick. Human approval: the POST happens only when `approved_hash == payload_sha256`.

## 5. Risk engine
- `score = severity x confidence x recency x exposure`, exposure being the buyer's spend share via that party. Upstream propagation at 0.5 per hop. Implemented as one pure Python module with table-driven tests.
- **Geopolitical:** hand-set country index (assumption) plus Context.dev regional news.
- **Regulatory:** sanctions hit scores 100 after normalisation. Certificate expiry from evidence. EUDR flags palm, soy and cocoa HS codes upstream. CSDDD is flagged, not scored.
- **Concentration:** shared upstream from the query above; score is supply share through it.
- **Financial:** insolvency, layoffs or restructuring keywords, plus headcount delta from enrichment.
- **Live events:** recall feed snapshot (assumption) and strike news.
- **Price premium:** (seller price minus cheapest published alternative) / cheapest, only where published.

## 6. Screens and graph view
- **Supply map:** arrows seller to buyer. Dotted `inferred`, solid `claimed`, double `agreed`, thick with badge `audited`. Confidence % on the label. Node colour by risk. Dashed outline for `unregistered`.
- **Risk inbox:** cards with score, reason and source-URL chips.
- **Alternatives:** opted-in suppliers, price range, unit, lead time, certificates.
- **Approval:** UBL/JSON preview, diff, payload hash, approve or reject.
- **Audit timeline:** every agent step with its evidence link.
- **Supplier confirm page** and **auditor stamp page**, both simple forms.
- **Discovery log:** live run output with URLs.

## 7. Demo script (4 min)
- **0:00–0:20** Pitch the contract-first split and the one-codebase agents.
- **0:20–0:50** Hotel login, supply map, trust legend, click an edge for evidence.
- **0:50–1:20** Live discovery: Context.dev pulls a real dairy supplier page, the agent writes an `inferred` node with URL and confidence.
- **1:20–1:45** Supplier confirms in a second window: `claimed` becomes `agreed` live.
- **1:45–2:15** Risk card from the monitor webhook (staged replay if needed) with a shared-upstream warning.
- **2:15–2:45** Alternatives: opted-in only, published ranges. A private supplier is absent.
- **2:45–3:20** Procurement draft, diff, manager approval, hash check, Valio mock POST, partial-stock substitution.
- **3:20–3:40** Auditor stamps `audited`, audit timeline shown.
- **3:40–4:00** Blast-radius query and production path.

## 9. Judging-criteria mapping
- **Valio (30% demo, 20% need, 20% controls, 15% exceptions, 15% standards):** full chain demo; alternatives with published prices; approval hash and append-only audit; substitution within GPC brick; GLN, GTIN, UBL-shaped orders, UN/ECE Rec 20, ISO 3166 and 4217.
- **Context.dev (15%):** live discovery, monitors with webhooks, sourced news.
- **Trust and privacy (10%):** scope views and pytest leak tests.
- **Concreteness (10%):** SQL, OpenAPI contract, timed script.
- **Side bounties:** Gemini (agents), Aiven (Postgres), CRACI (CI), Codex if meaningful. Cala skipped.

## 10. Risks and cuts
- **Cut order:** ArcadeDB, Exa, Cala, Oxylabs, Modal, live webhook (use replay).
- **Keep:** contract, approval gate, append-only audit, Context.dev discovery.
- **Risks:** Valio mock shape differs from `valio_mock.yaml` (adapter layer absorbs it). Monitor latency (replay). Gemini schema drift (validate and retry once). Contract drift between web and api (regenerate types in CI).

## 11. Biggest weakness of this proposal
Four engineers split across a Python backend, a Python worker and a React app means the contract must be frozen by Saturday night; if it slips, the front end builds against mocks that drift from the API. The Python agent stack is also less visually impressive than a graph-native store on screen.

# Entrant 53: Network Built Like Software (lens: dev workflow bounties)

## 0. Bold bet
We treat the supply-chain network as a software supply chain: every edge, risk signal and order carries a provenance record, and every agent run is a build step with inputs, tools and outputs hashed and visible. The same pipeline that ships our app (CRACI CI with SBOM and vulnerability scan, Codex-assisted development) runs on rails the judges can see in one screen, so the bounty stack is part of the demo rather than a side slide.

## 1. Summary and name
- Name: **Provenance Net**.
- A hotel-chain procurement manager sees its supply map, a risk alert on an upstream dairy producer, visible alternatives with price ranges, and an agent-proposed switch. One human approval places the Valio mock order. Every edge and decision shows its provenance: which agent run created it, which sources it used, and its trust level.
- Assumptions (labelled): Valio mock API exposes product, price, availability, lead time and substitution fields. SBOM generation uses CycloneDX output from a standard open-source generator (assumption on the exact tool; confirm Friday). CRACI runners accept our GitHub Actions workflow unchanged (assumption).

## 2. Architecture and DB choice
- Components: React app → Node/TypeScript API → agent worker (Gemini function calling) → Valio client (generated from the mock's OpenAPI description) → Context.dev client.
- Store: **Postgres** on Aiven. Single store for network, visibility, proposals, orders, provenance and audit. ArcadeDB is not used: the core queries are four-hop traversals that a recursive CTE handles, and a second database adds setup risk.
- Dev workflow: one monorepo, one GitHub Actions workflow on CRACI runners. Steps: install, typecheck, unit tests, seed-fixture validation against JSON Schema, build, CycloneDX SBOM, vulnerability scan, deploy to Aiven Runtime on green. The deploy step is the only one that can be skipped during the demo, so CI never blocks a live change.
- Codex: used for the Valio client from the OpenAPI spec, seed-data generation, and test scaffolding. Keep a short `CODEX.md` log of which modules were generated, reviewed and edited, to support the bounty claim.

## 3. Data model and key queries
- Tables: `company` (registered | unregistered | inferred), `edge` (src, dst, kind, trust, confidence, sources jsonb, visible bool, provenance_run_id), `product`, `producer`, `par`, `window`, `risk_signal`, `proposal`, `order_ref`, `agent_run` (id, agent, input_hash, tools jsonb, output_hash, started_at, model), `audit_event` (prev_hash, hash).
- Trust is a column on `edge`. `agreed` requires confirmation rows from both companies. `audited` requires a row in `edge_stamp` from the simulated auditor account.
- Provenance: every `edge`, `risk_signal` and `proposal` points to an `agent_run` or a human action. The hash chain in `audit_event` makes tampering visible.
- Visibility: buyer-scoped views only. `v_buyer_risk`, `v_aggregate_usage` (counts over at least five companies, no names), `v_alternatives` (opted-in suppliers), `v_published_price`. A company's own edges never appear in a buyer view.
- Key queries:
  - Upstream: `WITH RECURSIVE up AS (SELECT src,dst,1 AS d FROM edge WHERE dst=$valio UNION ALL SELECT e.src,e.dst,up.d+1 FROM edge e JOIN up ON e.dst=up.src WHERE up.d<4) SELECT * FROM up;`
  - Hidden concentration: buyer's direct suppliers grouped by upstream `producer`, keeping groups with `count(DISTINCT supplier) >= 2`.
  - Blast radius: producer → products → `par` rows, summed per site per week.
  - Alternatives: `v_alternatives` joined to `par`, filtered by `lead_time <= window.cutoff`, ordered by published price.

## 4. Agents (discovery, monitoring, procurement)
- Each agent run is a recorded build step: inputs are hashed, tool calls logged, outputs hashed and written to `agent_run`.
- **Discovery**: input: Valio dairy catalogue. Tools: Context.dev company enrichment and news search. Output: `inferred` producers and edges with confidence and two source URLs. Edges with fewer than two sources are rejected at validation.
- **Monitoring**: input: producers and dairy suppliers. Tools: Context.dev monitors and webhooks on producer pages and news. Output: `risk_signal` with severity 1–5 and source URL. Runs every 15 minutes and on webhook.
- **Procurement**: input: risk signal, pars, windows, ceiling. Tools: alternatives query, Valio availability and price calls. Output: `proposal` with one reason per line. It never submits. Partial availability produces a linked revised proposal; a missed window produces an alternative-day line.
- Human approval: only approval of a `proposal` calls Valio, with an idempotency key, and writes an audit event.

## 5. Risk engine
- Score = severity × exposure × urgency, 0–100.
  - Severity: recall 5, sanction 5, insolvency 4, strike 3, negative news 2.
  - Exposure: weekly chain par value passing through the affected producer, scaled to the chain maximum.
  - Urgency: 1.0 if days to stock-out is below supplier lead time, 0.6 within twice lead time, else 0.3.
- Feeds: geopolitical from country-risk table and Context.dev news; regulatory from sanctions CSV, certificate expiry dates, seeded CSDDD and EUDR flags (assumption); concentration from the query above; financial from news and company fields; live events from monitors; price premium only when the seller publishes a price and the current price is more than 8% above the cheapest opted-in alternative.
- Each risk card carries three source URLs and its `agent_run` id.

## 6. Screens and graph view
1. **Home / supply map**: Valio-centred graph with one hotel's view. Edge style shows trust: dashed inferred, solid claimed, double agreed, badged audited. Red halo marks risk.
2. **Risk alert**: signal, sources, affected dish and hotels, "Ask procurement agent".
3. **Alternatives**: opted-in suppliers, trust badge, published price range, lead time against window.
4. **Approval**: proposed lines, reasons, total against ceiling, Approve, Valio order reference.
5. **Provenance panel** (opens on any edge or card): trust level, confidence, source URLs, agent run id, input and output hashes, tool calls.
6. **Build panel** (footer link): latest CI run, SBOM component count, vulnerability scan result, and the Codex-assisted modules listed in `CODEX.md`.

## 7. Demo script (4 min)
- 0:00–0:25 Hotel login. Supply map with trust styling.
- 0:25–1:00 Live risk: a Context.dev monitor fires on a real dairy news page. Risk alert with source URLs and `agent_run` id.
- 1:00–1:40 Concentration: three suppliers share one upstream co-op. Open provenance panel on the edge.
- 1:40–2:20 Alternatives with price ranges; proposal revises one partial-availability line.
- 2:20–2:55 Approve. Valio mock order placed; audit hash shown.
- 2:55–3:20 Phone: supplier confirms edge (claimed → agreed); auditor stamps (audited).
- 3:20–3:45 Live discovery: new inferred producer appears with confidence and URLs.
- 3:45–4:00 Build panel: green CI run, SBOM count, vulnerability scan, Codex modules listed.
- Backup: pre-recorded video with the same beats.

## 8. 48h build plan (4 engineers)
- **Friday night**: E1 schema, Valio client generated with Codex. E2 Context.dev client, monitor webhook plus scan button. E3 supply map static UI. E4 CI workflow on CRACI runners (install, test, build, SBOM), seed fixtures and JSON Schema validation.

- **Saturday night**: E1 procurement agent and order call with idempotency key. E2 Gemini tool loop, cached proposal for the seed. E3 approval screen and phone confirm page. E4 Aiven Runtime deploy on green, build panel.

## 9. Judging-criteria mapping
- Valio end-to-end (30%): approved order through the mock API with idempotency key.
- Buyer need (20%): alternatives, pars and windows for a hotel buyer.
- Autonomy and controls (20%): agent runs recorded and hashed; approval gate; hash-chained audit.
- Exceptions (15%): partial-availability revision; missed-window alternative day.
- Open standards (15%): CycloneDX SBOM, JSON Schema, OpenAPI client, Postgres.
- Context.dev (15%): monitors and discovery in the core flow, with URLs and run ids.
- Side bounties: Codex (documented module generation), CRACI (SBOM and scan in CI), Gemini (agent LLM), Aiven (Postgres and runtime). Cala skipped.

## 10. Risks and cuts
- Cut first: Build panel depth (show count only), Codex log beyond a list, Kafka, ArcadeDB, Cala.
- Biggest technical risks: CRACI runner setup (fallback: GitHub-hosted runner, same workflow); Valio mock schema (checked Friday); live monitor needs a public URL (scan button fallback); LLM latency (cached proposal for the seed).

## 11. Biggest weakness of this proposal
The provenance and CI story is strong for judges who care about software and trust, but it adds surface area that a buyer does not see, and the 4-engineer team may spend Saturday on pipeline plumbing instead of the buyer flow. We keep CI to one workflow and time-box it to Friday night.

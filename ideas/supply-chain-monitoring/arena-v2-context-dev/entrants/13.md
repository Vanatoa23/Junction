# Entrant 13: Flat Watchlist and Alert Feed (lens: Contrarian)

## 0. Bold bet (2 sentences)
A supply chain is a list of companies with tags, not a graph; one parent per row plus a SQL overlap check on incident footprints answers "what is hit" and "what is a safe alternative", and ships in 40 hours. The product is the sourced alert feed, and each Context.dev monitor is a live sensor on one supplier row.

## 1. Summary and name
- Name: **Tripwire** (A: name unclaimed for the event).
- Client pastes or uploads a supplier CSV (name, domain, country, product, tier, optional parent). Tripwire watches every row and turns detected web changes into a feed of alerts with source URLs. When an incident hits a supplier, it proposes an alternative that passes an explicit disjoint check, and a human approves.
- Contrarian stance: no graph database, no graph traversal, no graph UI. Tier 2 is one `parent_id` column. Downstream is cut.

## 2. Architecture and DB
- One Postgres on Aiven (A: single small instance is enough). No Kafka, Valkey, ClickHouse or OpenSearch.
- Two processes on Aiven Runtime: web app (React + Express, SSE feed) and worker.
- Flow: Context.dev monitor webhooks and Exa Monitor callbacks hit `/hooks/:source`, which writes a raw `events` row with source URL and `detected_at`. Worker fetches structured extraction for the watched page, diffs against the last `snapshots` row, and calls Gemini only on a real diff. Result becomes an `alerts` row, pushed to the feed over SSE.
- Tables: `clients`; `suppliers` (client_id, name, domain, country, tier, parent_id self-FK, depth capped at 2); `supplier_tags` (supplier_id, tag such as `port:Gdansk`, `plant:ACME-PL-2`, `region:Pomorskie`, `sanction:<id>`); `snapshots` (supplier_id, source_url, field_hash, extracted jsonb); `events` (raw); `incidents` (title, footprint_tags text[], severity, source_urls[]); `alerts` (incident_id, supplier_id, status); `alternatives` (alert_id, candidate, score, disjoint_check jsonb, approved_by, approved_at).
- Privacy: every client-owned row carries client_id and every query filters on it. Incidents are shared public facts; supplier lists never join across clients.

## 3. Data model and incident footprint
- Footprint = set of tags an incident touches. Gemini proposes tags from extracted fields and the page text; each tag keeps its source URL and confidence.
- Hit = supplier tags intersect footprint (plus the supplier's tier-2 parent tags).
- Disjoint check for an alternative: `candidate.tags ∩ footprint = ∅` and the same for the candidate's parent chain. This is a SQL anti-join, and the UI shows it row by row: "7 tags checked, 0 shared: port Gdansk not shared, plant ACME-PL-2 not shared, region Pomorskie not shared."
- Explainable by design: a judge can read the overlap query on screen.

## 4. Onboarding and bootstrap
- Input: CSV or paste with name plus domain (name-only rows are flagged).
- Step 1 (about 20 s): Context.dev company enrichment per domain gives country, HQ and description, and flags failures.
- Step 2 (about 60 s for 50 rows, A): Context.dev structured JSON extraction on each supplier's locations or about pages, yielding plant and port tags.
- Step 3 (optional, about 90 s, A): Exa search for missing domains and recent news. Cala is a data source only: a company lookup for parent and investor hints on tier 2.
- Exa Websets: cut from v1.
- The client reviews one tag table and confirms. Expect about 3 minutes for 50 suppliers (A).

## 5. Monitoring design
Three watch types per supplier:
1. Context.dev monitor on each supplier's newsroom or notice page, with a webhook on change. Change is judged on a hash of the extracted fields, not raw HTML, to cut layout noise.
2. Context.dev news search per supplier name plus plant location, polled every 15 minutes (A).
3. Exa Monitor on regional risk queries (strike, sanction, port closure, plant fire) with a date filter, which catches incidents no single supplier page reports.
- Noise filter: drop unchanged hashes; dedupe by supplier plus normalised title; require a source URL; severity threshold per client.
- Latency: each alert records `detected_at` (webhook receipt) against the source's published time where one exists. The feed footer shows p50 and p95.
- Filings: out of v1 (A: no filings feature is in the brief's Context.dev list).

## 6. Incident-disjoint alternatives agent
- Trigger: alert with severity above threshold and at least one hit supplier.
- Sources: Exa company search by product category, excluding footprint countries; Cala company lookup for the same category; Context.dev enrichment on each candidate.
- Pre-filter: drop any candidate whose extraction shows a footprint tag. Then rank by product-keyword overlap (Exa), distance from the failed supplier's country (coarse, A), and absence of open alerts.
- Validation: the disjoint checklist from section 3, plus a two-sentence Gemini rationale citing only fetched source URLs.
- Human approval: "Approve switch" records the approver. After approval, optionally place a mock order via Valio's API (secondary, stacked only if it works).
- The check is labelled "Not affected by the same incident" in the UI.

## 7. Upstream and downstream
- Upstream: IN, as a tier-2 import with a parent column. Same monitoring. Depth capped at 2.
- Downstream (client's customers): OUT. It needs customer data the client rarely has, and it is a credit-risk product, not a supply-chain one. Roadmap only.

## 8. Screens and demo script
Screens: (1) supplier table with tag chips, source counts and status; (2) live feed with alerts, source URLs, `detected_at` and a latency badge; (3) incident page with footprint, hit suppliers and alternatives with checklists; (4) approve modal.

Script (3:30):
- 0:00-0:25 Paste a 40-row CSV. Enrichment progress fills. Frame: "the web is the database".
- 0:25-1:00 Tag table with source URLs under each tag. Hits Context.dev completeness and impact.
- 1:00-1:45 Edit a canary notice page we control (labelled synthetic). Webhook fires, a feed item appears with the diff, source URL and latency. Hits real-timeness and latency.
- 1:45-2:30 A live regional item from the Exa Monitor. Gemini tags it, and it hits the Gdansk supplier. Hits creative live web use.
- 2:30-3:15 Three alternatives. One is rejected in the checklist for sharing the port. Approve one.
- 3:15-3:30 Close on measured numbers: p50 latency, and precision on 20 labelled events.

## 9. Build plan, risks, cuts
- About 40 hours, four engineers, 10 hours each:
  - E1: Context.dev monitors, webhook receiver, snapshot diff.
  - E2: Postgres schema, CSV import, onboarding enrichment jobs.
  - E3: Exa Monitor, Gemini classifier, footprint, disjoint SQL, alternatives agent.
  - E4: feed and incident UI, SSE, approve flow, seed data, Runtime deploy.
- Timeline: hours 0-4 schema and seed; 4-20 pipelines; 20-32 UI; 32-38 rehearse; freeze two hours before demo.
- Cut order: Valio mock order, then Cala, then Exa Monitor (fall back to a seeded incident, labelled), then tier 2, then SSE (use polling).
- Risks: webhook delivery at the venue (polling fallback and a recorded replay); suppliers' pages not changing (pre-verify monitored pages; the canary covers the live beat); Gemini latency (classify diffs only).

## 10. Biggest weakness (honest)
A tree with one parent per row cannot model a supplier shared across two branches or a plant owned by two companies, so judges who expect a graph will read this as a lookup table. My answer is that a first-tier list is enough for this demo and tier 3 needs a real graph, which I am deliberately not building. The product is also only as good as the pages suppliers publish; many small suppliers have no monitorable notice page, and those rows will show "no signal" rather than "safe".

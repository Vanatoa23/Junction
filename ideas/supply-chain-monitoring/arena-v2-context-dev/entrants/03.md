# Entrant 03: Canary, the alert you watch arrive (lens: Real-timeness on stage)

## 0. Bold bet (2 sentences)
Every change on a supplier's public web footprint carries a timestamped trail from edit to on-screen alert, and the judges watch that clock stop live while a presenter publishes a supplier notice from a phone. The incident-disjoint check is a visible table, so the same moment proves both "it reacted" and "the alternative is actually safe".

## 1. Summary and name
- **Canary**: a client pastes or uploads its supplier list. Canary watches each supplier's public pages and news through Context.dev monitors, turns changes into structured incidents with source URLs, and offers alternatives that pass a disjointness check.
- Stage moment: a demo-owned "Supplier Notices" page, labelled **SEEDED**, is edited live. An on-screen timer shows elapsed time from edit to rendered alert, split by stage.
- Real companies are monitored in parallel, so the feed also carries genuine web changes with source URLs.
- Upstream is a data-only stretch; downstream is cut first (section 7).

## 2. Architecture and DB
- **Aiven Postgres** is the only datastore. JSONB holds footprints and webhook payloads. `LISTEN/NOTIFY` fans events out to the app, which pushes to the browser over SSE. No Kafka, no graph DB: recursive CTEs suffice at roughly 500 companies **(A)**.
- One TypeScript service on Aiven Runtime, plus a static React front end. Modules: webhook ingest, Gemini classifier (structured output), footprint and disjoint check (pure functions), alternatives job, SSE.
- **Context.dev** (JS SDK): enrichment, monitors, news search, scrape. **Exa**: bootstrap and alternative discovery. **Cala**: ownership and relationship edges, as a data source only.
- Demo site: a small static host on our domain serving the SEEDED notices page. Its server logs the publish time `t0` to the DB.

## 3. Data model and incident footprint
- `companies(id, domain, name, country, parent_group_id, enrichment jsonb)`: public, shared across tenants.
- `edges(client_id, buyer, supplier, tier)`: private to the client.
- `watches(company_id, kind page|news, url or query, context_monitor_id, interval_s)`.
- `events(id, company_id, source_url, t0, detected_at, webhook_at, classified_at, rendered_at, payload jsonb, severity, dedup_hash)`.
- `incidents(id, event_ids[], footprint jsonb)`.
- `alerts(id, client_id, incident_id, affected_supplier_ids[])`: private.
- `alternatives(id, incident_id, candidate_id, check jsonb, rank, approved_by, approved_at)`: private.
- **Footprint keys**: `region` (ISO 3166-2), `ports` (UN/LOCODE), `sites` (normalised facility name), `parent_group` (ownership collapsed via Cala), `sanction_refs`, `commodity`.
- **Privacy**: every client-scoped query filters on `client_id` in one repository layer. Shared rows contain only public-web facts, never a client's supplier list.

## 4. Onboarding and bootstrap
- CSV columns: name, country, tier. Gemini normalises names. Exa company search resolves domains where none is given. Cala adds parent group and investor edges where it has them. Context.dev enrichment fills domain, HQ region and description.
- Per company: 2 page monitors (newsroom or notices, plus a status page if found) and 1 news query.
- Time **(A)**: about 30 suppliers in 3 to 4 minutes, bound by enrichment rate. Stage path: a 12-row CSV is uploaded live, with counters ticking per enriched company. A pre-warmed 30-supplier client exists as a fallback.

## 5. Monitoring design
- **Context.dev monitor** on each newsroom or notices URL, webhook on change **(A: monitor interval can go to about 1 minute)**.
- **Context.dev news search** every 5 minutes with `"<name>" strike OR port OR sanction OR plant closure OR recall`.
- **Exa Monitor** on the same query as a second, independent source for trade press.
- Noise filter: classify only non-trivial diffs. Severity threshold. Dedup on a hash of the extracted notice. Six-hour cooldown per company.
- **Latency budget, targets**:
  - edit to monitor detection: 60 s
  - detection to webhook received: 5 s **(A)**
  - webhook to classified and footprint computed: 8 s
  - classified to alternatives shown as "working": under 1 s; proposals within 15 s
  - event to browser over SSE: under 1 s
  - Total target: 75 s. Shown on screen as a per-stage chip and a running p50 over the last 50 events.
- **Degraded path**: if webhooks fail on venue Wi-Fi, poll Context.dev scrape every 60 s and diff locally. The same classifier and timer apply, and the chip reads "poll".
- Every event stores `t0`, `detected_at`, `webhook_at`, `rendered_at`, so the timer is a real measurement.

## 6. Incident-disjoint alternatives agent
- Incident footprint F. Candidate C is accepted only if C's footprint is disjoint from F on every hard key: `region`, `ports`, `sites`, `parent_group`, `sanction_refs`.
- `commodity` overlap is allowed but flagged.
- The check renders as a table: one row per key, "shared: none", with the evidence URL. Failing candidates stay visible with the key that failed, so nothing is silently dropped.
- Candidates: Exa company search (category company, same commodity, outside F's region), Cala same-category peers, shortlist enriched by Context.dev. Each region or port fact needs two independent sources.
- Ranking: certification and capacity mentions from Context.dev scrape, then distance from the client.
- Top 3 are shown with check tables. Human approval records `approved_by`, then posts to the Valio mock order API (secondary, only after approval).

## 7. Upstream and downstream
- **Upstream: in as data only.** One hop of Cala supplier edges, shown as a graph count. Not monitored in the demo, because tier-2 watches multiply volume by about 10x.
- **Downstream: out of the core build.** Stretch only: customer newsrooms filtered for insolvency keywords, if hours 30 to 34 are free.

## 8. Screens and demo script (timed)
Screens: (1) live board with source URLs and an event-age ticker; (2) onboarding with enrichment counters; (3) incident view with the running timer and stage chips; (4) alternatives with the disjoint table; (5) latency page with a histogram.
- **0:00 to 0:20** Hook: "A supplier posts a notice. How long until we know?" Timer starts on the board.
- **0:20 to 0:50** Onboard a 12-row CSV. Enrichment counters tick, monitors are created.
- **0:50 to 1:15** Board shows real web changes from the last 72 hours, each with source URL and `detected_at`.
- **1:15 to 2:30** The moment: presenter publishes the SEEDED notice from a phone. `t0` is logged. The timer runs, the webhook chip lights, the classifier card appears, and the alert shows source URL and footprint. The timer stops at render.
- **2:30 to 3:05** Three alternatives, disjoint table, approve, mock order placed.
- **3:05 to 3:35** Latency histogram. Accuracy on 40 labelled seeded events **(A)**. A second client login sees none of the first client's edges.
- **3:35 to 3:50** Close.

## 9. Build plan, risks, cuts
- **Hours 0 to 5**: Context.dev smoke test for monitor, webhook and the real interval floor. Aiven Postgres. Demo site. If the monitor floor is above 5 minutes, switch to the scrape poll.
- **Hours 5 to 15**: E1 ingest, monitors, webhooks. E2 classifier and footprint. E3 onboarding, Exa, Cala. E4 UI, SSE, timer, demo site.
- **Hours 15 to 27**: alternatives agent and disjoint check. Second client for the privacy beat.
- **Hours 27 to 34**: five full rehearsals, timer and histogram polish.
- **Hours 34 to 38**: recorded backup run, pre-warmed client, fallback to poll mode.
- **Freeze 38 to 40.**
- **Risks**: monitor interval floor unknown **(A)**. Webhook reachability on venue Wi-Fi. Gemini latency spikes. Judges entering hostile inputs.
- **Cut first**: downstream, then the Valio order, then the Exa Monitor (keep Context.dev monitors), then PDF parsing.

## 10. Biggest weakness (honest)
The stage moment is driven by our own seeded page, so judges may read it as staged, and the real-web feed is slower and less predictable. The latency numbers rest on monitor-cadence and webhook assumptions **(A)** that we cannot verify until hour 5.

# Entrant 12: SecondSource (lens: Valio prize stacked on Context.dev)

## 0. Bold bet (2 sentences)
Context.dev monitors are the only trigger in the product: no incident exists until a Context.dev webhook fires with a source URL, and the Valio order is the last link in that same chain, placed only after a human approves. Valio adds about 8 engineer-hours after monitoring is green, so it stacks prize points without taking time from detection.

## 1. Summary and name
- **SecondSource**: a client enters its supply list; Context.dev watches every supplier's pages and news; a change that matches an incident footprint opens an incident; an agent proposes incident-disjoint alternatives; an approved switch becomes an order in Valio's mock ordering API.
- One feed shows the full chain: source URL -> change event -> incident -> disjoint check -> approval -> Valio order ref.
- Labelled SYNTHETIC: fictional demo client (30 suppliers), Valio synthetic catalogue, one staged port-notice page we host.
- Stacked prizes: Context.dev (core), Valio (catalogue, mock order, human approval all used), Gemini (classification, rationale), Aiven (Postgres, Runtime), CRACI (CI and SBOM). Codex only if used meaningfully (A).
- Assumption (A): Valio's mock exposes catalogue listing, order create and order status endpoints.

## 2. Architecture and DB
- Stack: TypeScript, Fastify API, React/Vite UI, one worker process. Hosted on Aiven Runtime (A: runs a Node service and a worker).
- DB: Aiven managed Postgres. Postgres is also the job queue (`SELECT ... FOR UPDATE SKIP LOCKED`). No Kafka, no Valkey, no graph DB. Supply graph is plain edge tables, queried to depth 2 with recursive CTEs.
- Detection path: Context.dev monitor webhook -> `/hooks/contextdev` (verifies signature, A) stores raw event with source URL and timestamps -> enqueue -> worker maps URL to company -> Gemini returns schema-constrained JSON (incident type, region, ports, sanction refs, confidence, quoted evidence) -> rule gate -> footprint match -> alert.
- Alternatives path: runs only when an open incident hits a supplier in some client's graph. Valio path runs only after human approval.

## 3. Data model and incident footprint
- `companies` (shared, public facts only): id, name, domain, country, category, source.
- `client_suppliers`, `edges` (client-private): client_id, buyer_id, supplier_id, tier, sku[].
- `footprint_keys` (shared, public): company_id, dim, value, source_url, verified_at. Dims: `region`, `port` (UN/LOCODE), `plant`, `sanction` (list + entity id), `parent` (owner, via Cala and Context.dev enrichment, A).
- `incidents`: id, type, detected_at, source_event_id, confidence. `incident_footprint`: incident_id, dim, value.
- `alerts`: client_id, incident_id, company_id, status. `alternatives`: client_id, alert_id, candidate_id, rank, disjoint_report_json, status (proposed | approved | rejected | ordered).
- `orders`: alternative_id UNIQUE, valio_order_ref, idempotency_key = alternative id, approved_by, approved_at.
- `monitors`: company_id, kind (page | news), cd_monitor_id, url or query. `change_events`: monitor_id, source_url, observed_at, received_at, latency_ms.
- Privacy: client-scoped tables carry client_id; every API query filters by the session's client. Shared tables never store client identity. One monitor per public company or URL, fanned out to clients at alert time through the edge join. A client's edges never appear in another client's response.

## 4. Onboarding and bootstrap
- Client pastes or uploads CSV (name, country, tier, SKU).
- Step 1: Context.dev company enrichment resolves name -> domain, country, parent (A). Batched, about 1-2 s per company.
- Step 2: Cala lookup for funding and investors, stored as sourced attributes. Feeds the `parent` dim.
- Step 3: Context.dev scrape of each domain's plant and locations pages. Gemini extracts `plant` and `region` keys, each with its source_url.
- Step 4: Create 2 monitors per company: newsroom or notice page, plus a news query.
- Step 5: Exa company search by category builds the alternatives pool, run lazily at incident time.
- Timing: 30 suppliers about 2-3 min live. Demo uses a pre-run snapshot; one new supplier is onboarded live (about 40 s).
- Unknown dims stay unknown. Unknown means fail-closed later.

## 5. Monitoring design
- Per company: page monitor on newsroom and plant pages (Context.dev monitor, webhook on change). News query "<name> strike OR sanction OR fire OR recall OR port closure" every 6 h via Context.dev news search.
- Per region: 5 public port-authority notice pages as shared monitors.
- Demo source: one staged port-notice page we host (labelled SYNTHETIC), edited live during the demo. A real Context.dev monitor fires on it.
- Noise filter: (1) diff of at least 20 changed words after boilerplate strip; (2) Gemini confidence at least 0.7; (3) incident opens on one source at confidence at least 0.9, or two independent sources; (4) dedupe by hash of (type, region, date).
- Latency: `detect_ms = received_at - observed_at`, `alert_ms = alert_at - received_at`. Shown as p50 and p95 over the last 50 events.
- Accuracy: 40 labelled synthetic snippets, precision and recall printed on the dashboard.

## 6. Incident-disjoint alternatives agent
- Trigger: incident footprint intersects a supplier in an affected client's graph.
- Candidates: Exa company search (category match, date within 12 months) plus Valio catalogue SKU match. Cap 10.
- Each candidate is enriched through Context.dev (company plus plant and port scrape) into footprint keys.
- Disjoint check, explicit and fail-closed, per dimension D with incident values I_D and candidate values C_D:
  - PASS if C_D is known and C_D intersect I_D is empty.
  - FAIL if they overlap, naming the key and its source_url.
  - UNVERIFIED if C_D is unknown. Any UNVERIFIED removes the candidate.
- Report per candidate: table of dim, result, evidence URL. Shown to the client.
- Ranking for passing candidates: SKU fit, lead time, unit price from catalogue, count of open alerts. Gemini writes the rationale and may cite only footprint keys.
- Human approval: client selects and approves. Only approval creates a Valio order. The agent never orders.

## 7. Upstream and downstream
- Upstream: IN, limited. Client-supplied tier-2 rows plus Cala parent data feed the `parent` dim. No automatic tier-2 discovery (A: too slow to make reliable in 40 h).
- Downstream: OUT. Roadmap only. Cut first from the demo.

## 9. Build plan, risks, cuts
- Budget, 160 engineer-h: monitoring and classification 70 h (E1, E2); graph, onboarding and UI 40 h (E3); alternatives and disjoint check 35 h (E4); Valio adapter 8 h (E4, after Saturday H24); ops and demo prep 7 h.
- Milestones:
  - H0-6: schema, seed, Aiven DB live.
  - H6-14: one real monitor -> webhook -> classified event with source URL. Gate at H14: if it fails, replay a recorded webhook (labelled) and continue.
  - H14-26: incident, footprint, disjoint check, alternatives.
  - H26-34: Valio mock order, approval, latency dashboard.
  - H34-38: UI polish, staged page script.
  - H38-40: freeze. Three full rehearsals. Backup video recorded by H36.
- Risks: Context.dev monitor delay or webhook shape (A); Valio mock schema differs from assumption; staged page reliability; Gemini quota; judges editing demo sources.
- Cut order: Cala live calls (use snapshot), then Exa live (use cache), then news polling (keep page monitors), then Valio last. Valio's order step is about 8 h, so it is cut only if monitoring misses H26.

## 10. Biggest weakness (honest)
The Valio step is a side prize that judges may read as bolted on, and it is a simulated purchase against a mock with an unconfirmed schema (A). Real-timeness rests mainly on one staged page we control, so judges may see it as scripted. Two real public notice pages are monitored, but they may not change during the demo window.

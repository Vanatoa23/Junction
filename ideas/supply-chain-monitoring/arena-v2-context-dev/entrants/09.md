# Entrant 09: SecondSource, verified replacements for hit suppliers (lens: Alternatives agent excellence)

## 0. Bold bet (2 sentences)
**Bet:** the judges will remember the moment a supplier is hit and, within a minute, the app returns a replacement with a source link for every claim. Every alternative must pass a written five-check "not hit by the same incident" test, and a candidate that cannot prove a check is shown as unverified, never silently offered.

## 1. Summary and name
- **SecondSource.** A client pastes its supplier list. Context.dev monitors every company's site, news and region/port/sanction pages. When an incident touches a supplier, we build an incident footprint, and an alternatives agent (Exa + Cala + Context.dev enrichment) proposes up to 3 replacements that pass the disjoint check. A human approves.
- Context.dev is core: all signals arrive via Context.dev monitor webhooks, all candidates are enriched by Context.dev, and a live Context.dev news check runs on each candidate before it is offered.
- The hero is the alternatives agent. Monitoring is its feeder.

## 2. Architecture and DB
- React (Vite) UI, then a TypeScript API (Fastify) on Aiven Runtime.
- **Aiven Postgres** is the single store. Every client-owned row carries `client_id`. Postgres RLS is the target, with repository-level scoping as the fallback (A).
- **Aiven Valkey** holds the BullMQ job queue and dedupe keys. No Kafka and no ClickHouse. ArcadeDB is cut: 2-hop upstream uses recursive CTEs.
- `/hooks/contextdev` verifies the HMAC signature, enqueues the event, and returns 200 in under 200 ms.
- Worker: Gemini with structured output for classification and summaries. Exa for search and page contents. Cala via REST or MCP for ownership and supplier edges.

## 3. Data model and incident footprint
- `company(id, domain UNIQUE, name, country, footprint jsonb)`: global public entity cache, no client data.
- `supply_edge(client_id, buyer_id, supplier_id, tier, product, criticality)`: client-private.
- `monitor(id, company_id, cd_monitor_id, kind site|news|region|sanction, query)`.
- `signal(id, monitor_id, company_id, source_url, published_at, detected_at, type, severity, confidence, keys text[], quote, hash UNIQUE)`.
- `incident(id, title, keys text[], first_signal_at, status)`.
- `alert(id, client_id, incident_id, supplier_id, status)`.
- `alternative(id, alert_id, candidate_id, rank, checks jsonb, status proposed|unverified|rejected|approved, approved_by, approved_at)`.
- **Footprint keys** are typed strings: `REGION:<code>`, `PORT:<UN/LOCODE>`, `PLANT:<id>`, `SANCTION:<program>`, `PARENT:<domain>`, `CARRIER:<scac>`. Example: a strike at Rotterdam gives `{PORT:NLRTM, REGION:NL-ZH}`.
- **Privacy rule:** `supply_edge` never leaves client scope. Outbound queries to Exa, Cala and Context.dev carry only product category, excluded region and incident keys. They never carry the client name or its supplier list.

## 4. Onboarding and bootstrap
- Input: CSV or paste with name, country, product, tier (1 or 2). Target: 40 suppliers in about 4 minutes (A).
- **Step 1, resolve:** Context.dev company enrichment in batch by name and country. Exa search with domain filter as fallback.
- **Step 2, parents and tier 2:** Cala ownership and supplier edges for each resolved node. Seeded with the sponsor's first nodes.
- **Step 3, footprint:** Context.dev structured JSON extraction from locations, plants and contact pages gives `PLANT`, `REGION` and `PORT` keys. Each key stores its source URL.
- **Step 4, monitors:** created for each company (section 5).
- Demo set: 12 real companies pre-resolved. Any seeded value is labelled `SEED`.

## 5. Monitoring design
- **Per company:** Context.dev site monitor on `/news`, `/press` and `/locations`. Context.dev news query: `<company> AND (strike OR fire OR recall OR sanction OR insolvency)`, daily.
- **Per footprint key:** region and port advisory pages, and sanction list pages, watched with page-level monitors.
- **Pipeline:** webhook, then Gemini classifier (schema: type, severity, keys, confidence, cited quote), then dedupe by hash.
- **Noise filter:** alert only if the source URL resolves and confidence is 0.7 or higher, and either the domain is an official source or two independent sources agree within 48 h. Everything else goes to a daily digest.
- **Incident clustering:** signals sharing at least one key within 72 h merge into one incident.
- **Latency,** per signal: `t_pub` (source `published_at`, else the detected page change), `t_hook` (webhook received), `t_alert` (alert row). Live p50 and p95 on screen. Target p95 under 90 s from `t_hook` to `t_alert` (A). The vendor's poll interval is an assumption (A) and is shown as measured, not promised.

## 6. Incident-disjoint alternatives agent (hero)
The incident footprint `I` is the set of keys hit. Each candidate `c` has its own footprint `F(c)`.

**Pipeline**
1. **Need:** product class and required region. No client name is sent.
2. **Source candidates:** Exa deep search (category `company`, last 12 months, excluding incident-region domains) plus a Cala query for the same product class. Union, then dedupe by domain.
3. **Enrich:** Context.dev company enrichment and footprint extraction, batched, up to 25 candidates.
4. **Disjoint check:** five explicit checks, each returning PASS, FAIL or UNKNOWN with an evidence URL.
   - **C1 Region:** `F(c).regions ∩ I.regions = ∅`.
   - **C2 Port:** `F(c).ports ∩ I.ports = ∅`, including inbound lanes.
   - **C3 Upstream plant:** the candidate's own tier-2 suppliers (Cala and Context.dev) `∩ I.plants = ∅`.
   - **C4 Sanction:** neither the candidate nor its parent is in `I.sanctions`, and no program overlaps.
   - **C5 Parent:** the 2-hop Cala ownership chains of the candidate and the hit supplier share no node.
   - **Live check:** Context.dev news search on the candidate's region and keys for the last 14 days shows no signal of the same incident class.
5. **Gate:** offered as verified only if C1 to C5 all PASS and the live check is clean. Any UNKNOWN gives status `unverified`: human-only, never ranked above a verified one. Any FAIL is hidden, and the reason is logged.
6. **Rank** verified candidates: 0.35 capacity fit (sourced claim) + 0.25 product match + 0.20 sourced lead time + 0.20 quiet record (no signals in 90 days from our own monitors). Show the top 3.
7. **Validate:** every claim on the card needs a source URL from Exa Contents. Code drops any claim without a URL, so the LLM cannot slip one through.
8. **Human approval:** the approve button writes `alternative.status = approved` and an order draft. Valio's mock order API is an optional post-approval step, cut first.

**Explainability:** the check matrix, with each cell linked to its evidence, is the explanation shown to judges.

## 7. Upstream and downstream
- **Upstream: IN, narrowly.** Two hops via Cala edges for tier-1 suppliers only. It feeds check C3. Not continuously monitored beyond the hero set.
- **Downstream: OUT.** Roadmap only. No code, no demo time.

## 8. Screens and demo script (timed)
- **Screens:** (1) paste list and resolved graph, with Exa and Cala counts; (2) live feed with source URLs and latency badges; (3) incident footprint with flagged suppliers; (4) alternatives with the check matrix and evidence; (5) approval and audit log.
- **Script, 3:30**
  - 0:00 to 0:25, impact: one client, 40 suppliers, one sentence on the problem.
  - 0:25 to 1:00, onboarding: paste the list, Context.dev resolves it, the graph appears.
  - 1:00 to 1:40, real-timeness and live web: a monitored real public page changes. Show the webhook arrival, source URL and latency badge. Fallback: a labelled replay.
  - 1:40 to 2:30, incident: footprint shown, supplier flagged.
  - 2:30 to 3:10, alternatives: check matrix, 3 candidates with evidence, one rejected by C2 with its reason. This shows the hard rule working.
  - 3:10 to 3:30, approve, audit log, latency stats, then the five criteria.
- A backup video is recorded by hour 34.

## 9. Build plan, risks, cuts
- **Team, about 40 h each:**
  - E1: Context.dev monitors, webhook, classifier, latency.
  - E2: Exa and Cala sourcing, five checks, ranking.
  - E3: schema, RLS, queue, incidents, onboarding.
  - E4: UI, seeds, demo, backup video.
- **Milestones:** H8 schema and 12 real companies resolved. H16 first real webhook end to end. H24 alternatives with checks. H32 UI complete. H36 rehearsal. H38 code freeze.
- **Risks:**
  - Context.dev monitor latency and quotas (A). Mitigation: show measured numbers only.
  - Exa and Cala rate limits. Mitigation: cache candidates in Postgres.
  - Sparse footprints give many UNKNOWNs. Mitigation: choose a product class with dense public data.
  - LLM invention. Mitigation: code-level URL enforcement.
  - Venue Wi-Fi. Mitigation: local recording.
- **Cut order:** Valio mock order, Exa Monitors (use Context.dev instead), upstream beyond 2 hops, Cala beyond ownership, people enrichment, RLS (disclosed fallback to repository scoping).

## 10. Biggest weakness (honest)
The disjoint check is only as good as public footprint data. For niche parts most candidates return UNKNOWN, so the panel will often say "no verified alternative", which is correct but less dramatic. I ran no web searches for this entry, so no candidate supplier or source has been verified live. All candidate names and sources must be checked on Friday morning before they go on screen.

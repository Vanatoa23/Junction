# Entrant 11: Tierlight (lens: Client UX)

## 0. Bold bet (2 sentences)
A client pastes a supplier list and sees a live, monitored supply map within 60 seconds, with every monitor already armed. Each incident arrives as one alert card with a pre-checked, incident-disjoint alternative that a procurement manager can approve or reject in 10 seconds.

## 1. Summary and name
- **Tierlight.** Client pastes or uploads a CSV (name, country, tier, optional domain). Output: live supply map, alert inbox, alternative cards.
- Context.dev is the spine: enrichment (domain, HQ, logo), page monitors with webhooks, news search per supplier, PDF parsing for plant locations. Every alert shows source URLs and timestamps.
- Upstream in as optional tier-2 only. Downstream out (explicit cut, see section 7).
- **(A)** Context.dev webhooks fire within seconds of a detected change. We measure this on screen, not trust it.

## 2. Architecture and DB
- Web: Next.js (TypeScript) hosted on Aiven Runtime **(A)**. Map: Cytoscape.js. Progress streamed over SSE.
- Backend: one Node service with an API, a webhook route and a worker loop.
- DB: Aiven Postgres only. Job queue is a table polled with `FOR UPDATE SKIP LOCKED`. No Kafka or Valkey. Row-level security on every client-owned table, keyed on `client_id`.
- LLM: Gemini for news relevance scoring, page-diff summaries and alternative rationale text. The independence check is deterministic code, not an LLM.
- Sources: Context.dev (enrichment, scrape, monitors, news, PDF parse, batch), Exa (bootstrap search, Websets for alternative candidate pools **(A)**), Cala (tier-2 and ownership nodes).
- Valio mock ordering API, reachable only from an approved alternative.

## 3. Data model and incident footprint
- **Shared (public facts):** `companies(id, name, domain, hq_country, logo)`, `company_facts(company_id, dimension, value, source_url, observed_at)`, `incidents(id, type, title, source_urls[], detected_at)`, `incident_footprint(incident_id, dimension, value)`.
- **Private to client (RLS):** `clients`, `supply_edges(client_id, buyer_id, supplier_id, tier)`, `monitors(client_id, company_id, kind, status)`, `alerts(client_id, company_id, incident_id, status, severity)`, `alternatives(client_id, alert_id, candidate_id, checks jsonb, decision)`.
- **Footprint dimensions:** `region`, `port`, `plant`, `sanction_regime`, `commodity`.
- A company's footprint is its `company_facts` mapped onto these dimensions. An incident's footprint is the set of dimension values it touches.
- **(A)** Sanction regimes come from an open sanctions list imported at setup, plus news facts. Not from Context.dev.

## 4. Onboarding and bootstrap
Target: paste to live map in under 60 seconds for up to 150 suppliers.
- **0-5 s:** Parse CSV, dedupe by normalised name, show a 3-row preview with inline errors. User confirms.
- **5-25 s:** Context.dev company enrichment in batch for every row. Rows with a domain go straight to enrichment. Returns canonical domain, HQ, logo.
- **25-35 s:** Unresolved rows go to Exa (company-category search for the domain). Cala checks ownership so a subsidiary does not resolve to its parent. Still-unresolved rows show greyed with a "Find domain" action. They never block.
- **35-50 s:** Create one page monitor per domain in a batch, queue the first scan, and drop nodes onto the map as each one resolves.
- **50-60 s:** First scan fills the inbox as **baseline** items, labelled as baseline, not alerts.
- Optional tier-2: "Suggest tier-2" runs Cala per tier-1 node. Each suggestion needs a tick before it is monitored.
- Demo data: a labelled SEEDED 40-supplier list, plus one real list verified before the demo.

## 5. Monitoring design
Three watches per supplier:
1. **Pages:** Context.dev monitor on homepage, newsroom and press pages. Webhook on change, with the diff.
2. **News:** Context.dev news search on the supplier name with incident terms (strike, fire, shutdown, sanction, recall, insolvency, port closure), polled every 15 minutes **(A)**.
3. **Filings:** PDF parse of annual or sustainability reports on demand. Writes facts (plant locations), never alerts.

Noise filter, in three stages:
- Rules: drop timestamp-only page changes, dedupe by URL.
- Gemini relevance score 0-1, alert only at 0.7 or above.
- Per-client mute by incident type, learned from "not relevant" clicks.

Latency: each event stores `observed_at` (webhook receipt), `source_published_at` (news date or diff time) and `shown_at`. The inbox footer shows p50 and p95 for the session. Target: under 2 minutes for page changes, under 15 minutes for news **(A)**.

## 6. Incident-disjoint alternatives agent
- **Check:** candidate C qualifies only if `footprint(C) ∩ footprint(incident) = ∅` on every dimension. C's tier-2 nodes are included in its footprint.
- **Display:** five rows (region, port, plant, sanction regime, commodity). Each is pass, fail or unverified, with the source URL behind it.
- **Unknown is not a pass.** Unverified rows make the candidate "to verify", never "ready".
- **Sources:** the candidate pool comes from Exa Websets (same commodity, other regions) and from the client's own list. Ranking: commodity match, capacity fact, lead time from source, then distance. Gemini writes the one-line reason.
- **Empty result:** "No independent alternative found." The card shows the closest candidates and the exact failed check.
- **Human approval:** Approve sends a mock order via Valio's API. Reject records a reason, which feeds the mute rules.

## 7. Upstream and downstream
- **Upstream: in, as tier-2 only.** Tier-2 plants feed the incident footprint. That is where the independence check earns its keep.
- **Downstream: out.** Credit-risk claims about the client's customers need data we cannot source honestly in 40 hours. We say so on the slide.

## 8. Screens and demo script (timed)
Screens: (1) paste box with live progress, (2) supply map with status-coloured nodes, (3) alert inbox with triage (Acknowledge, Snooze, Resolve), (4) alternative card.

Script, 3 min 45 s:
- **0:00-0:20:** Problem and claim.
- **0:20-1:00:** Paste the SEEDED 40-supplier list. Visible timer. Map is live at about 45 s.
- **1:00-1:30:** Open one supplier. Domain, sources, three monitors armed.
- **1:30-2:10:** Staged live change. The team edits a status page on a team-controlled domain (labelled STAGED). Webhook fires, alert appears, latency shown from `observed_at` to `shown_at`.
- **2:10-2:50:** The 10-second decision. Incident footprint, then the alternative card with five checks. Approve.
- **2:50-3:15:** Valio mock order confirmation.
- **3:15-3:45:** Latency panel and a criteria recap.

Coverage: impact (client acts on the alert), creative live web use (monitors, news, PDF, diffs), completeness (paste to order), latency and accuracy (on-screen timers, source links), real-timeness (a change happens during the demo).

## 9. Build plan, risks, cuts
- **Team of 4, 40 hours:**
  - A: paste flow, enrichment pipeline, map (hours 0-12).
  - B: Context.dev monitors, webhook, news query, noise filter (hours 0-14).
  - C: footprint model, independence check, Gemini rationale (hours 0-12).
  - D: Aiven schema, RLS, seeded data, Valio mock, demo harness and staged page (hours 0-6, then demo rehearsal).
- Feature freeze at hour 24. Rehearse three times, hours 24-36. Record the backup video, hours 36-40.
- **Risks:** Context.dev batch latency at 150 rows; news noise; no real incident during the demo window (the staged change covers this); Exa and Cala access.
- **Cut first:** Cala tier-2, PDF parsing, Valio ordering, 15-minute news polling. Keep page monitors and the independence check.

## 10. Biggest weakness (honest)
The staged change proves the pipe, not detection quality on real news. The independence check is only as good as the footprint facts, and tier-2 plant data will be thin, so some "pass" results will be over-confident. The "unverified" state reduces this but does not remove it.

# Entrant 08: Quietline, only signals you can verify (lens: Accuracy and noise)

## 0. Bold bet (2 sentences)
Quietline alerts a client only when an incident is corroborated and tied to the right company, so a judge sees a short, sourced alert feed instead of a noisy news firehose. We show the accuracy funnel and latency on screen, measured against a small labelled set, so the claims are checkable.

## 1. Summary and name
- **Quietline**: monitors each supplier with Context.dev and turns web change into a short list of verified incidents, each linked to its source URLs.
- Client enters a supplier list (paste or CSV). Every company is matched to a canonical entity before monitoring starts.
- Alerts have two levels: **Confirmed** (pushed to the client) and **Unconfirmed** (feed only, never pushed).
- Alternatives pass an explicit disjoint check before they are offered (section 6).
- Scope for demo: tier-1 suppliers. Upstream is schema-only, downstream is out (section 8).

## 2. Architecture and DB
- Stack: TypeScript (Node + Next.js) on Aiven Runtime. Aiven Postgres is the only datastore. Postgres `SKIP LOCKED` is the job queue (no Valkey, A: fine at demo scale).
- Flow: Context.dev monitors and news search (plus Exa Monitors, A) → webhook receiver → raw_items → Gemini classify → verifier → entity resolver → corroboration → alert → client feed.
- Gemini returns a fixed JSON schema plus a verbatim `quote`. A deterministic check confirms the quote exists in the fetched text. Failing items are dropped and counted in the funnel.
- Privacy: every client table has `client_id`, enforced by a query helper that requires it (RLS on Aiven is (A), backup is the helper). Company facts are shared globally, but edges, alerts and alternatives are per client only.

## 3. Data model and incident footprint
- `companies(id, canonical_name, domain UNIQUE, context_id, aliases[], country, registry_id, source)`
- `client_supplier_edges(client_id, parent_id, child_id, tier, status)`
- `raw_items(id, source_url, source_domain, published_at, fetched_at, text_hash, origin: monitor|news|exa)`
- `incident_candidates(id, raw_item_id, type, severity, quote, classifier_conf, verifier_pass)`
- `incidents(id, fingerprint, type, region, first_seen, corroboration_n, status)`
- `incident_footprint(incident_id, dim, value)`: dims are `region`, `plant`, `port`, `sanction_programme`, `parent_company`, `corridor`. Each value is an ID, not free text.
- `company_footprint(company_id, dim, value, source_url, verified_at)`: the same dims, per company. Filled from Context.dev page extraction and Cala facility data, with a source URL on each row.
- `alerts(id, client_id, incident_id, company_id, level, evidence_ids[], created_at)`
- `alternatives(id, alert_id, candidate_id, disjoint_json, status: proposed|approved|rejected)`
- Fingerprint = type + region + ±72h window + normalized headline hash. Used for dedupe.

## 4. Onboarding and bootstrap
- Step 1: paste or upload the list (name, country, optional domain). Target: 30 suppliers in under 3 minutes.
- Step 2: Context.dev company enrichment fills domain, legal name, HQ (A: enrichment returns these fields).
- Step 3: Cala lookup by name and country returns a registry or graph ID where it exists. Exa search fills the rest.
- Step 4: entity resolver (section 5). Each supplier ends as `matched` (score ≥ 0.9 with domain or registry agreement), `ambiguous` (put in a review queue with two candidate rows), or `unmatched` (monitored by name only, flagged in the UI).
- Demo bootstrap time: about 90 seconds for 30 suppliers, if the enrichment calls run in parallel (A).

## 5. Monitoring design and noise control
- **Entity match first.** A news item is attributed to a company only if (a) the source domain equals the company domain, or (b) the name matches an alias AND country or region agrees with the footprint. Name-only matches are never attributed. A "do not match" table stops repeat errors.
- **Watch per company:**
  - Context.dev monitor on the supplier's newsroom or status page (webhook on change).
  - Context.dev news search per company, every 30 min for tier-1 (A on rate limit).
  - Exa Monitor on sanctions and strike keywords per region (A).
  - PDF parsing of regulator notices where a link exists (stretch).
- **Classifier.** Six types: strike, plant closure or fire, port or logistics disruption, sanction or export control, insolvency, recall. Gemini gets the page text and the entity, and returns type, region, severity, quote. Confidence below 0.7 is never pushed.
- **Corroboration.** Confirmed = two independent domains within 72h, or one primary source (regulator or the company's own page, detected by a monitor change). Otherwise Unconfirmed.
- **Noise budget:** per company, at most 1 Confirmed alert per 24h, with the rest folded into the same incident. Cooldown of 6h on repeat types.
- **Latency.** Each alert stores `published_at`, `webhook_received_at`, `alert_at`. The UI shows p50 and p95 of each gap.

## 6. Incident-disjoint alternatives agent
- Input: incident footprint I, and client supplier S affected by it.
- Candidates: same product category from Cala and Exa Websets, plus Context.dev enrichment for each candidate's domain and facilities.
- Disjoint check, run per candidate C, dimension by dimension:
  - region(C) ∩ region(I) = ∅
  - plant(C) ∩ plant(I) = ∅
  - port(C) ∩ port(I) = ∅
  - sanction_programme(C) ∩ sanction_programme(I) = ∅
  - parent_company(C) ∩ parent_company(I) = ∅
  - corridor(C) ∩ corridor(I) = ∅
- **Unknown is FAIL.** If a dimension is missing for C, the candidate is rejected and the reason shown is "footprint unknown: port". This is the explainable rule.
- Ranking: passed candidates sorted by capacity fit (client-entered), then lead time (A). Top 3 shown.
- Human approval is required. Approve creates the switch order draft; placing it through Valio's mock API is optional (A, stack only if time allows).

## 7. Upstream and downstream
- Upstream: in as schema and a one-line footprint edge (`parent_company`), used by the disjoint check. Monitoring is out for demo.
- Downstream: out. Credit-risk news on customers is a natural extension, not built.

- **0:40 to 1:20 Live feed.** Each card shows the Confirmed/Unconfirmed badge, source URLs, the quote, and the latency tags.

## 9. Build plan, risks, cuts
- **Hours 0 to 6:** schema, Context.dev client, onboarding paste and enrichment (2 engineers).
- **Hours 6 to 16:** monitors, webhook receiver, entity resolver with review queue (2 engineers).
- **Hours 16 to 26:** classifier, verifier, corroboration, noise rules, latency columns (all four, in pairs).
- **Hours 26 to 32:** footprint, disjoint check, alternatives agent (2 engineers).
- **Hours 32 to 38:** feed, incident page, accuracy panel (2 engineers).
- **Hours 38 to 40:** labelled eval set, seeded demo data labels, backup video, freeze.
- Top risks: real news volume may be too low on demo day (mitigation: the SYNTHETIC change step); Context.dev monitor latency is (A) and must be measured early; entity matching errors (mitigation: strict name-only rule).
- Cut first: Valio mock order, PDF parsing, Exa Monitors, Cala beyond a single lookup, upstream monitoring.

## 10. Biggest weakness (honest)
The accuracy numbers come from a 40-item labelled set that we wrote, so they show the pipeline works on known cases, not that it generalises. A judge who asks for a larger test will find that the precision figure is not yet earned. The strict "unknown is FAIL" rule will also reject many alternatives in the demo, which is correct but may look thin.

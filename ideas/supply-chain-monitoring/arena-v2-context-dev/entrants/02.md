# Entrant 02: Fenceline (lens: Incident model first)
## 0. Bold bet (2 sentences)
Every incident is a typed object whose footprint is computed deterministically from the supply graph, and an alternative is offered only with a PASS on an explicit disjointness check that shows its proof, so judges see the hard rule enforced rather than claimed. Context.dev change monitors and news search produce the incidents live, with source URLs on every atom.

## 1. Summary and name
- **Fenceline**: a client pastes its supplier list; we build a private supply graph, watch every node with Context.dev, turn live changes into incidents with footprints, and propose alternatives that are provably outside the incident's footprint. Human approves; only then does the mock order go out.
- Data labels: real web sources show URL and retrieved-at. Seeded demo data (synthetic client list, staged notice page) is tagged SEEDED in the UI.

## 2. Architecture and DB
- One TypeScript service (API, workers, webhook receiver) on Aiven Runtime; Gemini as the only LLM; Aiven Postgres for everything (queue via `SELECT ... FOR UPDATE SKIP LOCKED`, JSONB footprints, relational overlap tables). No Kafka, no ClickHouse: fewer moving parts (A: Aiven Runtime deploys a Node service from a git push).
- Flow: Context.dev monitor or news poll -> `raw_event` (hash, url, fetched_at) -> Gemini relevance and extraction into a footprint *proposal* -> deterministic resolver maps names to graph IDs -> closure -> `incident` -> `alert` per affected client edge -> alternatives agent -> disjointness checker -> approval queue.
- Key rule: the LLM only proposes atoms. Closure, overlap and disjointness are plain code with unit tests.

## 3. Data model and incident footprint
- Tables (every client-owned row carries `client_id`; Postgres row-level security enforces the privacy rule): `client`, `company` (global facts: name, domain, country, Cala ID, Context.dev ID), `site` (company_id, region code, optional port), `edge` (client_id, from, to, tier, part/HS code, kind supplies|customer), `raw_event`, `incident`, `footprint_atom` (incident_id, kind, key, state), `alert`, `alternative`, `disjoint_check`.
- **Footprint atom kinds:** `company` (incl. parent group), `site`, `region` (hierarchical code, e.g. `FI-UUS` under `FI`), `port` (UN/LOCODE), `upstream` (plant or raw-material node, tier 2+), `regime` (sanction programme or list entry ID), `window` (start, end, open-ended allowed).
- **Atom state:** CONFIRMED (linked to a source URL), INFERRED (derived by closure, carries confidence and the rule used), UNKNOWN (no data for that kind on that company).
- **Closure rules (deterministic, depth capped at 3):** site -> its region and region ancestors; site -> its port if the site's logistics link says so; company -> parent group; company -> known upstream nodes; regime -> entities whose jurisdiction or ownership matches.
- **Incident footprint** = closure of the atoms extracted from the event, after resolution to IDs. Unresolved names are kept as `UNRESOLVED` and block auto-alerting until a human maps them.

## 4. Onboarding and bootstrap
- Paste or CSV: name, country, tier, part, HS code. Dedupe and normalise (A: under 2 seconds for 50 rows).
- Step 1, Context.dev company enrichment (batch): domain, HQ, parent. About 1 minute for 50 companies (A).
- Step 2, Cala: resolve ownership and investor edges, which feed the parent-group atom. Every edge stores the Cala source link. Seeded nodes are labelled.
- Step 3, Exa Websets: find sites and ports for companies missing them; async, 5-10 minutes (A). Results are CONFIRMED only with a page URL.
- Step 4, Context.dev scrape of each company's notices, sites and status pages to set up monitors.
- Target: a 50-company list is a monitored graph in about 10 minutes, with a progress screen per step. Tier-2 upstream is requested from the client and is allowed to be partial; partial means UNKNOWN, not safe.

## 5. Monitoring design
- Per company: (a) Context.dev page-change monitor on its notices/newsroom page, with webhook; (b) per site: status or notice page monitor; (c) Context.dev news search every 30 min on `"<company>" OR "<region name>" + strike|sanction|closure|fire|recall`; (d) PDF parsing of official sanctions annexes and port notices, monitored for hash change.
- Noise filter: content-hash dedupe; Gemini relevance score with threshold; an incident is CONFIRMED with one official source or two independent sources, otherwise PROPOSED.
- Latency: `t_source` (article published time, or Context.dev change time (A)), `t_received` (webhook or poll), `t_alert`. Dashboard shows p50 and p95 for each leg.
- Demo change: we stage an edit on a notice page we control, and label it as staged; all other sources are live.

## 6. Incident-disjoint alternatives agent
- **Candidates:** Exa company search (category company, query by part and HS code), Cala same-category companies, Context.dev enrichment of each candidate.
- **Check, per atom kind K in closure(incident) and closure(candidate):** PASS if no shared key and candidate's K is not UNKNOWN; FAIL on any shared key (exact ID, or region ancestor/descendant overlap, or same parent group); UNVERIFIED if candidate's K is UNKNOWN. An alternative is admitted only if every kind is PASS. Any UNVERIFIED is shown, never offered as "clear".
- **Proof object** (`disjoint_check.proof` JSON): per kind, both atom sets, the result, and source URLs. The UI renders it as a table of ticks and crosses.
- **Ranking** (only among admitted candidates): part and HS match, then region diversity, then lead time (A: lead time from candidate's own published data).
- **Validation:** Gemini summarises the candidate's capability claims from its scraped page, with the URL beside each claim.
- **Approval:** a human clicks Approve; the order goes to Valio's mock ordering API only then.

## 7. Upstream and downstream
- **Upstream: in, but narrow.** Tier-2 nodes and their plants are needed for the disjointness check, so we take them from client input, Cala, and supplier notice pages. Depth 2 for the demo.
- **Downstream: out of the demo.** Schema only (`edge.kind = customer`) and a news monitor on 3 named customers if time allows. Credit-risk scoring is not built.

## 8. Screens and demo script (timed)
1. Onboarding (0:00-0:40): paste 50-row list; progress per step (Context.dev, Cala, Exa); SEEDED tags visible.
2. Graph (0:40-1:00): private client view; click a node to see its monitors and last check time.
3. Live feed (1:00-1:30): staged change on a notice page fires a webhook; event appears with URL, excerpt, `t_source` to `t_alert` latency.
4. Incident (1:30-2:10): footprint tree (site, region, port, upstream, regime) with CONFIRMED and INFERRED marked; affected edges highlighted.
5. Alternatives (2:10-3:10): four candidates; two FAIL (same port, same strike region) with the failing row shown; one PASS with full proof table; one UNVERIFIED with the reason.
6. Approve (3:10-3:30): click Approve; mock order; latency summary.
- Coverage: impact (client's real edges), live web (notice page, news, PDF annex), completeness (all screens), latency (p50/p95 shown), real-timeness (feed updates while the judge watches).

## 9. Build plan, risks, cuts
- **Team, about 40h:**
  - E1: Context.dev monitors and webhook receiver, `raw_event`, polling, latency timestamps (h0-14).
  - E2: onboarding pipeline (Context.dev, Cala, Exa) and graph API (h0-16), then alternatives agent (h16-30).
  - E3: footprint model, closure, resolver, disjointness checker, proof tests (h0-24). Owns the lens.
  - E4: frontend screens, seeded demo client, latency dashboard, Valio mock wiring (h4-34).
- **Milestones:** h8 live webhook into DB; h16 incident with footprint and alert; h24 PASS and FAIL proofs on real data; h32 full demo flow; h36 freeze; h38-40 three rehearsals and backup video.
- **Risks:** webhook reachability at venue (mitigate: polling fallback every 60 s); Context.dev monitor latency and limits (A, to verify at h2); sparse upstream data gives many UNVERIFIED results (mitigate: a seeded, labelled case with full tier-2 data); Gemini proposing wrong atoms (mitigate: deterministic resolver, UNRESOLVED blocks alerts).
- **Cut order:** downstream first, then Cala depth beyond 1, then Websets (use Exa search), then PDF parsing, then Valio mock order (keep the approval button as a stub).

## 10. Biggest weakness (honest)
Upstream coverage is thin in real data, so most candidates will come out UNVERIFIED on tier-2 atoms; the PASS set in a live demo may be small. The demo therefore depends on one carefully seeded, labelled case, and a judge who asks for an unseeded company may see mostly UNVERIFIED results.

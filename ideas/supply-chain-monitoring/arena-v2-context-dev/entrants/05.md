# Entrant 05: Sixty-Second Bootstrap (lens: Exa/Cala bootstrap and entity resolution)

## 0. Bold bet
Ten pasted supplier names become a resolved, enriched, monitored graph in under 60 seconds, with every fact carrying a source URL. We bet that entity resolution quality, not the number of monitors, is what judges will trust.

## 1. Summary and name
**Tessera.** A client pastes or uploads a supplier list. Each name is resolved to one canonical company, enriched, and given live Context.dev monitors. The UI streams each row from "pending" to "monitored" with a visible clock.
- Division of labour: **Cala = identity spine** (canonical ID, ownership, funding). **Exa = discovery and disambiguation** (find the domain and candidate companies). **Context.dev = live web reader** (enrichment, page scraping, news, monitors and webhooks).
- Context.dev is in the critical path: resolution cannot finish a row without its enrichment, and every change event comes from its monitors.

## 2. Architecture and DB
- **Front end:** React with SSE for bootstrap progress and a graph view.
- **API and workers:** TypeScript (Node). One API process, one worker process, job queue on Valkey (BullMQ) **(A: BullMQ runs on Valkey)**.
- **Database:** Aiven Postgres for all state, plus Valkey for queues and per-domain rate limiting. No graph DB; edges are a table.
- **LLM:** Gemini for schema extraction and signal classification.
- **Webhook receiver:** public endpoint on Aiven Runtime, or a tunnel as fallback **(A)**.
- **Data flow:** paste → normalise → resolve (Cala, Exa, Context.dev enrichment) → score → write evidence → create monitors → webhook events → classify → signal feed.

## 3. Data model and incident footprint
- `clients(id)`; every client-scoped table carries `client_id`. The shared `company_cache` holds only public facts and never client edges.
- `suppliers(id, client_id, canonical_key, cala_id, domain, name, country, status, score, method)`. `canonical_key` = Cala ID if present, else domain.
- `supplier_aliases(supplier_id, alias, source)`.
- `evidence(id, supplier_id, field, value, source_url, source_system, fetched_at)`. Every enriched field has one row. This is the source of the "source URL" chips.
- `edges(client_id, from_id, to_id, kind, tier, confidence)`; kinds are supplies, customer and owns.
- `monitors(id, supplier_id, kind, target_url, webhook_id, status, last_event_at)`.
- `signals(id, supplier_id, monitor_id, detected_at, source_url, content_hash, kind, severity, quote)`.
- `footprint(supplier_id, dimension, value, source_url)`. Dimensions: region, port, plant, sanction_list. Filled from Context.dev scrapes of facility pages and a sanctions list load **(A)**.
- `incidents(id, type, region, started_at, source_url)` and `alerts`, `alternatives(incident_id, candidate_id, check_json, approved_by)`.
- Privacy: queries go through one repository layer that requires `client_id`, with a test that a second client gets zero rows.

## 4. Onboarding and bootstrap
**Per row, in parallel across 10 rows, with 20s stage timeouts:**
1. **Normalise (under 50 ms):** NFKD, casefold, strip legal forms (Ltd, Oy, GmbH, Inc, SA), keep the original for display. Accept optional country and domain hints per row.
2. **Candidate generation (1–3 s):**
   - Cala company lookup by name and country **(A: Cala exposes name search)**, returning the entity ID, legal name, domain, HQ and parent.
   - Exa search with the company category and a name query, with Contents used on top hits to confirm the homepage.
   - Any user-supplied domain is taken as a candidate with maximum domain weight.
3. **Enrich (2–4 s):** Context.dev company enrichment on the best candidate domain, giving canonical name, domain and country.
4. **Score (under 10 ms):** name similarity (Jaro-Winkler on normalised tokens, weight 0.5), country match (0.2), domain agreement across Cala, Exa and Context.dev (0.3). Thresholds:
   - 0.85 or above: auto-accept.
   - 0.60–0.85: one-click chooser shown on screen. This is the "judge can see the ambiguity" moment.
   - Below 0.60: unresolved, with a domain input.
5. **Merge:** if two rows share a canonical key, flag as duplicate or subsidiary (Cala parent link decides, **(A)**). Never silently merge.
6. **Scrape (5–10 s):** Context.dev scrape and structured JSON extraction of the homepage, with a facility or products page found by link text. Output feeds evidence and footprint.
7. **Monitor:** create monitors (section 5). Write `monitored`.

**Timing budget:** 10 rows finish in about 35–45 s at p50, with a 60 s hard cap. A row that times out shows partial evidence and a retry button. **Fallback:** 30 pre-resolved demo suppliers (labelled seeded) load instantly if the live APIs stall. The live path stays the default.

## 5. Monitoring design
- **Per supplier:**
  - Context.dev monitors with webhooks on the homepage, the news or press page, and the facility page. These fire on page change.
  - Context.dev news search for the supplier name, polled every 15 minutes.
  - Exa news search (date-filtered) as a second news source for corroboration.
- **Noise filter:** hash normalised page text, keep only changed blocks, then Gemini classifies `kind` (strike, sanction, plant closure, recall, insolvency, none) with a quote. Alerts require severity of medium or higher, with a 24 h dedupe per supplier and kind.
- **Latency:** three timestamps per event, namely monitor event time, webhook receipt time and alert render time. Report the end-to-end p50/p95 on screen. Monitor event time is only available if Context.dev provides it **(A)**; if not, report receipt-to-render.
- **Probe:** a synthetic change to a page on our own domain, labelled "synthetic", to demonstrate the pipeline on demand.

## 6. Incident-disjoint alternatives agent
- **Incident footprint:** the incident's region, ports, plants and sanctioned entities. The failed supplier's footprint is compared to each candidate's.
- **Check:** candidate is eligible only if the intersection is empty on region, port, plant and sanction_list, and its tier-1 suppliers do not overlap the failed supplier's tier-1 (upstream, section 8).
- **Explainable output:** a table with one row per dimension, showing "disjoint" or "shared", with the evidence source URL for each cell.

## 7. Upstream and downstream
- **Upstream: IN, lightweight.** Context.dev scrape of "suppliers", "partners" or "sourcing" pages on the top five critical suppliers. Edges are marked tier 2 and low confidence unless Cala confirms them.
- **Downstream: OUT.** Customer names are not reliably public. Cut first.
- **Alternatives sourcing:** Exa company search filtered by category and country, excluding the failed supplier's domain and its upstream domains. Cala peers in the same category are added **(A)**. Context.dev enrichment and a capability scrape validate each candidate. Gemini extracts the match.
- **Human approval:** the client approves in the UI. Only then can the optional Valio mock order fire.

## 8. Screens and demo script (timed)
**Screens:** (1) paste box and resolution grid with status, score bars and chooser; (2) graph with evidence chips; (3) supplier detail with sourced evidence and monitor status; (4) live signal feed with timestamps; (5) incident view with the disjoint table and approve button.

**Script (3:30):**
- 0:00–0:20 Problem statement and the claim: "ten names, sixty seconds, every fact sourced."
- 0:20–1:10 Paste ten names live. The clock runs. One row shows the chooser, and the judge clicks to resolve it.
- 1:10–1:40 Open a supplier. Show evidence with source URLs (Context.dev, Cala, Exa).
- 1:40–2:30 Live change: a monitored real page or news item fires a webhook. The signal appears with source URL and latency. **Fallback:** a replay of a real event captured before the demo, clearly labelled as recorded.
- 2:30–3:10 Incident: a region event hits a supplier. Footprint matches, alternatives appear with the disjoint table, and the client approves.
- 3:10–3:30 Map to the five criteria: impact, live use, completeness, latency and accuracy, and real-timeness.

## 9. Build plan, risks, cuts
**Build plan (40 h, 4 engineers):**
- **E1 (bootstrap):** resolution pipeline, Cala, Exa and Context.dev clients, scoring. Hours 0–14. Checkpoint at hour 10: one supplier resolved end to end.
- **E2 (monitors):** schema, monitor creation, webhook receiver, classifier. Hours 0–16. Checkpoint at hour 16: one real webhook stored.
- **E3 (front end):** paste grid with SSE, chooser, graph, supplier detail. Hours 0–16, then integration.
- **E4 (incidents and alternatives):** footprint, disjoint check, seeded fallback data, latency probe. Hours 10–26.
- **Hour 30:** 10-supplier bootstrap under 60 s on the live path. **Hour 34:** feature freeze. **Hours 34–40:** rehearsals, backup video recorded by hour 36.

**Top risks:**
- Cala coverage for small suppliers is thin. Mitigation: Exa and Context.dev fallback, and a visible "unresolved" state.
- Monitor detection latency is unknown **(A)**. Mitigation: replay fallback.
- Ten parallel calls hit rate limits. Mitigation: per-domain queues and cache.
- Webhooks need a public URL. Mitigation: Aiven Runtime or a tunnel, tested by hour 8.
- Name collisions. Mitigation: chooser and domain input.

**Cut order:** downstream, Valio order, Exa Websets (not used), people enrichment, graph animation, Exa news corroboration.

## 10. Biggest weakness (honest)
The 60-second claim depends on external APIs we do not control. Cala's coverage and latency for small suppliers are unknown, and resolution heuristics are validated on only a handful of names. If the live path stalls on demo day, the seeded fallback removes the "live" part of the bootstrap story.

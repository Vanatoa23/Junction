# Entrant 16: Tidewatch, a balanced supply-chain radar on Context.dev (lens: Balanced generalist)

## 0. Bold bet (2 sentences)
Every supplier on a client's list gets a Context.dev monitor on its own newsroom, status and filings pages, and a live change there fires a webhook that becomes an incident with source URLs in under 60 seconds. Alternatives are only offered after a visible, field-by-field "not the same incident" check against a footprint model that treats unknown data as a blocker, not a pass.

## 1. Summary and name
- **Tidewatch**: a client uploads its supplier list (tier 1, optionally tier 2). Tidewatch builds a private supply graph, watches every node with live web data, and when a watched source changes it opens an incident, scores exposure, and proposes a disjoint alternative for human approval.
- Context.dev is in the critical path three times: company enrichment (identity, domain, HQ), monitors with webhooks (change detection), and news search (incident discovery). Scraping plus structured JSON extraction turns changed pages into typed facts.
- Demo client is **synthetic** ("Northwind Foods", 30 invented suppliers, labelled SYNTHETIC in the UI). Monitored supplier pages are a mix of real public companies and three **our-own** mock status pages hosted on a public test domain (labelled), so a change can be triggered live and still produce a real webhook and real source URL.

## 2. Architecture and DB
- **Frontend**: Next.js on Aiven Runtime (one app, API routes plus UI). Simple, one deploy.
- **API and workers**: same Node/TypeScript codebase, two processes: `web` (API, webhook receiver) and `worker` (enrichment, extraction, alternative agent). Jobs in a Postgres table using `SELECT ... FOR UPDATE SKIP LOCKED`. No Kafka, no Valkey in MVP (Valkey only if webhook dedupe needs it).
- **DB**: Aiven managed Postgres (sponsor bounty). Single source of truth; ArcadeDB is cut.
- **LLM**: Gemini API for extraction-to-schema, severity classification, and alternative ranking rationale. Every LLM output is stored with its prompt version and input evidence IDs.
- **Context.dev**: enrichment (`company`), monitors (`pages` on newsroom, status, investor relations), news search, scrape with JSON extraction, webhook receiver `POST /hooks/contextdev` with signature check (A: HMAC header as documented by the SDK).
- **Exa**: bootstrap search with company category and domain filters; alternative candidate discovery.
- **Cala**: data source only: parent-company, investor and funding links feeding the upstream graph.
- **Flow**: client list → normalise → enrich → build graph → create monitors → webhook/news event → evidence row → classifier → incident → footprint match → alert → alternative agent → human approval → (optional) Valio mock order.

## 3. Data model and incident footprint
- `clients` (id, name), `client_members`. Every client-owned table carries `client_id`; Postgres row-level security keyed on it.
- `companies` (global, public facts only): id, canonical_name, domain, hq_country, cala_id, exa_id, contextdev_profile JSON, enriched_at. **Never contains client-specific edges.**
- `client_nodes` (client_id, company_id, tier, role, status), `client_edges` (client_id, from, to, kind: supplies | sub_supplies | customer). Private.
- `sites` (company_id, country, region code, city, lat/long, source_url, confidence): the footprint basis.
- `ports` and `regions` as reference tables (public, seeded from a fixed list, labelled).
- `monitors` (company_id, kind: page | news_query, cadence, contextdev_monitor_id, last_seen_at).
- `evidence` (id, source_url, fetched_at, published_at, content_hash, extracted JSON, snippet).
- `incidents` (id, kind: strike | sanction | port_closure | plant_outage | recall | fire, severity 1–5, status, detected_at, first_source_at, evidence_ids).
- `incident_footprint` (incident_id, dimension, value): dimensions are `region`, `site`, `port`, `parent_group`, `sanction_program`, `upstream_plant`.
- `exposures` (client_id, incident_id, company_id, match_dimensions[], confidence, state: affected | unverified | clear).
- `alerts` (client_id, incident_id, state: new | ack | acted, created_at).
- `alternatives` (client_id, replaces_company_id, candidate_company_id, incident_id, check_table JSON, rank, state: proposed | approved | rejected).

**Footprint rule (explainable):** a company's footprint is the set of its (region, site, port, parent_group, upstream_plant, sanction_program) tuples from `sites`, Cala parent links and tier-2 edges. An incident affects a company if any hard dimension overlaps with confidence ≥ 0.7. Missing footprint = `unverified`, shown as a warning, never auto-cleared.

## 4. Onboarding and bootstrap
- Input: paste or CSV upload (name, country, tier, optional domain). Max 60 rows for the demo.
- Step 1 (≤30 s): Context.dev `company` enrichment per row → canonical domain, HQ, logo. Unmatched rows flagged.
- Step 2 (≤60 s): Cala lookup for parent groups and investors, Exa search filtered by company category for missing sites (regional, port).
- Step 3 (≤60 s): Context.dev scrape of each domain's "locations / facilities" page with JSON extraction into `sites`. Sites with no source stay low confidence.
- Step 4: create monitors (page monitors on newsroom and status URLs found; news-query monitor per company). Show a progress bar and a "Ready: 42 of 48 nodes monitored, 6 need your help" summary.
- Target: 50 suppliers onboarded in under 3 minutes. Stated as an estimate (A), measured in rehearsal.

## 5. Monitoring design
- **Per company**: one news-query monitor (Context.dev news search: "<name> strike OR recall OR fire OR sanction OR port"), one or two page monitors (newsroom, status), and a monthly enrichment refresh.
- **Per region and port**: a shared news query (e.g. "Rotterdam port strike") so one incident fans out to all affected nodes.
- **Webhooks**: receiver verifies signature, stores raw event within 200 ms, enqueues job. Idempotency key = source URL + content hash.
- **Noise filter**: (a) content hash diff; (b) Gemini classifier returns {is_incident, kind, severity, sites, confidence}; (c) threshold 0.6 to create an incident, and high severity needs two sources or one authoritative domain; (d) 6-hour cooldown per (company, kind).
- **Latency**: three timestamps per event: `published_at` (source), `received_at` (webhook), `alerted_at` (UI). Show live p50 and p95 on the dashboard. Target: p95 under 90 s from webhook to alert.
- Filings: PDF parsing only for regulator notices where a URL exists (A). Otherwise cut.

## 6. Incident-disjoint alternatives agent
- Candidate pool: Exa search (category company, filters on the target's product and region), plus same-category companies already in `companies`. Sources only; no client edges read.
- Hard check per candidate, written as a table row per dimension: region, site, port, parent_group, upstream_plant, sanction_program. Result PASS, FAIL (with reason and evidence ID), or UNKNOWN. Any FAIL disqualifies. Any UNKNOWN blocks auto-proposal and marks the candidate "needs verification".
- Ranking among passing candidates: Gemini scores fit (capacity claim, product match) with evidence links; rank is shown with the check table.
- **Human approval** is mandatory: the approve button writes `alternatives.state = approved` and, if the Valio switch order is kept, places a mock order through Valio's mock API.

## 7. Upstream and downstream
- **Upstream: IN, light.** Tier-2 nodes come from supplier pages and Cala parent links, monitored with news-query monitors only. Used for the `upstream_plant` and `parent_group` checks.
- **Downstream: OUT of the demo, schema-ready.** `customer` edges exist in the schema; no monitors built. Mention as a next step, because customer credit signals need client data we do not have.

## 8. Screens and demo script (timed, 3:30)
- **0:00–0:25 Problem.** One sentence and the Northwind map (synthetic label visible).
- **0:25–1:10 Onboard.** Upload a 30-row CSV. Watch Context.dev enrichment logos fill and the "monitored" counter rise. Show the source URL on one site.
- **1:10–1:50 Watch.** Dashboard with monitors, cadence, last check and p95 latency. Click a node to see its evidence with source URLs.
- **1:50–2:35 Live change.** Edit one of our three mock status pages to "Plant B: strike from 17 Nov". Webhook arrives, incident card appears with source URL, timestamps and latency. Four suppliers flagged, one `unverified`.
- **2:35–3:10 Alternative.** Open the check table for a replacement candidate: region PASS, site PASS, port PASS, parent UNKNOWN → fixed by a Cala check, becomes PASS. Click Approve.
- **3:10–3:30 Close.** Map to the five criteria: impact, live web use, completeness, latency, real-timeness. Backup video starts if a live step fails.

## 9. Build plan, risks, cuts
- **Team split (40 h)**: E1 backend, webhooks, monitors, Context.dev client (0–18 h). E2 extraction, classifier, incident and footprint model, exposures (0–22 h). E3 Next.js UI, dashboard, onboarding, incident and check-table screens (0–26 h). E4 bootstrap (Exa, Cala, enrichment), seed data, Aiven setup, CRACI CI with SBOM, Codex use logged for bounty (0–14 h, then QA and backup video).
- **Milestones**: H4 DB and auth stub. H12 real webhook end to end on a mock page. H22 incident and footprint, alternatives check. H30 UI complete. H34 backup video recorded. H36 code freeze. H38–40 rehearsal ×3.
- **Risks**: Context.dev monitor latency and webhook semantics (verify in hour 1); Gemini rate limits (cache classifications); thin real footprint data (synthetic baseline, labelled); privacy regressions (RLS test in CI).
- **Cut order**: Valio order → downstream (already out) → PDF parsing → Cala beyond parent lookups → Exa Websets (use search only) → second page monitor per company.

## 10. Biggest weakness (honest)
The demo's real-world quality depends on public company footprints, which are sparse, so most "affected" and "unverified" results on real companies will be weak evidence; the strong demo relies on our own mock pages. Context.dev monitor latency and webhook retry behaviour are assumptions (A) until tested in hour 1, and if they are slower than the 90 s target the live step must be reframed as a pre-scheduled, labelled replay.

# Entrant 15: SecondSource (lens: Real-world impact)

## 0. Bold bet (2 sentences)
Build the demo around a real, recent incident class that hurt automakers: a single chip supplier whose ownership and China back-end site were the real single point of failure (the Nexperia export-control episode, Oct 2025). The product's claim is that a Tier-2 buyer would have seen it from public web signals hours before its own purchasing team did, and that an alternative is only offered if it fails the same-incident check.

## 1. Summary and name
- **SecondSource**: live monitoring of a client's supply base for disruptions, with incident-disjoint alternative suppliers and human approval.
- Who pays: a Tier-2 or Tier-3 maker (wire harnesses, electronics, castings) where one line stoppage at an OEM costs the client penalties and lost contracts. Reference pattern (verify figures before demo): JLR's cyberattack halted production for about five weeks in 2025; Novelis's Oswego aluminium fire hit Ford truck output in 2025; Nexperia's Oct 2025 export block forced OEM output cuts. In each case, the buyer's first signal was the OEM's own notice, not its supplier's.
- Demo client: **Kestrel Wiring Oy (SYNTHETIC, labelled)**, a fictional harness maker. Its seeded BOM links to real public companies, and all real-world incident data is shown with source URLs.

## 2. Architecture and DB
- Frontend: Next.js on Aiven Runtime. API: Node/TypeScript in the same app, plus one worker process.
- DB: **Aiven Postgres** (single source of truth). Recursive CTEs for upstream walks (depth 3). Row-level security keyed on `client_id`. No graph DB; not needed at this scale.
- Queue: Postgres `SKIP LOCKED` table as job queue (avoids Valkey setup time). Valkey only if time allows.
- Flow: Context.dev monitor webhook or news poll → normalise → Gemini classify (type, severity, affected entity) → incident candidate → footprint match against client graph → alert → Exa-based alternative search → footprint check → human approval → (optional) mock order via Valio API.

## 3. Data model and incident footprint
- `companies(id, name, domain, country, parent_id NULL, source_urls[])`: public, shared across clients.
- `edges(client_id, buyer, supplier, part_category, tier)`: **private per client**, RLS-enforced.
- `site_links(company_id, site_country, site_type [fab|backend|plant|port], site_ref, source_url)`: needed for the footprint check.
- `incidents(id, type [strike|fire|cyber|export_control|sanction|port|weather], status, first_seen_at, source_urls[])`: public.
- `incident_footprint(incident_id, dimension, value)`: dimensions `company`, `owner_group`, `site_country`, `backend_site`, `region`, `port`, `control_regime`.
- `alerts(client_id, incident_id, affected_company_id, hop_depth, created_at, latency_ms)`.
- `alternatives(client_id, incident_id, candidate_company_id, check_json, status [proposed|rejected|approved])`.
- Privacy rule: public tables never reference a client. Alternative search queries contain only part category and region, never the client name or BOM.

## 4. Onboarding and bootstrap
- Input: paste or CSV with supplier name, country, part category, and optional parent. Target onboarding time: under 2 minutes for 40 rows.
- **Cala** (data source, not a feature we rely on): resolve legal entity and parent/owner for each supplier, with its source. If Cala is unavailable, fall back to CSV owner fields.
- **Context.dev enrichment**: company domain, description, newsroom and government-notice URLs, people (for the approval screen). Batch processing for the list.
- **Exa**: find public newsroom pages and, for alternatives, a Websets query per part category.
- Bootstrap timing (A): 40 suppliers in about 4 minutes end to end, with enrichment running in the background while the map renders.

## 5. Monitoring design
- Per supplier, three watches:
  1. **Context.dev monitor with webhook** on the newsroom and operations-status page (change detection).
  2. **Context.dev news search** per supplier on a fixed query set: "strike", "fire", "cyberattack", "export ban", "sanction", "port closure", "shutdown", plus the supplier name (poll every 15 min, (A)).
  3. **Official-source watch**: scraped government and regulator notice pages (for example, export-control and sanctions announcements), with PDF parsing for PDF notices.
- Noise filter: Gemini classifies each item into type, severity (1–3), and affected entity. An item becomes an **incident candidate** only if (a) it comes from an official source, or (b) two independent sources report it within 24h. Near-duplicates are merged by URL and a normalised-title hash.
- Latency measured per alert: `source_published_at → webhook_received_at → alert_rendered_at`. Show p50 and p95 on the audit screen. Target p50 under 5 minutes for the webhook path (A).

## 6. Incident-disjoint alternatives agent
- Sources: Exa Websets for the part category (filtered to non-affected regions), plus Cala for supplier companies. Ranking: the client's existing qualification status first, then distance, then incumbent-to-candidate overlap in part category.
- **Check (fail-closed)**: a candidate passes only if the intersection of its footprint and the incident footprint is empty on every dimension: `company`, `owner_group`, `site_country`, `backend_site`, `region`, `port`, `control_regime`. It must also have no node within 3 hops upstream that is in the incident footprint. Unknown footprint means **fail**, shown as "unverified" and never offered as an alternative.
- Output is an explainable table, one row per dimension, with evidence URLs and the pass/fail result.
- Example (illustrative, Nexperia case): a candidate with a China back-end site in the same control regime fails `control_regime` and `backend_site`. A candidate with a non-PRC back-end and no shared owner passes every row. The table is the proof.
- Human approval: the buyer approves one alternative. Optional stacking: place the order through Valio's mock ordering API only after approval.

## 7. Upstream and downstream
- **Upstream: IN, one hop only.** Supplier's owner group and back-end sites (Cala and Context.dev). This is what made the Nexperia case visible: the risk sat in the owner and back-end, not the brand. Depth 2 and 3 are cut.
- **Downstream: OUT** for the demo. Show only a static "customer concentration" field to tell the story. Note as v2.

Screens: (1) supply map, (2) onboarding paste, (3) incident feed with source URLs, (4) incident detail with footprint, (5) alternatives check table, (6) audit and latency panel.
- 0:00–0:25: Context and the Nexperia story in one slide, with the real source URLs.
- 0:25–0:55: paste 12 suppliers, Cala and Context.dev enrichment fills in owner and newsroom URLs.
- 0:55–1:35: live feed. A replay lane shows archived real pages captured from the Nexperia and Dutch-government notices, with a live lane beside it when a real change occurs. Click the incident: source URLs, Gemini type and severity, and the affected supplier path (Kestrel → supplier → owner group).
- 1:35–2:20: alternatives. Show the check table; show one rejected candidate with the exact failing row.
- 2:20–2:50: approve one alternative; optional Valio mock order.

- Criteria mapping: impact (Nexperia-class incident), creative live web use (monitors, official notices), completeness (end-to-end), latency (audit panel), real-timeness (webhook path).

## 9. Build plan, risks, cuts
- Team split: A ingest and Context.dev monitors and webhooks; B Postgres, graph, footprint check; C UI and demo screens; D Gemini classification and Exa/Cala bootstrap. Everyone integrates at hours 26 and 34.
- Hours 0–8: schema, RLS, CSV import, Cala and Context.dev enrichment stubs.
- Hours 8–18: monitors and webhook receiver, news poll, Gemini classifier, incident candidates.
- Hours 18–26: footprint model and fail-closed check, Exa Websets alternatives, approval flow.
- Hours 26–34: UI, replay lane, audit panel.
- Hours 34–40: hardening, rehearsal ×3, backup video, freeze.
- **Cut order**: Valio order, then Websets (use Exa search), then Cala (CSV owner fields), then upstream beyond one hop, then the live lane (replay only, labelled).
- Risks: (1) no live incident during the demo window, so the live lane may be silent; mitigation is labelled replay plus a real monitor change to a real page we control. (2) Webhook delivery to a local demo needs a public Aiven Runtime URL. (3) Gemini misclassification; mitigation is the two-source or official-source rule. (4) Footprint data is mostly manual; mitigation is a fixed seeded footprint set for the demo companies, labelled.

## 10. Biggest weakness (honest)
The impact story rests on a real incident that may have changed by November 2026, and I could not verify the figures in section 1 against live sources in this pass. Footprint data (owner groups and back-end sites) is largely hand-seeded, so the "automatic" same-incident check is only as good as that seed. A judge who asks "how did you know the back-end site?" will get an honest answer, but it weakens the creative-use score.

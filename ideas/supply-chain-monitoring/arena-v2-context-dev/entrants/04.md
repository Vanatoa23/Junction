# Entrant 04: Tripwire, the ruthless demo path (lens: Ruthless minimum)

## 0. Bold bet
Context.dev monitors plus webhooks are the only change-detection path, and every alert, footprint and alternative is shown with its source URLs on a three-screen app. We cut everything that is not on one 3.5-minute demo path, including upstream/downstream, Cala, Valio and all Aiven services except Postgres and Runtime.

## 1. Summary and name
- **Tripwire.** A client pastes its first-tier supplier list (up to 15 rows). We enrich it, watch it live, and when an incident hits a supplier we propose alternatives that the same incident provably cannot touch. A human approves a switch intent.
- Demo path only: onboard 12 suppliers, watch them, see a live change detected via webhook, read the incident with source URLs, see the footprint, see 3 alternatives with pass/fail checks, approve.

## 2. Architecture and DB
- **Stack:** one Python service (FastAPI, server-rendered HTML with HTMX polling) on Aiven Runtime, one Aiven Postgres, Context.dev Python SDK, Gemini for classification.
- **One process:** web UI, `POST /hooks/cd` webhook receiver, and a worker thread that drains a Postgres job table (`FOR UPDATE SKIP LOCKED`). No Kafka, Valkey, ClickHouse, OpenSearch or ArcadeDB.
- **Flow:** Context.dev monitor fires webhook → verify secret, store raw payload in `signal`, enqueue → worker fetches structured extraction for the changed URL (Context.dev scrape/JSON extract) → Gemini maps it to the incident schema → footprint match → `alert` row → UI picks it up on 2s poll.
- **(A)** Webhook payload carries monitor id and changed URL; a separate call returns the extraction.

## 3. Data model and incident footprint
Eight tables:
- `client(id, name)`
- `supplier(id, domain UNIQUE, name, description, enrich_json, source_urls)`. Global public cache, with no client data.
- `supply_edge(client_id, supplier_id, category, tier)`. Private to the client.
- `tag(supplier_id, kind, value, source_url NULL, client_id NULL)`. `kind` is one of `region | plant | port | sanction_program | parent_group`. Rows with `client_id` set are client-entered and never visible to other clients.
- `monitor(id, supplier_id, cd_monitor_id, kind='page', url)`
- `signal(id, monitor_id, payload_json, received_at)`
- `incident(id, type, summary, footprint_json, source_urls[], published_at, detected_at)`
- `alert(id, client_id, incident_id, supplier_id, status)`, plus `alternative(id, alert_id, candidate_id, passed, checks_json, rank)` and `decision(alert_id, alternative_id, approved_at)`

**Footprint:** a set of tags per kind. An incident's footprint is the set of regions, plants, ports, sanction programs and parent groups it hits. A supplier is affected when any kind intersects. **Privacy:** every client query is scoped by `client_id` from the session. Only public web facts are shared across clients.

## 4. Onboarding and bootstrap
- **Input:** paste a CSV box (name, domain, category, plant town, port). No upload parser.
- **Enrichment:** Context.dev company enrichment per domain, 8 in parallel. **(A)** It returns name, description and HQ region. Target: 12 suppliers in under 60 seconds, with a live progress list.
- **Plant and port tags** come from the client's CSV. We do not need Cala.
- **Candidate pool:** a seeded CSV of about 40 companies across the same categories, labelled **SEEDED** in the UI. Optional Exa search export of one query per category, capped at 2 hours.

## 5. Monitoring design
- **Per supplier: 1 monitor** on its newsroom or status URL (24 monitors would be too many to demo). **(A)** Context.dev URL monitor with change webhook.
- **Staged source:** a page "Nordic Castings (SYNTHETIC test page)" hosted on our Runtime app. We edit it live during the demo. This proves the real Context.dev → webhook → screen path. It is labelled, and it is the only staged input.
- **Noise filter:** Gemini must return `type != none` with confidence ≥ 0.7, the source URL must be the changed URL, and dedupe runs on (supplier, type, day). A keyword pre-filter runs before the LLM.
- **Latency:** stamp `published_at` (from extraction), `webhook_received_at` and `alert_shown_at`. The alert footer shows `webhook +Ns`. We report p50 across the last 20 alerts.

## 6. Incident-disjoint alternatives agent
- **Sources:** the seeded candidate pool, filtered to the same category, then enriched by Context.dev for region, plant and port **(A)**.
- **Check (deterministic code, not an LLM):** for each kind in `{region, plant, port, sanction_program, parent_group}`, require `alt.tags[kind] ∩ incident.footprint[kind] = ∅`. If the candidate has no tag for a kind, record `unknown` and **fail** it. Fail-closed is the rule. The `checks_json` is shown row by row in the UI, so each rejection is explainable.
- **Ranking:** passed only, then same category, then a client-entered lead time as tie-break.
- **Validation:** rerun the check at approval time against the latest incident state, so no stale pass goes through.
- **Human approval:** the "Approve switch intent" button writes a `decision` row. There is no ordering API. Valio's mock API is dropped.

## 7. Upstream and downstream
**Out.** We keep only the `parent_group` tag because the disjointness check needs it. No upstream, downstream or credit-risk monitors, and no tables for them.

## 8. Screens and demo script
Three screens:
1. **Supply list:** paste box with live enrichment progress, then a table of suppliers with status dot, monitor state and last signal time.
2. **Alert:** incident type and summary, clickable source URLs, extracted quote, footprint chips, and the three timers (published, webhook, shown).
3. **Alternatives:** the affected supplier's footprint, then three candidate rows with a pass/fail grid per kind. One candidate fails on region, one on plant, one passes. Approve button on the pass.

**Script, 3:30:**
- 0:00–0:25 Problem statement. Paste 12 suppliers, enrichment runs live.
- 0:25–0:50 Screen 1: monitors active, source URLs visible.
- 0:50–1:50 Edit the staged page. Webhook arrives. Alert appears within seconds. Click the source URLs.
- 1:50–2:50 Footprint and alternatives. Walk the rejected candidates and their reasons. Open the passing one.
- 2:50–3:15 Approve. Show the decision row and timers.
- 3:15–3:30 Map to the five criteria, one line each.

Backup video recorded at hour 34.

## 9. Build plan, risks, cuts
**Plan (4 engineers, 40h):**
- A (ingest): monitors, webhook, job queue, worker. h0–14.
- B (data and onboarding): schema, CSV, enrichment, seeded pool, then the disjointness check. h0–10, then h14–24.
- C (incident): Gemini classifier, noise gate, footprint matching. h8–24.
- D (UI): three screens, HTMX polling, timers. h0–30.
- h24–34: integration and five full rehearsals. h34: backup video. h36: code freeze. h36–40: buffer.

**Risks:** Context.dev monitor latency is unmeasured **(A)**. The webhook must be reachable on Runtime. Gemini rate limits. Pre-run the staged classification to warm the cache. Fallback: replay the recorded signal from `signal`, labelled as replay.

**Cut first, in order:** news-query monitors, Exa, candidate enrichment (use CSV fields), HTMX polling (use manual refresh), per-client login (single demo session with a client switcher).

**Cut entirely:** upstream/downstream, Cala, Exa Websets and Monitors, Valio mock, Codex, Kafka, Valkey, ClickHouse, OpenSearch, ArcadeDB, PDF parsing, people enrichment, batch, MCP, SDKs other than Python, tiers beyond 1. CRACI only if its CI is free to add.

## 10. Biggest weakness
Real-world coverage rests on Context.dev monitors that we have not measured on real supplier newsrooms. The staged page proves the pipeline, not coverage. Also, plant and port tags are typed by the client, so the disjointness check is only as good as those tags. Fail-closed limits the damage, but a missing tag means a false "no alternative".

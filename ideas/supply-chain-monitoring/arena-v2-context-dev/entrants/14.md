# Entrant 14: Tideline, an observable event pipeline (lens: Pipeline architecture)

## 0. Bold bet (2 sentences)
Every Context.dev change becomes a durable, idempotent event that judges watch move through six named stages on a live wall, with a measured latency on every hop. We bet that visible, measured plumbing reads as "real-time" more convincingly than any risk dashboard.

## 1. Summary and name
- **Tideline**: the client pastes its supplier list; we monitor each company with Context.dev monitors and webhooks. A web change flows: webhook → queue → classify → entity match → impact → alternatives → alert.
- Context.dev is the event source, not decoration: monitors with webhooks (change detection), scraping plus structured JSON extraction (site footprint), company enrichment (domain, parent), news search (incident discovery).
- Stack: React + Vite front with SSE; Node/TypeScript workers on Aiven Runtime; **Aiven Postgres** for everything, including the queue (`SKIP LOCKED`). Gemini for classification. Exa and Cala feed bootstrap and alternatives.
- Cut from the start: Kafka, ClickHouse, OpenSearch, ArcadeDB. Postgres does all of it at 40-hour scale.

## 2. Architecture and DB
Stages, each an idempotent handler keyed on `(event_id, stage)`:
1. **Ingest**: `POST /hooks/cdev` verifies the signature (A: HMAC header, confirm in docs), inserts into `events` with `event_key = hash(monitor_id, content_hash)` under a unique index, and returns 200 in under 100 ms. A duplicate is a no-op.
2. **Queue**: `jobs(event_id, stage, state, attempts, run_after)`, claimed with `FOR UPDATE SKIP LOCKED`. Exponential backoff, then `dead` state, visible on screen.
3. **Classify**: Gemini returns a JSON-schema object (type: strike | sanction | port | plant | cyber | credit | other; severity; geo codes; named entities; confidence). Confidence below 0.6 becomes `watch`, not an alert.
4. **Entity match**: alias table, then Context.dev company enrichment for unknown names.
5. **Impact**: recursive CTE over `edges`, at most 3 hops, returns affected client nodes and tier.
6. **Alternatives**: only if severity is high and the node is single-sourced. Async, shown as progress.
7. **Alert**: writes `alerts`, pushes to the UI over SSE.

**Replay**: `POST /admin/replay?from=&stage=` re-enqueues. Handlers are pure given the payload and a versioned rule set. `stage_runs` stores input hash and output hash, so a replay that yields the same hashes is shown as "idempotent: 0 duplicates".

**Latency budget (p50 targets)**: ingest <100 ms; classify ~3 s; match and impact <200 ms each; alert <500 ms after impact; alternatives 20–40 s.

## 3. Data model and incident footprint
- `clients`, `companies(id, name, domain, country, cdev_id, parent_id)`, `aliases`, `monitors(company_id, kind, cdev_monitor_id)`.
- `edges(client_id, from_id, to_id, tier, kind: supplies | customer)`. Every client-scoped table carries `client_id` with Postgres row-level security.
- `events`, `jobs`, `stage_runs(event_id, stage, started_at, ended_at, latency_ms, status, attempts, in_hash, out_hash)`.
- `incidents(id, type, severity, confidence, detected_at, status)` plus `source_urls[]`.
- **Footprint**: `footprint(owner_type, owner_id, dimension, value)`. Dimensions: `region`, `site`, `port`, `sanction_list`, `parent`, `lane`. Incidents and companies both carry footprints.
- `alerts(client_id, incident_id, company_id, status)`, `alternatives(alert_id, candidate_id, score, disjoint_check jsonb)`.

## 4. Onboarding and bootstrap
- **A (5 s)**: CSV or paste with name, country, tier. Normalise and dedupe. Tier 1 required, tier 2 optional.
- **B (30–60 s, parallel)**: Context.dev company enrichment per domain for domain, HQ and parent; a scrape of each company's locations and investor pages with structured JSON extraction gives the site footprint. Batch processing if time allows (A).
- **C (20 s)**: Cala lookup for ownership and funding, as a sourced data source. Exa search (company category) fills missing tier-1 candidates.
- **D**: create monitors (§5). Progress streams to the same pipeline wall, so bootstrap is also visible.
- Target: 20 companies in under 2 minutes. Pre-cached results for demo companies, labelled SEED.

## 5. Monitoring design
Per company (A: monitor config shape, confirm in docs):
- **M1 site monitor**: scrape `/news`, `/press`, `/locations`, with JSON extraction `{plants[], ports[], notices[]}`. Hash on change. Interval 15 min in demo, 60 min in production.
- **M2 news monitor**: Context.dev news search for `"<company>" strike OR sanction OR fire OR recall`, hourly (A on cadence).
- **M3 filings** (optional, first cut): PDF parsing of regulator filings.
- **Noise filter**, in order: content-hash dedupe, keyword gate, Gemini confidence, and a two-distinct-domain rule for high severity.
- **Reconcile**: a job every 6 h upserts monitors by `(company_id, kind)`, so drift is repaired without manual work.
- **Latency**: `observed_at` (Context.dev timestamp, or our fetch time if absent) to `alert.created_at`, reported as p50 and p95 per stage.

## 6. Incident-disjoint alternatives agent
- **Sources**: Exa company search filtered by product category and region; Cala for same-category suppliers in other countries; the client's existing approved alternates.
- **Ranking**: capability match (Gemini tags from each candidate's own site, with a source URL), footprint distance, Cala funding and health, lead time.
- **Disjoint check (explicit)**: compare `footprint(candidate)` with `footprint(incident)` on every dimension: region, site, port, sanction list, parent, lane. Any shared key means FAIL. The result is stored in `alternatives.disjoint_check` and rendered as a table, e.g. "region FI≠NL PASS; port Rotterdam = Rotterdam FAIL".
- **Validation**: a candidate needs a capability source URL and a passing check. A failed check is rejected with its reason shown.
- **Human approval**: the candidate sits in an approval queue. Approve calls Valio's mock order API with idempotency key `alert_id + candidate_id` (secondary, optional).

## 7. Upstream and downstream
- **Upstream: in, depth 1.** Tier-2 comes from edges the client's tier-1 suppliers report. Shown as grey nodes. Same pipeline, one config value.
- **Downstream: stretch.** One scripted customer-insolvency news monitor, labelled. Not in the core demo.

## 8. Screens and demo script (timed)
- **S1 Onboard**: paste list, bootstrap lanes filling.
- **S2 Supply map**: the client's private graph, nodes coloured by status.
- **S3 Pipeline wall**: six lanes, event cards moving left to right, per-hop ms, p50/p95 counter. This is the centrepiece.
- **S4 Incident**: classification JSON, footprint, source URLs.
- **S5 Alternatives**: candidate cards with the PASS/FAIL disjoint table, then approve.
- **S6 Replay**: stop a worker, restart, replay; the wall shows "0 duplicate alerts".

**Script (3:30)**
- 0:00–0:20: hook, "the web is the database".
- 0:20–0:50: onboard 12 suppliers live (completeness, impact).
- 0:50–1:30: a live change on a monitored page, detected by webhook; wall lights up with latency (real-timeness, latency).
- 1:30–2:10: incident detail with source URLs (live web data, accuracy).
- 2:10–3:00: alternatives with disjoint table; approve.
- 3:00–3:30: replay for idempotency.

Mapping: impact (supply map), creative live use (site, news, webhook), completeness (end to end), latency (stage metrics), real-timeness (live wall).

## 9. Build plan, risks, cuts
- **E1 pipeline core (0–14 h)**: schema, ingest, queue, `stage_runs`, replay.
- **E2 Context.dev (0–12 h)**: monitor upsert, webhook verification, enrichment, news, scrape. Monitors pre-built for 20 seed companies.
- **E3 AI stages (8–22 h)**: Gemini classify and schema, entity match, impact CTE, footprints.
- **E4 UI (6–30 h)**: wall via SSE, map, incident and alternative pages.
- **Shared 22–36 h**: alternatives agent, disjoint check, approval.
- **36–40 h**: freeze at 36 h, three rehearsals, backup video.
- **Milestones**: H12 one event end to end with stub classify; H24 real change demo; H32 alternatives.
- **Risks**: a live change cannot be forced on real pages (mitigate: real monitors plus a labelled test page we edit); Context.dev webhook latency outside our control; Gemini JSON failures (schema-validated retry, then `watch`); Exa and Cala rate limits (cache demo results).
- **Cut first**: upstream, downstream, filings, Valio, Exa Websets. Keep: webhook, `stage_runs`, footprint, disjoint check.

## 10. Biggest weakness (honest)
The wall is plumbing, and judges may read it as a dashboard. If no real page changes during the four-minute slot, the wall sits idle, so the scripted test-page change must be rehearsed. Footprints are thin because suppliers rarely disclose plants or ports, so the disjoint check often rests on coarse region and parent keys.
